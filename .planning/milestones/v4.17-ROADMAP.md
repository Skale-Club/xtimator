## Overview

Fix a real regression against a locked v4.15 decision (tenant-facing surfaces still leak raw credit numbers), then polish the super-admin experience — clearer navigation with sensible grouping, better naming for two features the owner flagged as confusing, a credit-model-centric admin Billing page (replacing the stale tier/MRR view), and a visually premium Inbox redesign matching the rest of the admin's Phase-71 glassmorphism design system.

> **Numbering:** continues the GLOBAL phase counter. v4.16 ended at Phase 155. v4.17 starts at Phase 156.
>
> **Coverage:** 15/15 v4.17 requirements mapped (CREDITFIX-01..03, NAV-01..03, NAMING-01..02, BILLADMIN-01..03, INBOX-05..08). No orphans, no duplicates.
>
> **Locked scope guardrails:** No new backend/ledger logic — 100% reuse of the existing credit-ledger, `billing_config`, and cost-aggregation functions shipped in v4.7 (Phases 110-116) and v4.15 (Phases 150-153). The credit-leak fix (Phase 156) repairs an already-violated locked decision (CREDITUI-04 from v4.15) — ships first, independent of everything else. User-facing renames only — Legal Pages' public routes and the `legal_pages` DB table are untouched; Support Mode's internal functions/audit-log literals/cookie name are unchanged, only user-facing copy changes to "View as Company". The "Content" sidebar group is new UI work built from scratch. The Inbox redesign reuses Xtimator's own Phase-71 glass tokens/components, not a literal Xphere clone. All 4 phases are file-independent — no blocking dependency spine; the numbered order is the recommended execution sequence (most urgent/lowest-risk first, most subjective/highest-effort last).

## Milestone Summary

**Key Decisions:**

- Credit-leak fix (Phase 156) sequenced first, independent of everything else — it repairs an already-shipped, already-violated locked decision, treated as the highest-priority item in the milestone (Rationale: a live regression the owner personally found via screenshots, not a hypothetical)
- All 4 phases planned and largely executed in parallel (file-disjoint) rather than strictly sequential, since none actually depend on each other — cut milestone wall-clock time significantly (Rationale: the owner explicitly asked for this to be fully complete by the time they woke up)
- User-facing-rename-only for both Legal Pages→Pages and Support Mode→View as Company, mirroring the v4.16 WhatsApp→Inbox precedent exactly (Rationale: contains blast radius; avoids touching public routes, DB tables, audit logs, or cookies for a purely cosmetic/IA complaint)
- "View as Company" and "Message Template" were chosen without the owner's real-time confirmation, since they had gone to sleep — the AI made the best-judgment call and documented rationale in each phase's CONTEXT.md (Rationale: the milestone's explicit "fully autonomous overnight" mandate)
- Inbox redesign reuses Xtimator's own Phase-71 glass tokens/components rather than importing Xphere's literal CSS variables a second time — the v4.16 port had already tried "structure from Xphere, tokens from Xtimator" and still read as generic; this milestone added the missing visual richness (avatars, accent bars) using the SAME token strategy, just applied more thoroughly

**Issues Resolved:**

- STATE.md's frontmatter `milestone`/`milestone_name` fields intermittently reverted to a stale `v3.1.1` value after nearly every `gsd-tools.cjs phase complete`/`state`/`roadmap` command throughout this milestone (the same known recurring tool bug documented in v4.15/v4.16) — manually re-asserted after every occurrence
- A plan-checker revision round for Phase 156 caught a regression-guard test whose regex never matched the real violation shape (JSX-expression-rendered digits via `.toLocaleString()`, not literal digits in source) — the checker's OWN first suggested fix also had false-positive/false-negative problems, requiring a second empirically-verified iteration before it was genuinely correct
- A plan-checker revision round for Phase 159 caught the new avatar utility's test file living at a path `vitest.config.ts`'s include globs would never collect — would have silently reported "0 tests, exit 0" as a false pass
- The milestone-level integration audit caught one cross-phase gap neither phase's own scoped verification could see: a hand-maintained static-contract allowlist test (`billing-config.test.ts`) outside Phase 158's declared file-touch scope, which failed only when the full test suite ran
- A residual "Legal Pages" H1 heading (Phase 157's own goal-verifier flagged as an "accepted exception," but the phase's own CONTEXT.md verification checklist explicitly required a zero-result grep) was caught and fixed same-session, closing a real nav-label/page-heading inconsistency

**Issues Deferred:**

- Live-browser visual/contrast check of the redesigned Inbox (light + dark admin themes) and the overhauled admin Billing page — no live UAT was performed in this environment (no seeded admin credentials); both flagged as manual-verification items
- `TierCardsGrid`'s "Custom branding" (Pro) and "Stripe Connect payments" (Business) feature bullets have no code-level gate found anywhere — left as-is per the "no new backend logic" constraint, documented in-code as unverifiable/potentially-inaccurate claims for a future milestone to resolve properly
- The 4 creds-gated live-nav e2e tests from v4.16 (row-click, direct-link, empty-state, mobile collapse) remain pending real execution, still blocked on `TEST_ADMIN_EMAIL`/`TEST_ADMIN_PASSWORD`

**Technical Debt Incurred:**

- `topup-pack-card.tsx` retains an unused `credits` prop (destructured but never rendered, post-fix) — eslint-warning-only, not a build error, left rather than touching the component's prop contract for a cosmetic cleanup
- No historical revenue/MRR trend charting exists yet on the new credit-model admin Billing page (deferred to v2 as BILLADMIN-04) — this milestone shipped the current-state view first
