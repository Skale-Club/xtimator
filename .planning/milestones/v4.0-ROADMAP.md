# v4.0 Multi-Tenancy — Milestone Archive

**Status:** ✅ Shipped 2026-05-26
**Scope:** Multiple companies per user — schema, switcher UI, full RLS rewrite, action sweep, billing per-company, multi-company access on the companies table.

---

## Goal

A single user can own and switch between multiple companies; every tenant-scoped surface (projects, clients, estimates, price book, integrations, billing, notifications) is gated by the active company instead of `auth.uid()` ownership of a single `companies` row.

## Locked decisions

- **Roles:** Owner only for v4.0 (no Admin/Member tier — those are v5+).
- **Invites/teams:** explicitly out of scope (one user can own multiple companies, but a company has exactly one user).
- **Stripe Connect:** per-company (already aligned since Phase 70).
- **Backwards compat:** zero re-onboarding — migration auto-creates 1 owner membership per existing company.
- **`companies.user_id`:** kept (not dropped) — DROP COLUMN deferred to v5+ cleanup because of chain of legacy readers (auth.ts redirect, company.ts mode:'first', inngest transcribe attribution).

## Mode reflection

The Phase 79 + 81 flow used the full multi-agent pipeline (researcher → planner → 3-5 executor subagents → verifier). Phases 82-85 switched to **inline-pragmatic** execution: the work in each was mechanically uniform enough (one migration, or one codemod) that spawning a full subagent pipeline would have been pure overhead. The autonomous skill respected this — running each phase via single-purpose inline tools (Python, curl + Management API, Edit) while keeping the same artifacts (CONTEXT.md or SUMMARY.md, contract tests, atomic commits).

The decision rule: spawn the full pipeline when the work is exploratory (multiple files with non-uniform changes, ambiguous architecture, or UI design); execute inline when the work is mechanically uniform and the verification surface is a single contract test.
