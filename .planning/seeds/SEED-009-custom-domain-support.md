# SEED-009: Custom Domain Support for Clients

## Why This Matters

Currently all clients access their estimates via Xtimator's domain (e.g., `xtimator.com/estimate/{token}`). Some businesses — especially agencies, franchises, or branded service companies — want their clients to see a fully branded experience under their own domain (e.g., `estimates.mycompany.com`). This gives clients greater autonomy and trust, reinforcing the business's own identity rather than redirecting them to a third-party tool.

Custom domain support transforms Xtimator from "your estimate tool" into "your professional estimate platform" — a meaningful differentiation for sales-focused businesses.

## When to Surface

**Trigger:** When adding multi-tenant / white-label / client branding features

This seed should be presented during `/gsd-new-milestone` when the milestone scope matches any of these conditions:
- multi-tenant architecture
- white-label support
- client-side domain configuration
- subdomain routing per company
- CNAME / DNS configuration for estimates

## Scope Estimate

**Small** — A few hours of work. Main effort is subdomain routing logic and DNS configuration documentation. Does not require schema changes; primarily URL handling and middleware routing.

## Breadcrumbs

Related code and decisions found in the current codebase:

- `app/estimate/[token]/page.tsx` — public estimate page; uses `getEstimateByShareToken(token)` to fetch by share_token; renders `EstimateView` with `appName={branding.appName}` from `getBranding()`
- `app/estimate/[token]/layout.tsx` — forced light theme via `[data-theme="light"]` wrapper; sets layout context for estimate views
- `lib/queries/share.ts` — `getEstimateByShareToken()` uses service role client, fetches estimate by `share_token`, joins company + project + client data
- `lib/platform-config.ts` — `Branding` type with `canonicalBaseUrl: string | null` already exists on `platform_branding` table; this field could serve as the per-company custom domain configuration entry point
- `proxy.ts` — route protection with 404-rewrite pattern for admin gates; this same pattern could route subdomain requests to the estimate view without revealing platform internals
- `components/share/estimate-view.tsx` — renders company branding (logo, name, primary color) and `appName` in footer; this footer currently shows "Generated by {appName}" — would need to be conditionally hidden for white-label
- `platform_branding` (DB) — singleton row (id=1) with `logo_url`, `primary_color`, `app_name`; `canonical_base_url` field already present and could be extended for per-company domain mapping

Key existing infrastructure:
- `canonical_base_url` already stored in DB — natural place to add `custom_domain` column per company
- `EstimateView` already renders company branding — already white-label ready at the content level
- `proxy.ts` already has 404-rewrite routing pattern for sensitive paths

## Notes

Key implementation considerations:
- **No schema migration needed** — `canonical_base_url` and `app_name` already exist; only needs a `custom_domain` column on `companies` table
- **No middleware file exists** — `proxy.ts` handles route logic; could add subdomain detection there
- **Footer shows platform branding** — `EstimateView` footer "Generated by {appName}" would need a white-label mode (company toggle) to fully hide Xtimator
- **TLS/SSL** — Vercel handles certs automatically for apex + first-level subdomains; wildcard cert or per-company cert management is v2 territory
- **Token uniqueness** — share tokens already globally unique; no conflict with multi-domain
- **Auth boundary** — `/estimate/{token}` is already public (no auth required); custom domain routing just changes the host, not the auth model

This is distinct from current branding admin (logo/colors within platform) — custom domains remove the footer entirely and serve from the client's domain, not Xtimator's.
