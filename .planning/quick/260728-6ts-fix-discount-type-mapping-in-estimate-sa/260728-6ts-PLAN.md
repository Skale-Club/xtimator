<objective>
Fix a live, silent data-loss bug: `lib/actions/estimate.ts`'s discount-type
domain mapping (used by both `saveEstimate` and `recalculateEstimateTotals`)
only recognizes the editor-domain spellings `'percentage'`/`'fixed'`. AI-generated
estimates persist `discount_type: 'amount'` directly (`lib/services/generate-estimate.ts:554`),
and the editor's reducer passes that raw DB value straight through unnormalized
(`components/workspace/estimate/use-estimate-reducer.ts:132`'s `as 'percentage'|'fixed'|null`
is a compile-time cast only, not a runtime transform). Two compounding problems
result: (1) `lib/schemas/estimate.ts`'s `discountTypeSchema` currently REJECTS
`'amount'` outright (`z.enum(['percentage','fixed'])`), so the save fails
validation before the mapping even runs; (2) even if the value got through,
the 3-branch mapping falls through to `'none'` for anything it doesn't
recognize, silently zeroing the discount. This bug was discovered during
Phase 183 (PDF Parity Content) research — see
`.planning/phases/183-pdf-parity-content/183-RESEARCH.md`'s "Open Questions
#1" and "A related, more serious bug" sections — and explicitly deferred from
that phase's PDF-layer display-fix scope for a dedicated fix here.

Purpose: An owner who records a job walkthrough, gets an AI estimate with a
discount applied, and saves it (without first touching the discount-type
dropdown) must not silently lose that discount.

Output: `lib/schemas/estimate.ts`'s schema widened to accept the DB's actual
value space; a single shared `mapDiscountTypeToEngine()` helper in
`lib/actions/estimate.ts` replacing the two duplicated (and incomplete)
inline mappings; a regression test proving the fix.
</objective>

       //   'percentage' | 'fixed' — written by saveEstimate itself (schema-validated

       //
       // Previously this mapping only recognized 'percentage'/'fixed' and fell

         return 'none'
       }
