# Quick Task 260519-or1: OpenRouter Provider + Per-Company Model Override

**One-liner:** Add OpenRouter as a third AI provider with a searchable model
selector and let super-admins override the model per company so different
tenants can run on different models without code changes.

## Goal

Today the platform picks a single active AI provider (`anthropic` or `gemini`)
globally via `platform_integrations.ai_config`. The user wants:

1. **OpenRouter** as a third provider — single API key, hundreds of models from
   many vendors behind one OpenAI-compatible endpoint.
2. **Searchable model selector** for OpenRouter (catalog has ~300+ entries, a
   plain dropdown is unusable).
3. **Per-company override** — super-admin sets Company A → `model X`, Company B
   → `model Y`. The override implies OpenRouter (since that's where the model
   catalog lives).

## Scope

### In

- `openrouter` integration card on `/admin/integrations` (encrypted key, save,
  test, delete — same pattern as the other providers).
- Add `openrouter` to the active-provider selector. When selected, a
  searchable `cmdk` combobox lets the admin pick the platform-wide default
  model.
- `companies.ai_model_override TEXT NULL` column. When set, that company
  always uses OpenRouter with that specific model, regardless of the global
  active provider.
- New routes `/admin/companies` (list) and `/admin/companies/[id]` (per-company
  detail) with the model override field + reset button.
- `getAIProvider(companyId?)` resolution order:
  1. If `companies.ai_model_override` set → OpenRouter with that model.
  2. Else global `selected_ai_provider`:
     - `openrouter` → OpenRouter with `metadata.openrouter_default_model`.
     - `anthropic` → existing AnthropicAdapter.
     - `gemini` → existing GeminiAdapter.
- Thread `companyId` through the 4 existing `getAIProvider()` call sites.

### Out

- Per-company API keys (always uses platform OpenRouter key).
- Model capability badges, pricing display, context-window filtering.
- Migration of existing anthropic/gemini call paths to go through OpenRouter
  (they keep their direct SDK paths — OpenRouter is purely additive).
- Tests beyond a smoke test for the adapter and the override resolution.

## Decisions

- **D-1: Override storage** — single `TEXT` column on `companies`. Implicit
  contract: a non-null value means "use OpenRouter with this model id". No
  separate `ai_provider_override` enum because that doubles config surface
  for marginal benefit. If/when other providers need per-company overrides,
  switch to JSONB.
- **D-2: OpenAI SDK as transport** — OpenRouter is OpenAI-API-compatible, so
  `import OpenAI from 'openai'` with `baseURL: 'https://openrouter.ai/api/v1'`
  avoids hand-rolling fetch and tool-call parsing. (Already in deps via
  transitive — verify and add `openai` if missing.)
- **D-3: Tool-call JSON schema** — reuse the exact tool definition from the
  Anthropic adapter for `create_estimate`. OpenRouter passes it through to
  the target model; structured output is consistent across vendors.
- **D-4: Model catalog source** — fetch from
  `https://openrouter.ai/api/v1/models` server-side, cache 5 min in-memory.
  Admin-only API route (`requireAdmin()` guard).
- **D-5: Resolution precedence** — per-company override always wins. Reason:
  the user explicitly asked for "client A → model 1, client B → model 2"
  control, which would be defeated by global-takes-priority.
- **D-6: Fallback when override set but openrouter key missing** — HTTP 503
  with friendly message, matching the existing pattern (D-15 in phase 08).
