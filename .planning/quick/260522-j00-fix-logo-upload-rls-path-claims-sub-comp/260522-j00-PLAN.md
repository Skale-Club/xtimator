<objective>
Fix the broken logo upload in Company Settings.

The `logos` storage bucket has RLS policies (migration `20260409000001_initial_schema.sql` lines 349-369) that require the first folder of the object name to match a row in `companies` owned by the current user — i.e. `{company.id}/...`. Today, `updateCompanySettings` uploads to `{claims.sub}/logo.{ext}`, where `claims.sub` is the Supabase auth user UUID. Those two UUIDs are different, so every authenticated logo upload hits an RLS violation. The `try { ... } catch { ... }` block then swallows the underlying error and shows the generic "Failed to upload logo. Please try again." toast, with no trace in server logs.

Purpose: Restore working logo upload in /settings and stop silently swallowing storage errors so future regressions are debuggable.

Output: A 2-line edit to `lib/actions/settings.ts`. No new files, no abstraction changes, no test scaffolding (path-string fix requires real Supabase RLS to verify end-to-end; user will verify manually in the UI).
</objective>

```ts
async function getAuthContext() {
  const supabase = await createClient()
  const { data: claimsData } = await supabase.auth.getClaims()
  const claims = claimsData?.claims ?? null
  if (!claims) return { error: 'Not authenticated' as const }

  const { data: company } = await supabase
    .from('companies')
    .select('id')
    .eq('user_id', claims.sub)
    .single()

  if (!company) return { error: 'No company found' as const }

  return { supabase, company, claims }
}
```

From supabase/migrations/20260409000001_initial_schema.sql (lines 349-355 — the RLS rule we must satisfy):
```sql
CREATE POLICY "company_logos_insert" ON storage.objects FOR INSERT TO authenticated
  WITH CHECK (
    bucket_id = 'logos' AND
    (storage.foldername(name))[1] IN (
      SELECT id::text FROM companies WHERE user_id = (SELECT auth.uid())
    )
  );
```
First folder segment of the object name MUST equal a `companies.id` whose `user_id = auth.uid()`. `claims.sub` is `auth.uid()`, which is **not** the same value as `companies.id`.

Note: `storage.getPublicUrl('logos', ...)` keeps working with whatever path we upload — the bucket is `public:false` per migration line 273, so the public URL is non-resolvable for unauthenticated viewers, but that is **out of scope** for this fix (called out as an observation only). The fix here is strictly the path + error surfacing.
