<objective>
Remount the orphaned `WhatsAppConnectCard` on `/settings/integrations`. The component exists at `components/settings/whatsapp-connect-card.tsx` and is fully functional (connect via Meta number, OTP verification, delivery-format select, status badge, suspend/reactivate/disconnect) but is not rendered anywhere — Phase 90 rewrote the integrations page to show only the MCP Server entry card, dropping the WhatsApp card that Phase 45 had originally placed there.

This plan converts the integrations page from a static server component into an async server component that:
1. Fetches the active company's `company_whatsapp` row server-side (scoped to `getActiveCompanyId()`).
2. Maps that row into the card's `initial` prop shape (or `null` when no row exists).
3. Mounts `<WhatsAppConnectCard initial={initial} />` in a full-width section.
4. **Preserves** the existing MCP Server entry card (added alongside, not replaced).

NARROW SCOPE — this is the integrations-page-remount slice ONLY. It does NOT build the SendTab WhatsApp tab, the `/api/estimates/[id]/send-whatsapp` route, or the entitlement gate — those are Phase 81-02 / 81-03 work. `WhatsAppConnectCard` itself is NOT modified.

Purpose: Restore the user's ability to connect and manage their WhatsApp number from settings. Without this, the WhatsApp connect UI is unreachable.

Output: 1 modified page (`app/(app)/settings/integrations/page.tsx`) + 1 GREEN test suite (`tests/unit/whatsapp/integrations-page.test.tsx`).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server component → client component (`<WhatsAppConnectCard>`) | The `initial` prop crosses the server/client boundary and is serialized into the RSC payload. Only non-secret fields are passed: `phoneNumber`, `phoneNumberId`, `wabaId`, `status`, `deliveryFormat`. |
| server page → `company_whatsapp` table | Read scoped to `getActiveCompanyId()`; RLS on `company_whatsapp` gates by company ownership. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-QWA-01 | Information Disclosure | server-side `company_whatsapp` fetch | mitigate | The `.select(...)` lists ONLY `phone_number, phone_number_id, waba_id, status, delivery_format` — it explicitly does NOT select `verification_code`, `verification_expires_at`, or any access token (the platform Meta token lives in `platform_integrations`, never in `company_whatsapp`). No secret enters the RSC payload. Enforced by the acceptance-criteria check on the select string. |
| T-QWA-02 | Elevation of Privilege | reading another company's WhatsApp config | mitigate | The query is scoped to `getActiveCompanyId()` (the request user's validated active company per Phase 79's `company_members` RLS), AND `createClient()` is RLS-bound, so a cross-tenant read is doubly prevented. No arbitrary `company_id` can be injected — the id comes from the validated session resolver, not from user input. |
| T-QWA-03 | Denial of Service | unauthenticated / zero-membership access | accept | `getActiveCompanyId()` returns `null` for those cases; the page renders the card's connect form harmlessly. The (app) route group layout already gates authentication upstream, so an unauthenticated user never reaches this page. No additional control needed. |
</threat_model>
