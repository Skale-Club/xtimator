<implementation_notes>

**Adaptive submit decision (locked):**
On submit, branch on `currentEstimate`:
- **No estimate exists (`currentEstimate === null`):** Same path as `audio-recorder.tsx` + `estimate-tab.tsx::handleGenerate`:
  1. (Voice path) Upload audio blob to `audio` bucket → `createRecording()` → `transcribeRecording()` → `pollJob()` to wait for transcript.
  2. (Text path) `createTextRecording()` server action (already exists in lib/actions/recording.ts).
  3. Both paths then `fetch('/api/generate-estimate', { projectId, language })`.
  4. `router.push('/projects/{id}?tab=estimate')` and `router.refresh()`.
- **Estimate exists (`currentEstimate !== null`):** Always create a new VERSION (refining inline would not match the requirement "creating a new version"):
  1. (Voice path) Upload audio blob → `createRecording()` → `transcribeRecording()` → `pollJob()` (so transcript lands on the recording row, joining the corpus that drives generate-estimate).
  2. (Text path) `createTextRecording()` to add the typed instruction to the project's recording corpus.
  3. Both paths then `fetch('/api/generate-estimate', { projectId, language })` — the generate-estimate service already handles version increment (see `lib/services/generate-estimate.ts:212-224` — flips `is_current=false` on old rows, inserts new version).
  4. `router.push('/projects/{id}?tab=estimate')` and `router.refresh()`.

Rationale: `/api/estimates/[id]/refine` is stateless (no DB write — see route comments) and only useful when paired with the editor's reducer. For a header-level AI input, the unified "feed the corpus + re-run generate-estimate" path produces a clean new version and works identically whether or not an estimate exists. We do NOT use `/api/estimates/[id]/refine` in this task.

**Mobile touch targets:** circular buttons must be ≥44x44px (use `h-11 w-11` minimum). The Sparkles indicator is decorative — not a button.

**i18n:** Use existing `useTranslation()` t() pattern from audio-recorder.tsx for all visible strings. Add new keys to `tests/unit/i18n/` only if there's an existing harness — otherwise inline t() calls suffice (existing pattern: PT/ES translations are AI-generated at runtime).

**Visual style for the AI indicator:** Mirror the `gradient-brand shadow-glow-brand` + `Sparkles h-7 w-7 text-white` pattern from `estimate-tab.tsx:191-193`, scaled down to header size.

**File deletion safety:** When deleting `audio-tab.tsx`, `recording-list.tsx`, `recording-item.tsx`, search for ALL importers using Grep before delete. `audio-recorder.tsx` is special — its mic flow is the basis for `ai-voice-dialog.tsx`; copy the recording/upload/transcribe logic into the new dialog, then delete the original.

**Inngest cleanup function structure (mirror `notification-cleanup.ts`):**
- Export `runCleanupAudio(svc: ServiceClientLike): Promise<{ deleted: number; errors: number }>` — pure, testable.
- Export `cleanupAudioJob = inngest.createFunction({ id: 'cleanup-audio', triggers: [{ cron: '0 4 * * *' }] }, ...)` — daily 04:00 UTC.
- Algorithm:
  1. Query recordings where `created_at < (now - 7 days)` AND `storage_path IS NOT NULL`.
  2. For each row, call `createStorage(svc).delete('audio', storage_path)` inside a try/catch (continue on per-file failure, increment errors counter).
  3. Update the recording row to set `storage_path = null` so we don't re-attempt next day and the UI knows the audio is gone (recording row + transcript intact — see decision 4).
  4. Return `{ deleted, errors }`.
- Wrap the body in a single `step.run('delete-stale-audio-files', ...)` checkpoint.

</implementation_notes>
