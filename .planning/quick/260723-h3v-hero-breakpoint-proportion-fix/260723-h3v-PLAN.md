<objective>
User showed a hero screenshot and said the largest breakpoint (desktop, wide) looks great, but going down through the breakpoints the headline/button size and spacing "get unproportional." Diagnosed the actual bug: sm/md/lg each used an INDEPENDENT clamp() or flat Tailwind size, and consecutive segments' vw-computed values at their shared boundary didn't match — so text/buttons visibly SHRANK at the 640px and 768px transitions (viewport growing, text getting smaller) before growing again within each segment. Buttons additionally sat completely flat at their small mobile size across the entire 0-1023px range then jumped abruptly to full desktop size exactly at 1024px.
</objective>

<context>
- hero-section.tsx has a documented history of many prior dedicated quick-tasks purely to stabilize its cross-breakpoint behavior (h9x, u9c, and others referenced in code comments) — approached this conservatively: fix the provable monotonicity bugs, change nothing about line-wrap logic (`lg:whitespace-nowrap`, the `<br>` conditionals) or layout direction (`lg:flex-row`), and mathematically verify every new clamp() formula reduces to the CURRENT value at both the 375px mobile floor and the lg+ desktop ceiling before writing it, so mobile and the praised "role model" desktop look are both provably unchanged — only the transition between them changes.
- Button's true base padding is `has-[>svg]:px-3` (12px) when it contains an icon (the primary "Start" button does, via ArrowRight) — NOT the naive px-4(16px) default — this was verified by reading components/ui/button.tsx before computing the padding formula.
- One button property (the "See Demo" secondary button's horizontal padding) actually DECREASES from mobile to desktop (24px → 18px, an intentional design choice per the existing code) rather than increasing like everything else — its fix uses a simple two-step discrete value (24 → 20 → 18) instead of a continuous clamp, since the old code's actual bug there was overshooting DOWN to 16px (below the eventual 18px target) before correcting back up, not the general "flat then jump" pattern the other properties had.
- Also found and fixed one inconsistency in the real-touch-tablet (pointer:coarse) CSS in globals.css: the landscape 768-1279px block used a 40px button height at the same 15px font the portrait 640-1023px block pairs with 44px — no comment justified the smaller value, and landscape tablets in that width tier have at least as much room as portrait ones, so matched it to the proven 44px/15px pairing.
</context>
