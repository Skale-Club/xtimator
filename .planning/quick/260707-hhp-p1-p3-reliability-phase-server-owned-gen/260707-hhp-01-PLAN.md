<objective>
P1 (server half) + P2 of the reliability phase. Context: the generation pipeline is orchestrated
by the BROWSER (upload → createRecording → transcribeRecording → poll → POST generate → poll).
Every gap between client calls is a drop point — DB evidence shows attempts dying at different
links (07/03, 07/04, 07/06). The fix: the server owns orchestration after one dispatch call, and
a watchdog guarantees nothing hangs silently.

The chain infrastructure ALREADY EXISTS for audio: TranscribeAudioPayload.autoGenerateEstimate +
transcribe-audio.ts's 'dispatch-generate-estimate' step (lines 173-190), used in production by
inline-audio-recorder.tsx:168. This plan completes the pattern (photos + text), adds the composed
single-call action, the watchdog cron, and fixes a pre-existing bug in pipeline_attempts:
terminal_status uses precedence failed > started > succeeded, so ANY attempt containing a
'started' row (i.e., every multi-event attempt) reports 'started' forever — even fully completed
generations. Confirmed against production data.
</objective>
