# Phase quick-260705-c1y Plan 01: Telegram config + client + admin UI Summary

**A dormant-until-configured, server-only Telegram ops-alert transport (encrypted bot token + metadata chat_id) plus a Platform Alerts admin card with a working Save + Send test alert button — the credential-entry and outbound layer every later alerting plan builds on.**

## Performance

- **Duration:** ~10 min
- **Tasks:** 3
- **Files created:** 4
- **Files modified:** 5

## Accomplishments
- `'telegram'` is now a first-class `IntegrationProvider` in both the `lib/platform-config.ts` union and the `lib/schemas/admin.ts` `integrationKeySchema` enum, so the encrypted bot-token save validates and round-trips through the existing `saveIntegrationKey` path (no new migration).
- `getTelegramConfig()` reads the encrypted token + `metadata.chat_id` and returns `null` unless BOTH are present, keeping the whole system dormant until an operator configures it.
- `lib/telegram/client.ts` provides a server-only `sendTelegramMessage(text)` that POSTs to the Telegram `sendMessage` API (`chat_id`, `text`, `parse_mode: 'HTML'`), throws a clear `[Telegram] not configured` error when dormant, and throws with status + body on a non-2xx response — never logging or interpolating the token into an error.
- `saveTelegramChatId` and `sendTelegramTestAlert` server actions wire the admin flow: the chat_id save preserves the encrypted token and validates numeric (incl. negative-group) ids; the test alert is the single surface where a transport error reaches the operator.
- A `Platform Alerts` (`ops-alerts`) admin category renders the Telegram key card (existing `IntegrationCard`) plus a new `TelegramChatIdForm` with a Save button and a `Send test alert` button (reusing the existing `TestButton`).
