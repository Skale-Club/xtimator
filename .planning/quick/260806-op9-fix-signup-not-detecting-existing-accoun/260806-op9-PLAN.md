<objective>
Fix `signUp()` silently treating an already-registered email as a new signup.

This Supabase project has email confirmation ENABLED. With confirmation on, GoTrue's
anti-user-enumeration behavior returns, for an already-registered CONFIRMED email:
**no error**, plus a fabricated user object whose `identities` array is **empty** and
whose session is null. `lib/actions/auth.ts:56` destructures only `{ error }`, so the
action falls through to `redirect('/onboarding')` — a returning user who typed their
email into "Create an account" lands in onboarding for an account that already exists.
Reproduced in production with gt@gthomeimprovementma.com.

Purpose: returning users get told to sign in instead of being dumped into a
create-a-company flow for an account they already own.
Output: an `identities`-length guard in `signUp()` + regression tests for all three
signUp response shapes.
</objective>

3. AFTER the whole `if (error) { ... }` block and BEFORE the
   `logAuthEvent({ ...success: true })` / `safeInviteNext(next)` / `redirect()` logic,
   insert the guard:

```ts
  // GoTrue anti-user-enumeration: with email confirmation ENABLED, signing up with an
  // email that already has a CONFIRMED account returns NO error — instead it returns a
  // fabricated user with an EMPTY `identities` array and a null session, so an attacker
  // cannot probe which emails are registered. The empty `identities` array is the ONLY
  // signal available to this caller that the account already exists. A genuinely new
  // user always comes back with exactly one identity. Do not "simplify" this away, and
  // do not replace it with an email-existence probe — that would reintroduce the
  // enumeration hole GoTrue is closing.
  if (data?.user && (data.user.identities?.length ?? 0) === 0) {
    logAuthEvent({
      event: 'sign_up_attempt',
      success: false,
      email,
      error: 'email_already_registered',
    })
    return { error: 'An account with this email already exists. Sign in instead.' }
  }
```

Constraints on this edit:
- Optional chaining is load-bearing, not defensive noise: existing tests mock signUp as
  `{ error: null }` with NO `data` key, so `data?.user` must short-circuit and the guard
  must be inert there. `identities` is optional on Supabase's `User` type, hence
  `?.length ?? 0`.
- The guard must `return` — it must NOT fall through to `redirect()`, since
  `redirect()` throws for control flow and would discard the error.
- Placing it before `safeInviteNext` is intentional: an invited user who already has an
  account should be told to sign in, not sent into /invite/accept with no session. The
  invite branch itself is unmodified.
- `'email_already_registered'` is a sanitized literal, never a raw Supabase message.
  `sign_up_attempt` is the only valid event name here (see lib/auth-logger.ts
  `AuthEventName`); the logger sha256-redacts `email` itself.
- Return type stays `{ error: string }`, which components/landing/auth-dialog.tsx
  already renders via `onError(result.error)` — no client change needed.
