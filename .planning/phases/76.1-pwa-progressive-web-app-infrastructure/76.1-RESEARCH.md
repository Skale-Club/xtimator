## Summary

Phase 76.1 is substantially further along than the seed PLANNING.md suggests. A prior execution (likely from Phase 77 or the seed's ideation phase) has already built the core infrastructure: all four PWA icon files exist in `public/icons/`, a hand-rolled `public/sw.js` with correct cache strategies is committed, all three PWA client components (`InstallPrompt`, `OfflineIndicator`, `SWRegister`) are built and mounted in `app/(app)/layout.tsx`, and `app/offline/page.tsx` exists.

The seed PLANNING.md specifies `@ducanh2912/next-pwa` as the service worker library, but the project did NOT install it — instead it took the manual SW approach. This is actually the better choice for this project: `@ducanh2912/next-pwa` has not been updated in 2 years (latest 10.2.9), the maintainers themselves recommend migrating to `@serwist/next`, and the official Next.js 16 documentation now recommends the manual approach (hand-write `public/sw.js`) or Serwist. The hand-rolled SW in `public/sw.js` already covers all required caching strategies correctly and is compatible with `output: 'standalone'`.

What remains is a small set of gaps: (1) `viewport` export missing from `app/layout.tsx` (PWA installability requires it for Next.js 15+), (2) `apple-mobile-web-app-capable` and `apple-mobile-web-app-status-bar-style` meta tags missing, (3) `InstallPrompt` lacks the "≥1 estimate" gate, (4) create/record CTAs are not yet disabled when offline, (5) `sw.js` and `workbox-*.js` are not in `.gitignore`, and (6) Lighthouse Audit + manual device testing have not yet been performed.

**Primary recommendation:** Do NOT install `@ducanh2912/next-pwa`. Keep the manual `public/sw.js` approach. The phase is a completion effort — fill the 5-6 remaining gaps and run Lighthouse verification.

### Pattern 1: Next.js 15+ Viewport Export
**What:** `app/layout.tsx` must export a `viewport` const (separate from `Metadata`) for `theme-color` and `width=device-width` to be correctly injected as `<meta>` tags. The old `metadata.viewport` pattern is deprecated in Next.js 14.0+.
**When to use:** Required for PWA installability — Lighthouse checks for `theme-color` meta tag and proper viewport.
**Example:**
```typescript
// Source: https://nextjs.org/docs/app/api-reference/functions/generate-viewport
import type { Viewport } from 'next'

export const viewport: Viewport = {
  themeColor: [
    { media: '(prefers-color-scheme: dark)',  color: '#0a0a0f' },
    { media: '(prefers-color-scheme: light)', color: '#ffffff' },
  ],
  width: 'device-width',
  initialScale: 1,
  maximumScale: 1,
}
```

### Pattern 2: iOS Safari Apple Meta Tags
**What:** iOS Safari does not use `beforeinstallprompt`. Instead, the user manually taps Share → "Add to Home Screen". The meta tags below make the installed app behave correctly (no Safari chrome, correct status bar).
**Example (in generateMetadata or as static export — prefer generateMetadata for dynamic branding):**
```typescript
// In generateMetadata return value, or as <meta> in layout body
// Next.js does not have first-class support for apple-mobile-web-app-* in Metadata API
// Use <head> children in app/layout.tsx RootLayout:
<meta name="apple-mobile-web-app-capable" content="yes" />
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
<meta name="apple-mobile-web-app-title" content="Xtimator" />
// apple-touch-icon is already set via generateMetadata icons.apple
```

### Pattern 3: InstallPrompt "≥1 estimate" Gate
**What:** The seed spec requires showing the banner only after the user has at least one estimate. The current component has no such check. Since `InstallPrompt` is a client component, it cannot call server actions directly; it should receive a prop from the server layout.
**Approach:** Pass `hasEstimates: boolean` prop from `app/(app)/layout.tsx` (server component, already queries Supabase).
**Example:**
```typescript
// In (app)/layout.tsx — add to existing Promise.all:
const estimateCountRow = await requireServiceClient()
  .from('projects')
  .select('id', { count: 'exact', head: true })
  .eq('company_id', company.id)
  .limit(1)
const hasProjects = (estimateCountRow.count ?? 0) > 0

// Pass to component:
<InstallPrompt hasProjects={hasProjects} />
```

### Pattern 4: Offline CTA Disabling
**What:** Success criteria 5 requires create/record CTAs to be disabled with tooltip "Requires internet connection" when offline. The `OfflineIndicator` tracks `navigator.onLine` state but does not expose it to sibling components. A React context or a shared hook is the correct pattern.
**Approach:** Extract a `useOfflineStatus()` hook (or a simple context) that `OfflineIndicator` populates and the sidebar/topbar/capture buttons consume. Alternatively, since the "New Project" button is inside `Sidebar` and `MobileHeader` (client components), they can independently call `navigator.onLine` + listen to `online`/`offline` events — this avoids context complexity.
**Note:** The sidebar "New Project" button is at `href="/projects/new"` (found in `components/app-shell/sidebar.tsx:34`). The new project button in `components/dashboard/project-list.tsx` and `components/clients/client-new-project-button.tsx` also need the offline gate.

### Anti-Patterns to Avoid
- **Installing `@ducanh2912/next-pwa`:** The package is abandoned (2 years stale). Wrapping `next.config.ts` with `withPWA` when a working manual `public/sw.js` already exists would create duplicate service worker registration conflicts.
- **Blocking `/offline` from SW pre-cache:** The offline page must be pre-cached in the SW `install` event. The current `sw.js` does this correctly (`cache.addAll(['/offline'])`). Do not change this.
- **Using metadata.viewport (deprecated):** Next.js 14.0+ requires the separate `viewport` export. Using the old `metadata.viewport` string silently produces no output.
- **Caching `/api/*` routes:** The current SW correctly exempts all `/api/*` from caching (NetworkOnly). Do not change this — mutation routes, AI routes, and auth endpoints must never be cached.

## Common Pitfalls

### Pitfall 1: `viewport` Export Missing = Lighthouse Fail
**What goes wrong:** Lighthouse PWA "Installability" check requires `theme-color` meta tag. Without the `viewport` export in `app/layout.tsx`, Next.js 15+ does not inject `<meta name="theme-color">`, causing a mandatory Lighthouse failure.
**Why it happens:** The `Metadata` type deprecated `viewport` and `themeColor` fields in Next.js 14.0. They must now be in a separate `export const viewport: Viewport` in the same file.
**How to avoid:** Add the `viewport` export to `app/layout.tsx` with both `prefers-color-scheme` media variants.
**Warning signs:** Lighthouse reports "Does not provide a valid apple-touch-icon" or "Does not have a `<meta name=theme-color>` tag".

### Pitfall 2: iOS Safari `beforeinstallprompt` Never Fires
**What goes wrong:** `InstallPrompt` component listens for `beforeinstallprompt` event and shows the banner. On iOS Safari, this event NEVER fires — iOS Safari uses its own "Add to Home Screen" flow initiated by the user from the share menu.
**Why it happens:** Apple intentionally does not support the `beforeinstallprompt` API.
**How to avoid:** The current `InstallPrompt` is correct for Android Chrome. For iOS, the Lighthouse PWA test still passes as long as the manifest and meta tags are correct. The official Next.js docs recommend showing a static "Add to Home Screen" instruction for iOS users. Consider adding iOS-specific install instructions to the banner (detect via `navigator.userAgent`).
**Warning signs:** Banner never appears on iOS during testing — this is expected and not a bug.

### Pitfall 3: `sw.js` in `public/` Served Correctly by Next.js Standalone
**What goes wrong:** With `output: 'standalone'`, the `.next/standalone/` directory does NOT automatically copy `public/` files. The Dockerfile or deployment process must explicitly copy `public/` into the standalone output.
**Why it happens:** Next.js standalone output isolates the server bundle but requires manual public file copying.
**How to avoid:** The Hetzner Dockerfile (Phase 68) must include `COPY public ./public` after the build step. This is pre-existing infrastructure concern — verify the Dockerfile handles it.
**Warning signs:** `sw.js` returns 404 in the Docker build but works in `next dev`.

### Pitfall 4: Service Worker Scope and Auth Redirect Interaction
**What goes wrong:** The middleware proxy runs `updateSession` for all routes matching the config matcher. The `sw.js` file is served from `public/` and is a static file — it bypasses middleware automatically in Next.js. The `/offline` page IS matched by the middleware. If the user is unauthenticated and the SW navigates to `/offline`, the middleware will redirect to `/login`.
**Why it happens:** `/offline` is a regular Next.js page inside app router, not a public static file.
**How to avoid:** Either (a) add `/offline` to the proxy's public routes list (bypass auth), or (b) accept that `/offline` redirects to `/login` when unauthenticated — since the SW only shows `/offline` as a fallback for authenticated users who lose connectivity while already logged in, option (b) is acceptable. Verify behavior during QA.
**Warning signs:** Unauthenticated offline access redirects to login instead of showing the offline page.

### Pitfall 5: `workbox-*.js` in `.gitignore` — Not Applicable
**What goes wrong:** The seed spec says to add `workbox-*.js` to `.gitignore`. Since the project is using a hand-rolled `public/sw.js` (no Workbox code generation), no `workbox-*.js` files will ever be generated.
**Resolution:** Only add `sw.js` to `.gitignore` if you want to gitignore the manual file (which you probably do NOT want — it's the actual production code). Keep `public/sw.js` committed. Do NOT add it to `.gitignore`. The `workbox-*.js` pattern is irrelevant.

### Pitfall 6: `InstallPrompt` vs `SWRegister` Naming Mismatch with Seed
**What goes wrong:** The seed PLANNING.md specifies `components/pwa/use-install-prompt.ts` + `InstallBanner.tsx` as separate files. The actual codebase has `components/pwa/install-prompt.tsx` (a single file). The layout uses `<InstallPrompt />` not `<InstallBanner />`.
**Resolution:** The existing naming is correct and consistent. Do NOT rename or restructure. The seed spec predated implementation.

## iOS Safari Specifics (HIGH confidence)

iOS Safari (16.4+) supports PWA installation but with important differences:

1. **No `beforeinstallprompt` event** — installation is always triggered manually by the user via the Share menu → "Add to Home Screen". The `InstallPrompt` component handles Android Chrome via `beforeinstallprompt`. For iOS, you need a visible instruction telling users how to install manually.

2. **`apple-touch-icon`** — iOS uses the `apple-touch-icon` link for the home screen icon, not the manifest `icons` array. The current `generateMetadata` in `app/layout.tsx` already sets `icons.apple` pointing to the branding logo or fallback — this is correct.

3. **`apple-mobile-web-app-capable: yes`** — required for the installed app to launch without Safari's browser chrome. Without this, the app opens in Safari (with address bar) instead of standalone mode.

4. **`apple-mobile-web-app-status-bar-style`** — controls the status bar color in standalone mode. `black-translucent` is correct for a dark-first app (status bar overlays content, app gets full screen height).

5. **iOS 16.4+ required for push notifications** — out of scope for this phase, but relevant context.

6. **Splash screen** — iOS generates the splash screen from `apple-touch-icon` + `background_color`. No custom splash screen configuration is needed; the current manifest `background_color: '#0a0a0f'` is correct.

### Offline CTA Disabling Pattern
```tsx
// In any client component button that creates/records:
'use client'
import { useState, useEffect } from 'react'

function useIsOffline() {
  const [offline, setOffline] = useState(false)
  useEffect(() => {
    setOffline(!navigator.onLine)
    const onOnline  = () => setOffline(false)
    const onOffline = () => setOffline(true)
    window.addEventListener('online', onOnline)
    window.addEventListener('offline', onOffline)
    return () => {
      window.removeEventListener('online', onOnline)
      window.removeEventListener('offline', onOffline)
    }
  }, [])
  return offline
}

// Usage in New Project button:
const offline = useIsOffline()
<Button disabled={offline} title={offline ? 'Requires internet connection' : undefined}>
  New Project
</Button>
```
