<objective>
Build the single pure, client-safe module that is the composer's source of truth: given a literal body-text string (with `{{1}}`, `{{2}}`... tokens already positioned by the UI, never free-typed) and an ordered `ComposerParam[]` (label + example per position), derive Meta's `BODY` component shape, and validate the pair against Meta's documented auto-reject rules before anything is ever submitted.

Purpose: TMPLCOMP-01 requires that ONE ordered array drives the body text, `example.body_text`, and (downstream, in Plan 179-03) `variables_schema` — never three independently-editable duplicates that can drift apart (the exact class of bug the research's Pitfall 3 identifies as silent and unrecoverable once Meta approves a template). This module is that single source of truth, decoupled from any server/DB/fetch concern so it can be imported directly by the client-side composer component in Plan 179-04 with zero risk of pulling server secrets into the browser bundle.
Output: `lib/whatsapp/template-composer.ts`, fully unit-tested against every rejection rule the research verified against Meta's official docs.
</objective>

<interfaces>
Target shape this module produces (verified Meta payload shape — 179-RESEARCH.md §"Full creation payload"):
```json
{
  "type": "BODY",
  "text": "Hi {{1}}, your estimate \"{{2}}\" has been updated.",
  "example": { "body_text": [["John Smith", "Kitchen remodel"]] }
}
```
Note the DOUBLE array: `body_text` is an array of "example rows" (Meta supports multiple example sets); this module always emits exactly ONE row — `[params.map(p => p.example.trim())]`.

Meta's documented auto-reject rules this module's `validateComposerTemplate` must mirror (179-RESEARCH.md Pitfalls 1-2, HIGH confidence, directly quoted from `developers.facebook.com/.../templates/template-review`):
- "Absence of sample variable values when templates use variables" — every param needs a non-empty `example`.
- "Variable parameters are missing or have mismatched curly braces" / "are not sequential" — `{{n}}` tokens in the body must be exactly `1..params.length` in order, no gaps, no duplicates.
- "The message template cannot start or end with a parameter."
- Body component char limit: 1024 (179-RESEARCH.md §"Don't Hand-Roll" / Components doc).

    Create `lib/whatsapp/template-composer.ts`. No imports beyond TypeScript built-ins — this file must be safe for a `'use client'` component to import directly (no `fetch`, no `getWhatsAppPlatformConfig`, no server-only module).

    Export:
    ```typescript
    export interface ComposerParam { label: string; example: string }
    export interface ComposerValidationResult { valid: boolean; errors: string[] }
    export function nextVariableToken(params: ComposerParam[]): string
    export function validateComposerTemplate(bodyTemplate: string, params: ComposerParam[]): ComposerValidationResult
    export function buildBodyComponent(bodyTemplate: string, params: ComposerParam[]): { type: 'BODY'; text: string; example: { body_text: string[][] } }
    ```

    Implementation notes:
    - Use a `/\{\{(\d+)\}\}/g` pattern to extract token indexes from `bodyTemplate.trim()`.
    - "Sequential" check: the extracted index sequence, in order of first appearance, must equal `[1, 2, ..., params.length]` exactly (covers gaps, duplicates, reversal, and count mismatch in one comparison).
    - "Starts/ends with a variable": test the TRIMMED body against `/^\{\{\d+\}\}/` and `/\{\{\d+\}\}$/`.
    - Char limit constant `BODY_CHAR_LIMIT = 1024` — named, not a magic number.
    - `validateComposerTemplate` never throws; accumulates ALL applicable errors into one array rather than returning on the first failure.
    - Document at the top of the file (per research Pattern 1 + Anti-Patterns): this module is the single source of truth an admin's composer UI must drive everything from — never let free-typed `{{n}}` syntax bypass it.
