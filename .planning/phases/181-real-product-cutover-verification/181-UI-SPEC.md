# Phase 181 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

This phase introduces **zero new visual components, zero new colors, zero new typography scale values**. Per `181-RESEARCH.md`, the phase's only genuine UI-affecting change is making the real `SettingsLayoutClient`/`SettingsNav` rail reachable for demo sessions (replacing a bespoke collapsed single-form view that currently intercepts `/settings/*` for demo), filtering that rail's tab list to three items, and making the three now-exposed tab forms render read-only using each form's **existing** `readOnly`/`canManage` props (two of the three need zero new prop-plumbing beyond wiring; the third — `NotificationsForm` — needs one small, new `readOnly` prop). Landing-CTA href edits and dead-file deletion carry no visual contract at all (no label/style change, no rendered page left behind to spec). This contract's job is narrow and load-bearing: lock down exactly which settings tabs are visible in demo, and exactly how "read-only" should look on the three exposed forms, so it matches the ONE pattern the codebase already established (`CompanyInfoForm`'s `fieldset disabled` + swapped footer text) rather than inventing a second one.

Every value below is pre-populated from `181-CONTEXT.md`'s locked decisions (D-15 through D-19), `181-RESEARCH.md`'s direct file reads, and this session's own direct reads of `components/demo/demo-banner.tsx`, `lib/demo/guard.ts`, `components/settings/company-info-form.tsx`, `components/settings/team-section.tsx`, `components/settings/notifications-form.tsx`, `components/settings/settings-nav.tsx`, `components/settings/settings-layout-client.tsx`, `components/app-shell/nav-items.ts`, `components/app-shell/mobile-account-menu.tsx`, and `app/globals.css`. No question required user input this session — CONTEXT.md's auto-mode decisions plus RESEARCH.md's Open Question 1 recommendation resolve every design-contract question below without re-asking.

**Visual focal point:** on each newly-reachable settings surface, the eye lands first on the `SettingsNav` rail's active-tab state (existing accent-colored indicator, unchanged), then on the swapped footer note ("This is a read-only demo...") as the confirmation signal that the form is intentionally non-editable — no new visual anchor is introduced; both are the codebase's existing patterns applied verbatim.

## Read-Only Presentation Contract (phase-specific — supplements the template)

This is the one substantive design decision this phase makes. It is a direct extension of the **one pattern already proven in production** by `CompanyInfoForm`, applied consistently to the two other exposed forms.

### 1. Settings entry point + layout — un-hide, don't redesign

- `components/app-shell/sidebar.tsx` and `components/app-shell/mobile-account-menu.tsx`: remove the `{!isDemo && ...}` wrapper around the **Settings** `<DropdownMenuItem>`/`<Link>` only. **Trash stays wrapped** — it is not in the exposed list (D-15). Zero new markup, zero new classes — this is an unwrap, not a redesign.
- `app/(app)/settings/layout.tsx`: delete the `isDemoSession()` branch that renders a bespoke collapsed `<CompanyInfoForm readOnly />`-only view. Both demo and real-tenant requests now render the same `<SettingsLayoutClient>{children}</SettingsLayoutClient>` tree, unconditionally. This is what makes PARITY-01 ("same layout, navigation, components, styling") true — there is no demo-specific visual variant of the settings shell left anywhere.

### 2. `SettingsNav` — reuse the exact `demoHidden`-flag-plus-filter shape already used for the primary app nav

`components/app-shell/nav-items.ts` already has this pattern (`demoHidden?: boolean` on each item, filtered via `NAV_ITEMS.filter((item) => !(isDemo && item.demoHidden))`). `components/settings/settings-nav.tsx`'s local `ITEMS` array gets the identical shape — same flag name, same filter idiom, no new visual states (an item is either rendered with its current active/inactive/hover styling, or not rendered at all; there is no third "visible but disabled" state anywhere in this contract, consistent with D-16).

**Locked visible/hidden list** (resolves `181-RESEARCH.md`'s Open Question 1 using its own stated recommendation — conservative default, matches D-15's closed framing):

| Tab | `value` | Demo visibility |
|-----|---------|------------------|
| Company | `company` | **Visible** |
| Team | `team` | **Visible** |
| Notifications | `notifications` | **Visible** |
| Account | `account` | Hidden (`demoHidden: true`) |
| Estimates | `estimates` | Hidden (`demoHidden: true`) |
| Plans (billing) | `billing` | Hidden (`demoHidden: true`) |
| Message Template | `templates` | Hidden (`demoHidden: true`) |
| Knowledge | `knowledge` | Hidden (`demoHidden: true`) |
| Integrations | `integrations` | Hidden (`demoHidden: true`) |

The redirect target for every hidden-tab route-level guard is `/settings/company` — always itself in the exposed set, so a demo visitor who bookmarks/guesses a hidden URL never lands somewhere the nav can't show (Pitfall 2 from RESEARCH.md). Redirects are **silent** (`redirect(...)`, no toast, no banner, no query param) — matches every existing guard in these same files (e.g. `redirect('/onboarding')`); do not introduce a new "you were redirected" notice pattern.

Non-nav pages reachable only by direct URL (`appearance`, `delivery`, `defaults`, `staff`, `custom-domain`, `payments`, `integrations/mcp`, `integrations/stripe`, `knowledge/[id]`, `knowledge/new`) need the same silent route-level guard for the same reason, even though they were never in the visible list — this is a routing completeness note for the planner, not an additional visual state.

### 3. Read-only form treatment — one pattern, three forms

**Company tab (`CompanyInfoForm`) — zero new UI, wiring only.**
Component already implements the full contract: `<fieldset disabled={readOnly} className="m-0 min-w-0 space-y-8 border-0 p-0">` around every field, and — after the fieldset, as a sibling — a conditional swap between the `Save Company Info` button and a muted footer paragraph:
```
{readOnly
  ? <p className="text-sm text-muted-foreground">This is a read-only demo. Create a free account to edit your profile.</p>
  : <Button type="submit" ...>Save Company Info</Button>}
```
`(tabs)/company/page.tsx` only needs `<CompanyInfoForm company={company} readOnly={isDemo} />` (currently passes no `readOnly` at all). No component-level change.

**Team tab (`TeamSection`) — zero new UI, wiring only.**
Every mutation control (`Invite` button/dialog, per-member role `Select` + Remove `AlertDialog`, per-invite Revoke `AlertDialog`) is already gated behind the existing `canManage` boolean, and already renders a plain role-label pill (`<span className="text-xs font-medium rounded-full border px-3 py-1 text-muted-foreground">`) in place of manage controls when `canManage` is false — the exact same treatment a real non-owner/non-admin member sees today. `(tabs)/team/page.tsx` forces `const canManage = isDemo ? false : (role === 'owner' || role === 'admin')`. **No demo-specific copy or badge is added** — reusing the existing "member, no controls" visual state is the correct minimal diff; do not add a new "(demo)" label or tooltip to the role pill.

**Notifications tab (`NotificationsForm`) — one new prop, extending the proven pattern.**
Add `readOnly?: boolean` to `NotificationsFormProps`. Apply the *exact same mechanism* `CompanyInfoForm` already uses, extended to cover both Cards in one wrap (the component currently has no single top-level `<form>`, so the fieldset becomes the outer wrapper in place of the current root `<div className="space-y-6">`):

```tsx
<fieldset disabled={readOnly} className="space-y-6 border-0 p-0 m-0">
  <Card>{/* master email-digest switch + category matrix + Save preferences button — unchanged markup */}</Card>
  <Card>{/* browser notifications enable/disable button — unchanged markup */}</Card>
</fieldset>
{readOnly && (
  <p className="mt-6 text-sm text-muted-foreground">
    This is a read-only demo. Create a free account to manage your notification settings.
  </p>
)}
```

Deliberate, minimal divergence from `CompanyInfoForm`'s pattern, stated explicitly so it isn't mistaken for an inconsistency: `CompanyInfoForm` *swaps* its single Save button for text; `NotificationsForm` has **two** independent action buttons across two Cards (`Save preferences`, `Enable/Disable browser notifications`). Rather than conditionally unmounting both, the native `fieldset disabled` cascade disables every `Switch` and both `Button`s in place (each already renders shadcn's built-in `disabled:opacity-50 disabled:cursor-not-allowed` treatment — zero new CSS), and a single muted footer note (identical classes/position pattern to `CompanyInfoForm`'s) explains why. This is the "smaller, more consistent diff" `181-RESEARCH.md` itself recommends for this component. `(tabs)/notifications/page.tsx` passes `readOnly={isDemo}`.

The SMS-consent inline confirmation panel (`smsConsentPending` state) and its two buttons are also inside the fieldset and therefore inert for demo — no separate handling needed; a disabled `Switch` cannot trigger `setChannel`, so `smsConsentPending` can never become true in a demo session. No extra guard required.

### 4. Landing CTAs — no visual contract, href only

`components/landing/hero-section.tsx`, `final-cta-section.tsx`, `landing-footer.tsx`: `href="/demo"` → `href="/demo/entry"`. Label ("See Demo"), icon, size, variant, and position are **unchanged** — this is a pure link-target edit, zero visual diff.

### 5. Dead-code removal — no visual contract

`app/demo/page.tsx`, `app/demo/layout.tsx`, `app/demo/{dashboard,clients,projects,price-book}/{page,loading}.tsx`, `components/demo/demo-nav.tsx` are deleted outright. `/demo` 404s via Next's default not-found handling per D-19 (no custom redirect/copy authored). `app/demo/entry/route.ts` and `components/demo/demo-banner.tsx` are explicitly **not** touched — confirm the two are not conflated during deletion (they are separate files with similar names).
