<objective>
Close carry-forward (b) from Phase 172 (172-03-SUMMARY.md, "Email double-escape trap"): once Plan 174-04 wires `notify()` to resolve `channel='email'` through `resolveNotificationCopy` (html mode — already HTML-entity-escaped by `template-engine.ts`'s `escapeHtmlValue`) and stash it on the notification row for the digest worker to consume, that value must NOT be piped through `lib/email/notification-emails.ts`'s own `escapeHtml()` a second time — doing so corrupts entities (`&amp;` → `&amp;amp;`).

This plan builds the CONSUMER side of that fix — independent of, and parallel to, Plan 174-01 (the producer-side default-enrichment helper) and Plan 174-04 (the producer-side dispatch.ts wiring that will actually populate `metadata.email_copy`). This plan's own tests exercise the consumer contract directly (constructing `metadata.email_copy` by hand), so it does not need to wait for 174-04 to land — the two sides only share a simple, documented JSON shape: `metadata.email_copy: { subject: string; body: string }`.

Purpose: make the digest email pipeline idempotent-safe for resolver-sourced (pre-escaped) content BEFORE any real call site can ever produce it, per the "before/atomically-with the first email-channel cutover" instruction.
Output: `notification-emails.ts` gains a `preEscaped` flag; `notification-email-digest.ts` gains a pure, testable `buildDigestItem()` that prefers `metadata.email_copy`.
</objective>
