<objective>
Close carry-forward (b) from Phase 172 (172-03-SUMMARY.md, "Email double-escape trap"): once Plan 174-04 wires `notify()` to resolve `channel='email'` through `resolveNotificationCopy` (BODY in html mode — already HTML-entity-escaped by `template-engine.ts`'s `escapeHtmlValue`) and stash it on the notification row for the digest worker to consume, that BODY value must NOT be piped through `lib/email/notification-emails.ts`'s own `escapeHtml()` a second time — doing so corrupts entities (`&amp;` → `&amp;amp;`).

This plan builds the CONSUMER side of that fix — independent of, and parallel to, Plan 174-01 (the producer-side default-enrichment helper) and Plan 174-04 (the producer-side dispatch.ts wiring that will actually populate `metadata.email_copy`). This plan's own tests exercise the consumer contract directly (constructing `metadata.email_copy` by hand), so it does not need to wait for 174-04 to land — the two sides only share a simple, documented JSON shape.

**Revision note (plan-checker FLAG 3):** the original design treated `metadata.email_copy` as a UNIFORM `{ subject, body }` pair both resolved in html mode, with a single `preEscaped` flag gating BOTH fields. That was wrong: an email SUBJECT header is never an HTML-rendering context — a subject resolved in html mode would surface a literal `&amp;` in the recipient's inbox subject line. Plan 174-04's revision fixes `resolveNotificationCopy` so the title/subject ALWAYS renders in TEXT mode (only body's mode is channel-driven) — meaning `metadata.email_copy.subject` is now plain, unescaped text, exactly like `row.title` always was. Consequently `preEscaped` in THIS plan now governs BODY escaping ONLY; `item.title` is ALWAYS escaped normally by `escapeHtml()` (never bypassed) — which is also consistent with `sendNotificationDigestEmail`'s existing single-item `subject:` field, which already takes `item.title` RAW (no escaping) for the literal Resend subject header, and separately re-escapes the SAME title via `escapeHtml()` for the in-body HTML heading. Both uses now correctly assume `item.title` is always plain text.

Purpose: make the digest email pipeline correct and idempotent-safe for resolver-sourced (mixed-mode) content BEFORE any real call site can ever produce it, per the "before/atomically-with the first email-channel cutover" instruction.
Output: `notification-emails.ts` gains a `preEscaped` flag scoped to `body` only; `notification-email-digest.ts` gains a pure, testable `buildDigestItem()` that prefers `metadata.email_copy`.
</objective>
