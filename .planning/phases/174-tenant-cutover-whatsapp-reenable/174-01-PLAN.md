<objective>
Close carry-forward (a) from Phase 172 (172-03-SUMMARY.md, "Sparse-ctx regression risk"): `lib/notifications/copy.ts`'s `buildNotificationCopy` fills in coherent per-field defaults for a sparse `CopyContext` (e.g. `ctx.clientName ?? 'A client'`), but the `{{var}}` interpolator in `template-engine.ts` does NOT — a missing ctx field renders as `''`. Today this is inert (zero call sites pass `copyContext`), but the `notification_templates` table's 17 seed rows are ALREADY `is_active=true` (migration `20260721000001`), so the instant this phase's call-site sweep (174-05/06/07) flips `copyContext` on for a genuinely-sparse call site (e.g. `payment.received`'s `amountUSD`/`projectName`, which CAN be `undefined` today — see `lib/billing/connect-webhook.ts`), the resolver would find the active DB row and render literal blanks where `copy.ts` today renders "A payment received for a project."

This plan ships the ONE shared helper — `buildFullCopyContext` — that Plan 174-04 (dispatch.ts wiring) applies centrally to every `copyContext` before resolution, so the sweep plans (174-05/06/07) can stay purely mechanical: pass the SAME raw ctx they already build for `buildNotificationCopy`, unchanged.

**Revision note (plan-checker BLOCKER 1):** the original design of this plan proved idempotence by round-tripping `buildFullCopyContext`'s output back through `buildNotificationCopy` and comparing to `buildNotificationCopy(eventType, {})`. That oracle is TAUTOLOGICAL — `buildNotificationCopy` re-applies its OWN `??` defaults on every call regardless of what `buildFullCopyContext` produced, so the comparison passes even if `buildFullCopyContext` is a complete no-op that returns `ctx` unchanged. It can never catch a missing/omitted field, which is EXACTLY carry-forward (a)'s failure mode (a missing field renders as `''` via `renderTemplate`, not via `buildNotificationCopy`). This revision replaces that oracle with the RESOLVER-PATH proof: render `EVENT_TEMPLATE_SEED[eventType]` (172-02's DB-seed content, already proven byte-equivalent to `copy.ts` in 172-03) through `renderTemplate` using `buildFullCopyContext`'s output as the template vars — the exact path a real DB template row exercises in production. This genuinely fails if a field is omitted, because `renderTemplate` (unlike `buildNotificationCopy`) has no fallback defaults of its own.

Purpose: guarantee a sparse ctx never regresses to a blank tenant-facing notification once DB templates go live — proven via the actual rendering path, not a self-referential comparison.
Output: `lib/notifications/copy-context.ts` exporting `buildFullCopyContext`, proven exhaustive and resolver-path-correct against the seed content.

import type { EventType } from './event-types'
import type { CopyContext } from './copy'

export function buildFullCopyContext(eventType: EventType, ctx: CopyContext = {}): CopyContext {
  switch (eventType) {
    case 'estimate.viewed':
      return { ...ctx, clientName: ctx.clientName ?? 'A client', estimateNumber: ctx.estimateNumber ?? '' }
    // ...one case per EventType, grouped with fallthrough (`case 'estimate.accepted': case 'estimate.declined':`)
    // where two events share IDENTICAL default expressions...
  }
}

**The corrected (non-tautological) test oracle** — reuses 172-03's own proven pattern (`template-resolver.test.ts`'s "seed byte-equivalence" test, which already imports `EVENT_TEMPLATE_SEED` + `renderTemplate` + `TemplateVars` for exactly this purpose against a FULLY-populated fixture ctx). This plan's test does the SAME render, but against `buildFullCopyContext(eventType, {})` (an EMPTY input ctx) instead of a hand-written fully-populated fixture — proving the enrichment function itself, not a fixture the test author already filled in by hand:

```typescript
import type { EventType } from '@/lib/notifications/event-types'
import { EVENT_TEMPLATE_SEED } from '@/lib/notifications/template-seed'
import { renderTemplate, type TemplateVars } from '@/lib/notifications/template-engine'
import { buildNotificationCopy } from '@/lib/notifications/copy'
import { buildFullCopyContext } from '@/lib/notifications/copy-context'

const ALL_EVENT_TYPES: EventType[] = [ /* all 17, literal array */ ]

for (const eventType of ALL_EVENT_TYPES) {
  const fullCtx = buildFullCopyContext(eventType, {})

  const resolverBody = renderTemplate(EVENT_TEMPLATE_SEED[eventType].body, fullCtx as unknown as TemplateVars, 'text')
  expect(resolverBody, `body mismatch for "${eventType}"`).toBe(buildNotificationCopy(eventType, {}).body)

  const resolverTitle = renderTemplate(EVENT_TEMPLATE_SEED[eventType].title, fullCtx as unknown as TemplateVars, 'text')
  expect(resolverTitle, `title mismatch for "${eventType}"`).toBe(buildNotificationCopy(eventType, {}).title)
}
```

Why this genuinely fails on an omission (unlike the old oracle): if `buildFullCopyContext('payment.received', {})` forgot to fill `projectName`, `renderTemplate` would substitute `{{projectName}}` with `''` (its own missing-var behavior — see `template-engine.ts`'s `renderTemplate`, `raw === undefined → return ''`), producing `"A payment received for ."` — which does NOT equal `buildNotificationCopy('payment.received', {}).body` (`"A payment received for a project."`). The OLD oracle (`buildNotificationCopy(eventType, buildFullCopyContext(...))`) would have silently re-applied `?? 'a project'` inside `buildNotificationCopy` itself and passed regardless.
