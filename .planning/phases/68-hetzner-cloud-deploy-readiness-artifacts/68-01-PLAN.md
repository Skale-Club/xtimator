    Create `Dockerfile` at repo root with three stages: `deps`, `builder`, `runner`. Use `node:22-alpine` as the base for all three stages (single base = layer reuse + smallest possible image).

    Full Dockerfile content:

    ```dockerfile
    # syntax=docker/dockerfile:1.7

    # =========================================================================
    # Stage 1: deps — install production + build dependencies
    # =========================================================================
    FROM node:22-alpine AS deps

    # libc6-compat shim — some npm packages (sharp, pg, native modules) link
    # against glibc symbols. alpine ships musl; this shim covers the gap.
    RUN apk add --no-cache libc6-compat

    WORKDIR /app

    # Copy lockfile + manifest only — maximizes Docker layer cache hits when
    # only source code changes.
    COPY package.json package-lock.json* ./

    # npm ci is deterministic + faster than npm install in CI/Docker contexts.
    # --ignore-scripts skips the postinstall hooks for sharp + unrs-resolver
    # (matches the "ignoreScripts" array in package.json — same packages).
    RUN npm ci --ignore-scripts

    # =========================================================================
    # Stage 2: builder — compile Next.js to standalone output
    # =========================================================================
    FROM node:22-alpine AS builder

    WORKDIR /app

    # Copy node_modules from deps stage + the full source.
    # The full COPY happens here, AFTER deps is cached.
    COPY --from=deps /app/node_modules ./node_modules
    COPY . .

    # Disable Next telemetry at build time (no outbound calls during build).
    ENV NEXT_TELEMETRY_DISABLED=1

    # Build. Requires output: 'standalone' in next.config.ts to produce
    # .next/standalone/server.js — verified by Task 1.
    RUN npm run build

    # =========================================================================
    # Stage 3: runner — minimal runtime image
    # =========================================================================
    FROM node:22-alpine AS runner

    WORKDIR /app

    ENV NODE_ENV=production
    ENV NEXT_TELEMETRY_DISABLED=1
    ENV PORT=3000
    ENV HOSTNAME=0.0.0.0

    # Create unprivileged user — runs as uid/gid 1001:1001 (HETZNER-01 non-root).
    RUN addgroup --system --gid 1001 nodejs \
     && adduser --system --uid 1001 nextjs

    # Copy public assets verbatim (NOT in standalone output).
    COPY --from=builder --chown=nextjs:nodejs /app/public ./public

    # Copy standalone server + the static directory.
    # The standalone output already contains a minimal node_modules with
    # only the packages each route actually traces — the full node_modules
    # from deps stage is intentionally NOT copied.
    COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
    COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

    USER nextjs

    EXPOSE 3000

    # The standalone server entry — DO NOT use `npm start`, which requires
    # node_modules + `next` binary that aren't present in this stage.
    CMD ["node", "server.js"]
    ```

    Key choices and why:
    - **Three stages, single base image** (`node:22-alpine`): Docker reuses the alpine layer across all three stages. Final runtime image only contains stage 3's content (~150-300 MB target).
    - **`apk add libc6-compat`**: needed by sharp (image processing) and pg (Postgres native bindings) — both transitive deps. Without it, runtime crashes on first image transform or DB query with `Error loading shared library`.
    - **`npm ci --ignore-scripts`**: matches `package.json`'s `ignoreScripts: ["sharp", "unrs-resolver"]` field. The postinstall scripts for sharp/unrs would attempt to download platform-specific binaries during deps install; the alpine image doesn't always have the right glibc layer. Skipping is safe because Next's build step will install the right binaries via traced output, and at runtime the standalone bundle uses the wasm fallbacks.
    - **`USER nextjs`** (uid 1001): satisfies HETZNER-01 "runs as non-root user". Required for security; some Hetzner-style VPS setups also drop root privileges in their seccomp profiles.
    - **`HOSTNAME=0.0.0.0`**: Next's standalone server defaults to `localhost` which means it only binds to the loopback interface inside the container. With `0.0.0.0`, the container's `:3000` is reachable from the host via `-p 3000:3000`. This is the single most common "container starts but isn't reachable" footgun.
    - **`CMD ["node", "server.js"]`** (NOT `npm start`): exec form (no shell wrapper) so signals (SIGTERM from `docker stop`) reach the Node process directly for graceful shutdown.

    Image size budget: target ~150-300 MB. Hard cap per HETZNER-01: 500 MB. If the actual build exceeds 500 MB, Plan 03 must investigate (likely culprits: forgot `--ignore-scripts`, missed `.dockerignore` entries, or a transitive dep ballooned).

    Key compose choices:
    - **`restart: unless-stopped`** on both services: HETZNER-03 explicit requirement. Auto-restart on crash; survives `reboot`; stops only on `docker compose down`.
    - **`expose: "3000"` (NOT `ports`) on xtimator**: the app is reachable only via the internal `web` network — never directly bound to host. Caddy is the only public surface.
    - **`caddy_data` named volume**: Let's Encrypt certs + ACME state live here. If this volume is wiped, Caddy re-issues but consumes Let's Encrypt rate limits (5/week/domain). Plan 02 runbook covers backing this up.
    - **`depends_on.xtimator.condition: service_healthy`**: Caddy waits for the app to pass its health check before accepting traffic — prevents the "502 during startup" window.
    - **`DOMAIN` is required, no default**: `${DOMAIN:?...}` syntax fails the `compose up` if DOMAIN isn't set. Better than starting Caddy with a nonsense domain and getting a Let's Encrypt rate-limit ban.
    - **`GIT_SHA` falls back to 'unknown'**: not strictly required for the app to boot; `/api/health` (Plan 02) reports it but doesn't crash if missing.

    **3B — Create `Caddyfile` at repo root:**

    ```caddyfile
    # Caddyfile — Hetzner Cloud VPS production
    # Caddy v2 with automatic HTTPS via Let's Encrypt.
    #
    # The {$DOMAIN} placeholder is substituted at startup from the env var
    # set in docker-compose.yml. Set DOMAIN=xtimator.com in /opt/xtimator/.env.

    {
        # Caddy global options.
        # email: contact for Let's Encrypt expiration warnings. Override
        # via /opt/xtimator/.env if desired.
        email {$ACME_EMAIL:admin@{$DOMAIN}}

        # Disable the admin API on production — reduces attack surface.
        admin off
    }

    {$DOMAIN} {
        # Reverse proxy to the Next.js standalone server inside the
        # `xtimator` container. Docker DNS resolves `xtimator` to the
        # service IP on the `web` bridge network.
        reverse_proxy xtimator:3000 {
            # Pass real client IP + protocol to Next so request.headers
            # see the original values, not the proxy's.
            header_up X-Real-IP {remote_host}
            header_up X-Forwarded-For {remote_host}
            header_up X-Forwarded-Proto {scheme}
        }

        # Compress responses for smaller transfers.
        encode zstd gzip

        # Security headers — match the existing Next defaults plus a few
        # Caddy-level additions.
        header {
            # Strict-Transport-Security: 1 year, all subdomains, preload-eligible
            Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
            X-Content-Type-Options "nosniff"
            X-Frame-Options "DENY"
            Referrer-Policy "strict-origin-when-cross-origin"
            # Remove the default "Server: Caddy" reveal
            -Server
        }

        # Logs to Docker stdout so `docker compose logs caddy` shows them.
        log {
            output stdout
            format json
        }
    }

    # HTTP -> HTTPS redirect handled implicitly by Caddy when the site
    # block declares a domain (no explicit :80 block needed).
    ```

    Key Caddy choices:
    - **No explicit `tls` directive**: Caddy auto-issues Let's Encrypt certs for any domain in a site block. This IS the "automatic HTTPS via Let's Encrypt" gate from HETZNER-03.

    - **`-Server`**: removes the `Server: Caddy` header — minor info-leak prevention.
