<objective>
Widen the `saveEstimate` server action so the editor can persist the v4.11 advanced-pricing fields, and route its math through the SHARED `computeEstimateTotals` engine so the SERVER is the single math authority (GUARD-03). This is the load-bearing half of PUI-01: the contract the Wave-2 editor UI saves into.

Today `saveEstimate` (lib/actions/estimate.ts) hand-rolls its own subtotal/discount/tax math (L88-115) and only reads/persists `description/quantity/unit/unit_price` per item — it silently drops `taxable`, `tax_category`, line `discount`, `cost`, `markup_pct`, and the estimate-level `deposit_type`/`deposit_value`. This plan:
1. Extends `SaveItemInput` + `SaveEstimateInput` to carry the new optional fields.
2. Replaces the inline math block with a call to `computeEstimateTotals` (the pure function already used by `lib/services/generate-estimate.ts`), mapping the editor's `'percentage'|'fixed'` discount_type to the engine's `'percent'|'amount'`.
3. Persists the recomputed `tax_amount`, `discount_amount`, `total`, `deposit`, `balance_due` on the estimate row and the new per-item columns on each item.

Purpose: the editor never decides the persisted numbers — it sends inputs, the server recomputes (never-trust-client). Retrocompat: every new field is OPTIONAL with a no-op default (taxable→true, discount→0, deposit_type→'none'), so an unedited estimate saves byte-identical totals.
Output: a widened, server-authoritative `saveEstimate` + a test locking GUARD-03 + retrocompat.
</objective>

The pure engine contract the action must call (from lib/estimate/compute-totals.ts):

```typescript
interface ComputeTotalsItem { quantity: number; unit_price: number; discount?: number | null; cost?: number | null; markup_pct?: number | null; taxable?: boolean | null; tax_category?: 'labor'|'materials'|'other'|null }
interface ComputeTotalsOptions { taxRate: number; taxConfig?: TaxConfig | null; discountType?: 'amount'|'percent'|'none'|null; discountValue?: number | null; depositType?: 'none'|'percent'|'amount'|null; depositValue?: number | null }
function computeEstimateTotals(sections, options): { sections; subtotal; discountAmount; taxAmount; grandTotal; deposit; balanceDue }
```

Editor↔engine discount_type mapping (LOCKED): editor/DB `'percentage'` → engine `'percent'`; editor/DB `'fixed'` → engine `'amount'`; `null` → `'none'`. The editor's percentage `discount_value` is already a whole number (e.g. `10`), matching the engine.

The existing `tax_rate` on the estimate is a DECIMAL fraction (e.g. 0.0875) — pass it as the engine's `taxRate` directly (the engine multiplies by it). Leave `taxConfig` undefined here (the editor doesn't surface per-category config — flat retrocompat branch), matching today's flat behavior.
