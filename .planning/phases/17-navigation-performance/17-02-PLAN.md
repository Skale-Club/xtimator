# Phase 17 — Plan 02: Cache Company + Auth Claims in Layout

**Goal:** The app layout (`app/(app)/layout.tsx`) currently makes two sequential Supabase calls on every navigation (even when the user's company data hasn't changed). Wrap these in React `cache()` for per-request deduplication and `unstable_cache` for a 60-second cross-request TTL, eliminating 200–400ms of latency on warm navigations.

**Depends on:** Plan 01 (loading.tsx files exist)
**Estimated complexity:** Medium (new lib file, layout refactor, query consolidation across 5 pages)

---

## Context

### The Problem

Every time a user navigates to any authenticated page, the following happens on the server:

1. `layout.tsx` → `await supabase.auth.getClaims()` (~50ms)
2. `layout.tsx` → `await supabase.from('companies').select(...)` (~150-300ms)
3. `page.tsx` → `await supabase.auth.getClaims()` (~50ms) ← DUPLICATE
4. `page.tsx` → `await supabase.from('companies').select('id')...` (~150-300ms) ← DUPLICATE
5. `page.tsx` → page-specific queries (parallelized in most pages)

Steps 3 and 4 are redundant. They return the same data as steps 1 and 2.

### The Fix

**React `cache()`** (from `react`) deduplicates calls within a single render tree per request. When both `layout.tsx` and `page.tsx` call `getAuthClaims()`, only ONE Supabase call fires. React's cache is cleared automatically between requests.

**`unstable_cache`** (from `next/cache`) adds a 60-second cross-request persistent cache. On navigation #2 through #N within a session, the company query resolves from in-memory cache (~0ms) instead of hitting Supabase.

### Architecture

Create `lib/queries/auth.ts` — a new server-only module with cached versions of the two calls:

```
lib/queries/auth.ts          ← NEW: getAuthClaims() + getCachedCompany()
app/(app)/layout.tsx         ← MODIFY: use getAuthClaims() + getCachedCompany()
app/(app)/dashboard/page.tsx ← MODIFY: use getAuthClaims() + getCachedCompany()
app/(app)/clients/page.tsx   ← MODIFY: use getAuthClaims() + getCachedCompany()
app/(app)/projects/new/page.tsx ← MODIFY: use getAuthClaims() + getCachedCompany()
app/(app)/settings/page.tsx  ← MODIFY: use getAuthClaims() + getCachedCompany()
```

**pages NOT modified in this plan:**
- `app/(app)/projects/[id]/page.tsx` — already fetches company differently (via `project.company_id`)
- `app/(app)/clients/[id]/page.tsx` — reads company implicitly through RLS; does not query companies table directly

## Wave 1 — Create lib/queries/auth.ts

### Task 1-1: Create `lib/queries/auth.ts`

**File:** `lib/queries/auth.ts`

**Purpose:** Centralised, cached auth + company data fetching for the authenticated app shell. Pattern mirrors `lib/auth/admin-context.ts` which already uses React `cache()` in this codebase.

```ts
import 'server-only'
import { cache } from 'react'
import { unstable_cache } from 'next/cache'
import { createClient } from '@/lib/supabase/server'

// ─── Types ───────────────────────────────────────────────────────────────────

export interface AppCompany {
  id: string
  name: string
  logo_url: string | null
  owner_name: string | null
  theme_preference: string | null
}

// ─── Per-request deduplication ───────────────────────────────────────────────

/**
 * Returns the JWT claims for the current request.
 * Wrapped in React cache() so layout + page calling this within the same
 * render tree share a single Supabase call.
 */
export const getAuthClaims = cache(async () => {
  const supabase = await createClient()
  const { data: claimsData } = await supabase.auth.getClaims()
  return claimsData?.claims ?? null
})

// ─── Cross-request caching (60s TTL) ─────────────────────────────────────────

/**
 * Returns company data for a given userId.
 * Cached for 60 seconds across requests — company data changes only when the
 * user saves Settings. The 'company' tag is used for on-demand invalidation
 * from the settings save server action.
 *
 * Returns only the fields needed by the layout shell:
 * id, name, logo_url, owner_name, theme_preference
 */
export const getCachedCompany = unstable_cache(
  async (userId: string): Promise<AppCompany | null> => {
    const supabase = await createClient()
    const { data } = await supabase
      .from('companies')
      .select('id, name, logo_url, owner_name, theme_preference')
      .eq('user_id', userId)
      .single()
    return (data as AppCompany) ?? null
  },
  ['company-for-user'],
  { revalidate: 60, tags: ['company'] }
)
```

### Task 2-5: Update `app/(app)/settings/page.tsx`

**File:** `app/(app)/settings/page.tsx` (read before modifying)

**Change:** Settings page calls `getCompanySettings(supabase, claims.sub)` which fetches ALL company fields. This query cannot use `getCachedCompany` directly (different field set). Use `getAuthClaims()` for the claims dedup, keep the existing `getCompanySettings` call unchanged (it fetches the full record needed for the form).

```ts
// Replace only the getClaims part:
import { getAuthClaims } from '@/lib/queries/auth'
// ...
const claims = await getAuthClaims()
if (!claims) { redirect('/login') }

const supabase = await createClient()
const company = await getCompanySettings(supabase, claims.sub as string)
if (!company) { redirect('/onboarding') }
```

**Note:** `getCompanySettings` selects all fields — this is correct for the settings form and should NOT be replaced with `getCachedCompany`. The layout's cached call and this call will both fire (different queries, different data), but the claims call is deduplicated.

**Cache invalidation:** After the user saves settings, the settings save server action should call `revalidateTag('company')` to invalidate the `getCachedCompany` cache so the layout reflects updated company name/logo immediately.

Add to `lib/actions/company.ts` (in whichever server action saves company settings — look for the existing save action):
```ts
import { revalidateTag } from 'next/cache'
// ... after successful save:
revalidateTag('company')
```
