<objective>
Close audit findings B1/B2/B3/B7 (SAVE-01/02/06) + the server half of B8 (SAVE-07). Today saveEstimate (lib/actions/estimate.ts) is a non-transactional sequence: the header UPDATE (with totals + updated_at) commits FIRST, then per-section/per-item writes, then orphan deletes, then project total — all separate awaited PostgREST calls. A failure after the header leaves header totals ≠ items; and because the failed call still committed the new updated_at, the NEXT save from the same session fails the `.eq('updated_at', expectedUpdatedAt)` check and returns a FALSE "changed elsewhere" conflict whose only exit discards the user's edits (session poisoning). There is also no server-side is_current guard and no updated_at trigger, so a stale tab can silently write to a superseded version.

REQUIRED READING: .planning/audits/v4.19-ESTIMATE-DEEP-AUDIT.md § B. The current write sequence is lib/actions/estimate.ts:125-416 (post-164-02): pre-UPDATE lock SELECT :138-154, header UPDATE + compare-and-set :170-213, section/item upserts :218-355, orphan section deletes :357-374, project total :376-384, estimate_updated activity :386-414. 164-02 already added the lock guard + activity row + savePresentationSettings — the RPC must PRESERVE all of that (fold the lock/current guard into the transaction; keep the activity insert + revalidatePath in the action AFTER the RPC).

DESIGN (locked in REQUIREMENTS.md): one `SECURITY INVOKER` plpgsql function — RLS still applies (tenant isolation preserved; the caller is the authed user, company_id stamped on inserts as today). Money math STAYS in TypeScript (computeEstimateTotals runs in the action, authoritative — GUARD-03); the RPC receives already-computed header + per-item unit_price/total + per-section subtotal and only PERSISTS them atomically. Do NOT port the math to plpgsql (that forks GUARD-03).

```
save_estimate_atomic(
  p_estimate_id uuid,
  p_company_id uuid,
  p_expected_updated_at timestamptz,   -- NULL allowed (non-editor callers); when present, compare-and-set
  p_header jsonb,                       -- {summary, notes, timeline, payment_terms, warranty_terms,
                                        --  discount_type, discount_value, discount_amount, estimate_date,
                                        --  estimate_number, tax_rate, tax_amount, subtotal, total,
                                        --  deposit_type, deposit_value, balance_due, presentation_settings}
  p_sections jsonb                      -- ordered [{id, title, sort_order, subtotal,
                                        --   items:[{id, description, quantity, unit, unit_price, total,
                                        --   sort_order, price_source, taxable, tax_category, discount, cost, markup_pct}]}]
                                        --   NOTE: price_source is ALREADY RESOLVED by the action (isManuallyEdited ? null
                                        --   : price_source) BEFORE building the payload — the RPC receives the final value
                                        --   and does NOT see isManuallyEdited (Opus nit #5).
) RETURNS jsonb   -- {updated_at, project_total, project_id, previous_total, id_map: {"temp-x":"<uuid>", ...}}
                  -- project_id + previous_total are RETURNED (Opus BLOCKER #1) because the action's
                  -- post-RPC estimate_updated activity insert (estimate_activity.project_id is NOT NULL)
                  -- and revalidatePath both need them; the pre-UPDATE SELECT that supplied them is gone.
```
Transaction body (plpgsql = one implicit txn; RAISE rolls back everything):
1. SELECT sent_at, client_response, is_current, project_id, total, updated_at INTO locals FROM estimates WHERE id = p_estimate_id FOR UPDATE. (Row lock serializes concurrent saves; FOR UPDATE re-fetches the latest committed row via EvalPlanQual, so the updated_at read in step 4 is the locked snapshot — Opus warning #2. MUST include updated_at in this SELECT.) Not found → RAISE 'estimate_not_found'.
2. EXISTS(estimate_signatures WHERE estimate_id = p_estimate_id) OR sent_at IS NOT NULL OR client_response IS NOT NULL → RAISE 'estimate_locked'.
3. is_current IS NOT TRUE → RAISE 'estimate_not_current'.
4. p_expected_updated_at IS NOT NULL AND updated_at <> p_expected_updated_at → RAISE 'estimate_conflict'.
5. UPDATE estimates SET <header fields> WHERE id = p_estimate_id. (updated_at set by the trigger, NOT here.)
6. For each section in p_sections (in array order): temp- id → INSERT (company_id = p_company_id), capture new uuid into id_map; real id → UPDATE. For each item likewise; collect incoming item ids per section into a uuid[] and DELETE estimate_items WHERE section_id = <section> AND id <> ALL(v_incoming_items) — use `<> ALL(array)`, NOT `NOT IN (...)` (Opus nit #6: an empty/NULL-containing IN list silently suppresses the delete; the current JS deletes-all when a kept section is emptied, and `<> ALL('{}')` reproduces that correctly). After all sections: DELETE estimate_sections WHERE estimate_id = p_estimate_id AND id <> ALL(v_incoming_sections) (items cascade).
7. UPDATE projects SET total = (p_header->>'total')::numeric WHERE id = v_project_id.
8. RETURN jsonb_build_object('updated_at', <trigger-set updated_at>, 'project_total', ..., 'project_id', v_project_id, 'previous_total', v_previous_total, 'id_map', ...).
9. GRANT: end the migration with `GRANT EXECUTE ON FUNCTION public.save_estimate_atomic(...) TO authenticated;` and do NOT add the REVOKE the credit-ledger template ends with — that template is SECURITY DEFINER; this is SECURITY INVOKER called directly by the authed user via supabase.rpc, so a REVOKE would make it dead (Opus warning #3).

Error mapping in the action (map the RPC's SQLERRM / a custom SQLSTATE to the existing return contracts):
- 'estimate_locked' → { error: 'estimate_locked' }  (same as 164-02)
- 'estimate_conflict' → { error: '<the existing "changed elsewhere" copy>', conflict: true }
- 'estimate_not_current' → { error: 'estimate_not_current' } (new — 165-02 handles it like a lock)
- 'estimate_not_found' / anything else → { error: 'Failed to save estimate' }
Use DISTINCT SQLSTATEs matched on `error.code` (not just message) so the locked/conflict/not_current contracts are reliable through PostgREST/supabase-js (Opus warning #4 — no existing repo caller maps distinct plpgsql RAISE signals to typed errors; this is new ground). Assign e.g. P0001=locked, P0002=conflict, P0003=not_current, P0004=not_found; the action switches on `error.code`. Because a mocked-rpc unit test cannot prove the real RAISE→error.code surfacing, ALSO add ONE integration test against a real/local DB (or a documented manual-verify note if no local PG is available in this env) that exercises each RAISE path end-to-end.

updated_at trigger:
```
CREATE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END $$;
CREATE TRIGGER trg_estimates_set_updated_at BEFORE UPDATE ON estimates FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```
Note the action must STOP setting updated_at explicitly (the trigger owns it); the header UPDATE inside the RPC omits updated_at. The compare-and-set reads the OLD updated_at (step 4) before the trigger fires on step 5.
