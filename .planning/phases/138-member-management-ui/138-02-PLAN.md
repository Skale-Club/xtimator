<objective>
SEAT-05 (UI half): the mobile-safe `Settings → Team` surface. A server page (`app/(app)/settings/(tabs)/team/page.tsx`) resolves the active company + the viewer's role, calls `listCompanyRoster` (Plan 01), and renders `TeamSection` with a `canManage` flag (owner|admin). `TeamSection` lists members (name/email/role) + pending invites (email/role), and — when `canManage` — exposes an Invite dialog (email + role → `inviteMember`), per-member change-role + remove controls, and per-invite revoke. A plain `member` sees a read-only roster. A Team entry is added to the settings nav.

SECURITY: the page resolves `canManage` only to decide what to RENDER. Every mutation still calls the Plan-01 / SEAT-03 server actions, each of which re-checks `requireCompanyManager` — the UI gate is NOT the boundary. (Assert-by-design: no client-side role is trusted for authority; the server actions reject a non-manager regardless of what the UI shows.)

i18n: all visible strings go through `useTranslation()` `t('English source')` in the client component (and `<T>` in the server page) — this is the project's runtime-translation path; en/pt/es are produced at runtime, there are NO locale JSON files to author. Match the existing settings components' idiom.

SCOPE FENCE: roster + management controls ONLY. NO seat-cost / per-seat-price / projected-monthly-cost number anywhere on this surface (that is Phase 140, which reads billing_config). NO billing imports.

Purpose: an owner/admin manages the team from a phone; a member sees who's on the team.
Output: a wired, mobile-safe Team settings tab consuming the Plan-01 query + the SEAT-03/SEAT-05 actions.
</objective>
