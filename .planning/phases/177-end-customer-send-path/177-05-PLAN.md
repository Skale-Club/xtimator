```ts
export type CustomerEventType = 'estimate.sent'
// Extensible — Phase 178 / future work adds cases here as new end-customer
// event types are needed. Exactly one case exists today: the legacy
// send-sms route (177-07) is the first and only real caller.

export interface CustomerCopyContext {
  businessName?: string
  clientName?: string
  shareUrl?: string
}

export interface CustomerCopy {
  subject?: string // email only
  body: string
}

export function buildCustomerCopy(
  eventType: CustomerEventType,
  channel: 'email' | 'sms',
  ctx: CustomerCopyContext,
): CustomerCopy
```
For `'estimate.sent'`: sms body is plain text (`"${business} sent you an estimate. Review and approve it here: ${link}"`); email returns `{ subject, body }` where `body` is simple inline HTML (a couple of `<p>` tags — this is a fallback default, not a polished template; polish is a future admin-editor concern). Use a `switch` with a `default: { const _exhaustive: never = eventType; ... }` exhaustiveness guard, mirroring `copy.ts`'s style, so a future added `CustomerEventType` case that's forgotten here is a compile error.

New `lib/notifications/customer-template-resolver.ts`:
```ts
export async function resolveCustomerCopy(
  eventType: CustomerEventType,
  channel: 'email' | 'sms',
  ctx: CustomerCopyContext,
): Promise<CustomerCopy>
```
Mirrors `lib/notifications/template-resolver.ts`'s `resolveNotificationCopy` almost line-for-line: lazy-import `createServiceClient`, no client -> fallback, query `notification_templates` with `.eq('scope','customer').eq('event_type', eventType).eq('channel', channel).eq('is_active', true).select('subject, body').maybeSingle()`, no row or empty body -> `buildCustomerCopy` fallback, render with `renderTemplate(row.body, ctx as unknown as TemplateVars, channel === 'email' ? 'html' : 'text')`, empty-after-render -> fallback, ANY throw -> caught + `console.warn` + fallback. No `title` field (customer channels are email/sms only, no in_app — unlike the tenant resolver).
