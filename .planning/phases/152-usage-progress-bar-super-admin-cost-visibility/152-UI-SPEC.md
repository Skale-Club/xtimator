## Typography

Reusing the project's EXISTING type scale (`app/globals.css` lines 354-360) — no new sizes introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|

## Color

The project already has a **semantic status palette** (`--success`/`--warning`/`--danger`, defined in `app/globals.css` lines 161-173, 197-209, dark-mode and admin-dark-scoped variants included). **Reuse these tokens for the color-escalation bands — do not invent new hex values.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `hsl(var(--background))` / `hsl(var(--card))` | Page background, card surfaces (existing) |
| Secondary (30%) | `hsl(var(--muted))` / `--glass-bg` (Card `variant="glass"`) | Card chrome, the progress bar's unfilled track (`bg-primary/20` today — see decision below) |
| Accent (10%) | `hsl(var(--primary))` (green/amber/red escalation below overrides this for the bar itself) | The progress bar's FILLED indicator only, plus the numeric percentage label. Reserved for: (1) the progress bar indicator fill, (2) the percentage text label directly above/beside the bar. Nothing else on these two surfaces gets accent treatment. |
| Destructive | `hsl(var(--destructive))` | Not used this phase (no delete/destroy actions) — see Copywriting Contract, "Destructive confirmation: none" |

### Color-escalation bands (Claude's Discretion per CONTEXT.md — decided here, not left open)

Three bands, using the EXISTING semantic tokens so dark mode / admin-dark-scope automatically resolve correctly:

| Band | `percentUsed` range | Token | Rationale |
|------|---------------------|-------|-----------|
| Healthy | 0–69% | `--success` (green) | Majority of the cycle — no attention needed |
| Getting low | 70–89% | `--warning` (amber) | Matches `credit-balance-card.tsx`'s existing amber low-balance treatment (`amber-500/20` border, `amber-600`/`amber-400` text) — this phase's bar amber band is the percentage-based analog of that same signal |
| Critical | 90–100% | `--danger` (red) | Matches CONTEXT.md's ">90% red" default suggestion |

Implementation: the `Progress` primitive's `Indicator` currently hardcodes `bg-primary` (see `components/ui/progress.tsx` line 24). The color-escalation wrapper component (see Component Inventory below) must override the indicator color via a `className`/`indicatorClassName` prop or inline style keyed off `percentUsed`, mapping to `bg-[hsl(var(--success))]` / `bg-[hsl(var(--warning))]` / `bg-[hsl(var(--danger))]`. The track (unfilled portion) stays `bg-primary/20` as today — only the filled indicator escalates color.

No second semantic/destructive color is needed this phase (no destructive actions are introduced).

## Enforcement Mechanism (structural, not just convention — per CONTEXT.md)

This is not a generic template field, but is load-bearing for the checker and executor and is recorded here per CONTEXT.md's explicit instruction to give CREDITUI-04 "a hard enforcement mechanism instead of just a code-review convention":

1. **Prop-shape enforcement:** `UsageProgressBar`, the modified `CreditBalanceCard`, and the modified `CreditChip` accept `percentUsed: number` only — never `balance`, `cycleGrant`, `real_cost_usd`, or `markup`. The raw balance is computed to a percentage server-side (in the page/layout, using `lib/billing/usage-percent.ts`) before any client component receives it.
2. **Static grep test (new):** add a test (e.g. `tests/unit/billing/tenant-cost-neutrality.test.ts`, mirroring the existing `SAFE_EVENT_COLUMNS` convention referenced in CONTEXT.md and the pattern in `tests/unit/agent-tools/neutrality.test.ts`) asserting that `lib/queries/credits.ts` and every file under `components/billing/` contain none of the literal tokens `real_cost_usd`, `markup`, `balance_after`. This is a planner/executor task, not a design-contract field, but the UI-SPEC records the requirement so the plan doesn't drop it.
3. **File boundary:** the new admin-only cost query (`lib/queries/admin-company-cost.ts`) lives outside `lib/queries/credits.ts` specifically so the grep test in (2) can pass trivially for the tenant-facing file while the admin file is free to select the forbidden columns.
