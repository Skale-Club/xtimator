## B1 — the hero background VIDEO is deliberately NOT repointed

`app/admin/landing/actions.ts:190` writes `heroBackgroundVideoUrl`
(`hero-bg-videos/{ts}-{base}.{ext}`, schema allows up to 20 MB mp4/webm with no
transcoding). It is rendered as a bare `<video autoPlay muted loop playsInline>` at
`components/landing/hero-section.tsx:68`.

The Phase 187 proxy is documented whole-object pass-through with **no Range/206 and
no `Accept-Ranges`** (see 187-03-SUMMARY "Known limitation"). Safari — desktop and
iOS — refuses to play a `<video>` whose origin does not honour byte-range requests.
Today that URL points at Supabase's CDN, which does. Repointing it would trade a
working video for a broken one on every Apple device.

**Current production state: no hero background video is set** (`landing_content`
holds no video key), so this is a LATENT hazard, not an active break — nothing live
is being moved or preserved here. It is excluded so that the first admin who uploads
one does not silently ship a Safari-broken landing page.

**Named prerequisite before this is ever revisited: the asset proxy must support
Range/206 + `Accept-Ranges`.** Until that lands, `hero-bg-videos/` stays on Supabase.
Consequence to state honestly in the docs (Plan 04): video is the one asset class
that keeps using Supabase egress and stays off the Cloudflare same-origin path.
</objective>
