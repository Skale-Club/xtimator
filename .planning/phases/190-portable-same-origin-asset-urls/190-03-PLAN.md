<objective>
Give the two server-side renderers that have NO browser origin a way to resolve a
same-origin relative asset path: read the bytes in-process and hand them over as a
`data:` URI.

Purpose: this is the first of Phase 187's two explicitly deferred exclusions
("no server-side-renderer path"). `@react-pdf/renderer` running in Node cannot fetch
`/storage/logos/x`, and `lib/brand-icon.ts`'s `fetch(url)` throws on a relative
specifier and silently degrades to the bundled logo.
Output: `lib/storage/asset-inline.ts` plus its two consumers.

**Why bytes, not an absolutized HTTP fetch.** The obvious alternative —
`fetch(getCanonicalBaseUrl() + path)` — makes the container request its own public
domain. In this deployment that leaves the container, traverses Cloudflare, and
comes back through Traefik; this repo has already been bitten by a self-request
loop in that exact path (the Flexible-SSL HTTP->HTTPS redirect loop) and by a
`getCanonicalBaseUrl()` fallback resolving to production from a dev box. Reading
the object in-process removes the origin from the problem entirely, matches the
data-URI pattern `lib/brand-icon.ts` already uses, and cannot leak a credential
because no URL is ever emitted. Emails are the one place an absolute URL is
genuinely required — that is Plan 04, and it deliberately uses a different
mechanism.

**B3 — why the content-type allowlist is not optional.** `lib/storage/asset-source.ts`
defaults `contentType` to `'application/octet-stream'` on BOTH its R2 and Supabase
branches (whenever the header/blob type is missing — routine for the extensionless
keys this codebase really has). `@react-pdf/image`'s `resolveBase64Image` throws
``Invalid base64 image: ${uri}`` — interpolating the ENTIRE data URI — and
`@react-pdf/layout` catches that into a `console.warn`. Returning a data URI with an
unrecognised content type would therefore dump a multi-megabyte base64 blob into
container logs and Sentry breadcrumbs on every PDF render, directly contradicting
this plan's own no-logging must_have. The allowlist is the fix: unknown type -> `null`
-> no logo -> no log.

**B4 — what this plan does NOT claim.** All four `logos` writers run
`convertImageToWebp`, and `@react-pdf/image` accepts only jpg/jpeg/png. WebP is
rejected on BOTH the remote-URL path and the data-URI path, so **no company logo has
ever rendered in a PDF** — a live product bug that predates this phase and is not
caused or fixed by it. Meanwhile `lib/pdf/measure-header-height.ts:111` charges
64-72pt of header height purely on `company.logo_url` being TRUTHY, so a truthy
data URI still reserves space for an image react-pdf will not draw. This plan
guarantees only that measurement and rendering see the SAME company object; it does
not and cannot guarantee a visible logo. Converting `logos` to PNG changes upload
behaviour across four writers and belongs in its own scoped change — record it as
the named follow-up below, do not smuggle it in here.
</objective>

```typescript
/** Content types this resolver will emit as a data: URI.
 *
 *  B3 — this allowlist is a LOGGING-SAFETY control, not a nicety.
 *  @react-pdf/image's resolveBase64Image throws `Invalid base64 image: ${uri}`
 *  with the WHOLE uri interpolated, and @react-pdf/layout catches it into a
 *  console.warn. Emitting a data URI for a type react-pdf cannot decode would
 *  therefore print a multi-megabyte base64 blob into container logs and Sentry
 *  breadcrumbs on every render. asset-source.ts defaults contentType to
 *  'application/octet-stream' on BOTH its branches, so that case is routine.
 *  Unknown type -> null -> no logo -> no log. */
const INLINEABLE_CONTENT_TYPES = new Set(['image/png', 'image/jpeg', 'image/webp', 'image/gif'])

/** Max bytes we will inline. Production's largest platform-brand asset is ~2.8 MB
 *  total across all objects; a single logo/favicon is tens of kB. The cap exists so
 *  a mistakenly-huge object degrades to "no logo" instead of ballooning every PDF. */
const MAX_INLINE_BYTES = 2 * 1024 * 1024

export async function resolveAssetForRenderer(
  url: string | null | undefined,
): Promise<string | null>
```

Resolution order:
1. falsy -> `null`
2. `isStorageProxyPath(url)` false: return `url` unchanged IF
   `isAcceptableAbsoluteAssetUrl(url)` (Plan 01's shared predicate — do NOT
   hand-roll a second one); otherwise `null`.
3. Same-origin path: `parseStorageProxyPath`, `decodeURIComponent` each segment,
   join with `/`, `await fetchStoredAsset(bucket, key)`.
4. `null`/throw -> `null`.
5. Normalise the content type (`split(';')[0].trim().toLowerCase()`) and check
   `INLINEABLE_CONTENT_TYPES`. Not a member -> `null`.
6. Buffer with the cap, return `` `data:${normalisedType};base64,${buf.toString('base64')}` ``.

Read the body via a shared helper that accepts both `ReadableStream` and `Blob`
(`body instanceof Blob ? Buffer.from(await body.arrayBuffer()) : <chunked reader>`).
The chunked reader is what enforces the cap without `contentLength`.

Do NOT call `getSignedUrl`, do NOT call `getCanonicalBaseUrl`, do NOT `fetch()` any
URL. Do NOT log — not even on the reject branches; a "could not inline" warn would
reintroduce exactly the leak this allowlist prevents if someone later interpolates
the uri. Do NOT import `lib/storage/server` (`fetchStoredAsset` deliberately pins to
the R2-first/Supabase-fallback reader — routing it through the provider seam would
delete the reversibility guarantee, per `lib/storage/server.ts`'s own header).
Do NOT edit `lib/storage/s3-provider.ts`.

Add a note in the file header: WebP is in the allowlist because it is what the
`logos` writers actually produce and because the bytes are legitimately an image —
but `@react-pdf/image` does not decode WebP, so a WebP logo will still not appear in
a PDF. That is the pre-existing bug recorded as a follow-up in this plan's Task 2,
not something this allowlist should paper over by excluding WebP (excluding it would
also break `app/icon.tsx`, whose `ImageResponse` renderer DOES handle WebP).
