<objective>
Build the server-only module that decides *what key a browser is allowed to write* and issues a short-lived, single-key ticket for writing it — for both the R2 and the Supabase backend.

Purpose: UPLOAD-02. Today three client components compute their own `storagePath` string and hand it straight to Supabase Storage. Whatever the browser types is what gets written; the only thing standing between one tenant and another's prefix is a Supabase `storage.objects` RLS policy that **stops existing the moment R2 is active** (see `lib/storage/server.ts`'s header — S3 has no per-user policy layer). This module makes the key a server-derived value instead of a client-supplied one, so tenant confinement survives the backend swap.

Output: `lib/storage/upload-ticket.ts` + its unit test. No route yet (Plan 02), no client changes yet (Plan 03).
</objective>

```typescript
// lib/storage/upload-ticket.ts  — SERVER ONLY

/** Buckets a browser may be ticketed to write. Deliberately just `audio` — see <action> Task 1. */
export const UPLOAD_TICKET_BUCKETS = ['audio'] as const
export type UploadTicketBucket = (typeof UPLOAD_TICKET_BUCKETS)[number]

export interface MintUploadTicketArgs {
  bucket: UploadTicketBucket
  /** Caller-supplied. Plan 02's route proves it belongs to `companyId` BEFORE calling in. */
  projectId: string
  /** Caller-supplied, allowlisted+normalized here. */
  contentType: string
  /** Auth-derived by the route. NEVER read from the request body. */
  companyId: string
  /** Supabase-mode only: the RLS-bound request client used to mint the signed upload URL. */
  supabase: SupabaseClient
  /**
   * Optional re-ticket of an already-minted key (retry path). VALIDATED against
   * companyId/projectId — never trusted, never repaired.
   */
  key?: string
}

export type UploadTicket =
  | {
      strategy: 's3-presigned-put'
      bucket: string
      key: string
      url: string
      /** Sent VERBATIM by the browser. Includes the exact Content-Type the URL was signed for. */
      headers: Record<string, string>
      expiresInSeconds: number
      /** Echo of the normalized type — the browser stamps its Blob with this. */
      contentType: string
    }
  | {
      strategy: 'supabase-signed-upload'
      bucket: string
      key: string
      token: string
      expiresInSeconds: number
      contentType: string
    }

/** `audio/webm;codecs=opus` -> `audio/webm`. Returns null for anything not allowlisted. */
export function normalizeUploadContentType(raw: string): string | null

/** Pure. `{companyId}/{projectId}/{uuid}.{ext}` — the EXISTING production shape. */
export function deriveUploadKey(args: {
  companyId: string
  projectId: string
  contentType: string
  /** Deterministic id for tests; defaults to crypto.randomUUID(). */
  id?: string
}): string

/** Pure. True only if `key` is a well-formed key this exact tenant+project owns. */
export function assertKeyInTenant(key: string, companyId: string, projectId: string): boolean

export async function mintUploadTicket(args: MintUploadTicketArgs): Promise<UploadTicket>
```

  <name>Task 2: Dual-backend ticket minting with the content type pinned</name>
  <files>lib/storage/upload-ticket.ts, tests/unit/storage/upload-ticket.test.ts</files>

  <behavior>
`mintUploadTicket(args)` dispatches on `serverStorageBackend()` (Phase 188's ONE decision — do not read `STORAGE_PROVIDER` or `S3_*` presence yourself):

**R2 mode** (`'r2'`) returns `strategy: 's3-presigned-put'` where:
- `url` is `getSignedUrl(client, new PutObjectCommand({ Bucket, Key, ContentType }), { expiresIn: 900 })` from `@aws-sdk/s3-request-presigner`
- the URL contains `X-Amz-Signature`, `X-Amz-Expires=900`, and `content-type` inside `X-Amz-SignedHeaders`
- `headers` is exactly `{ 'Content-Type': <normalized type> }` — the value the URL was signed against
- the S3 client is built from `s3ConfigFromEnv()`; when that returns `null` in `'r2'` mode, throw a named error (unreachable in practice — `serverStorageBackend()` already validated it — but never silently degrade)
- `url` contains no `X-Amz-Security-Token` and, critically, **the secret access key does not appear anywhere in the returned object** — assert this directly against the fake secret

**Supabase mode** (`'supabase'`) returns `strategy: 'supabase-signed-upload'` where:
- it calls `args.supabase.storage.from(bucket).createSignedUploadUrl(key)` (the RLS-bound request client, NOT the service-role client)
- `token` is the token from that response, and the response's own `signedUrl` is **not** forwarded — the browser rebuilds it from `NEXT_PUBLIC_SUPABASE_URL`, which it already has
- a Supabase error is rethrown with `.status`/`.statusCode` preserved via `Object.assign`, mirroring `lib/storage/supabase-provider.ts`'s upload — the browser's retry classifier depends on those properties surviving

Common to both:
- with `args.key` absent: a fresh key from `deriveUploadKey`
- with `args.key` present and `assertKeyInTenant` true: the SAME key is re-ticketed (a retry must not create a second object)
- with `args.key` present and `assertKeyInTenant` false: throws — never falls back to minting a fresh key, because silently succeeding is how a probe learns nothing happened
- a non-allowlisted `contentType` throws before any backend call
- a bucket outside `UPLOAD_TICKET_BUCKETS` throws before any backend call
  </behavior>

  <action>
Extend `lib/storage/upload-ticket.ts`.

**R2 client construction:** build a local `S3Client` from `s3ConfigFromEnv()` inside the function. Do **not** modify `lib/storage/s3-provider.ts` (proven against R2, frozen by the milestone) and do not add a presign method to the `StorageProvider` interface — presigning a *write* is a different capability from the read-side `getSignedUrl` that interface already has, and widening the interface would force every provider to implement it. Construct fresh per call, no module-level singleton — same rationale as `lib/storage/server.ts`'s header ("a cached S3 client would survive env changes between tests").

**Why 900 seconds:** the browser retry ladder is 3 attempts with 1s + 2s backoff on top of a mobile-network upload of a multi-minute recording. 900s covers the worst realistic case with room, and it is a *write* URL for one exact key with a pinned content type, so its blast radius is one object the caller was already authorized to create. Write that reasoning into the code, not just the plan.

**The content-type pin is the sharpest edge in this phase.** A presigned PUT signed for `audio/webm` fails with `SignatureDoesNotMatch` if the browser sends `audio/webm;codecs=opus` — which is exactly what `getSupportedAudioMimeType()` returns on Chrome. That is why the ticket returns both `headers` (sent verbatim) and `contentType` (used to stamp the Blob), and why normalization happens once, server-side, before signing. Put a comment on the `headers` field saying it is verbatim-or-broken.

**Supabase-mode content type, verified from the installed client:** `@supabase/storage-js`'s `uploadToSignedUrl` sends a **Blob as multipart FormData** and, in that branch, ignores the `contentType` option entirely — the stored type comes from the Blob's own `.type`. So `contentType` in the ticket is not decoration; Plan 03's browser code must re-stamp the Blob with it. Record that finding in the docblock so nobody later "cleans up" the redundant-looking field.

**Testing without credentials or network:** presigning is pure crypto — no request is made — so a fake `s3ConfigFromEnv()` env (copy `FAKE_ENV` from `tests/unit/storage/r2-verify.test.ts`) produces a real, assertable URL.
