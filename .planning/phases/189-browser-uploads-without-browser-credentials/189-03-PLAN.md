  <name>Task 1: The ticket-driven browser upload module</name>
  <files>lib/storage/upload-ticket-types.ts, lib/storage/browser-upload.ts, tests/unit/storage/browser-upload.test.ts</files>

  <behavior>
`requestUploadTicket(args, opts)`:
- `POST /api/storage/upload-ticket` with `{ bucket, projectId, contentType, key? }`, `Content-Type: application/json`
- 2xx -> parsed `UploadTicket`
- network error or 5xx -> retried up to `attempts` (default 3) on the same `baseDelayMs * 2 ** (n - 1)` ladder `uploadWithRetry` uses
- 4xx -> thrown immediately with `.status` set, no further attempts
- honours `opts.signal`; an already-aborted signal rejects with `DOMException('Aborted', 'AbortError')`

`uploadViaTicket(args, opts)`:
- mints ONE ticket, then moves bytes via `uploadWithRetry(ticketProvider(ticket), ticket.bucket, ticket.key, stampedBlob, { contentType: ticket.contentType, attempts, baseDelayMs, signal })`
- resolves `{ path: ticket.key }`
- `strategy: 's3-presigned-put'` -> `fetch(ticket.url, { method: 'PUT', headers: ticket.headers, body: blob })`. Headers sent **verbatim** — no merging, no extra `Content-Type`, no `x-upsert`; any unsigned header or altered value breaks the signature.
- `strategy: 'supabase-signed-upload'` -> `createClient().storage.from(bucket).uploadToSignedUrl(key, token, stampedBlob, { upsert: false })`
- **Blob stamping (both strategies):** when `blob.type !== ticket.contentType`, upload `new Blob([blob], { type: ticket.contentType })`. `@supabase/storage-js`'s `uploadToSignedUrl` sends a Blob as multipart FormData and ignores its `contentType` option in that branch, so the Blob's own `.type` is the only thing reaching storage — this is what makes UPLOAD-03 true on the Supabase side.
- **Error shaping is load-bearing:** every failure thrown out of the provider's `upload()` carries `.status` via `Object.assign`, exactly as `lib/storage/supabase-provider.ts` does. A raw `fetch` non-2xx carries `res.status`; a Supabase `error` carries `.status`/`.statusCode`. Without this the wrapper sees "no status", treats a terminal 403 as retryable, and burns three attempts on an upload that can never succeed.
- the provider's `download` / `getSignedUrl` / `getPublicUrl` / `delete` / `list` throw `new Error('ticket provider is upload-only; read through the same-origin asset proxy')`

Test cases (mock `global.fetch`, fake timers for backoff):
- happy path, s3 strategy: exactly one ticket POST, one PUT, resolved path === ticket key, PUT headers deep-equal `ticket.headers`
- happy path, supabase strategy: `uploadToSignedUrl` called with `(key, token, blob, { upsert: false })`
- blob stamping: a `Blob` with `type: ''` is uploaded with `type === ticket.contentType`; a blob already matching is passed through untouched (identity check)
- transient: PUT fails 503 twice then 200 -> resolves, and **exactly one** ticket POST was made (the key is not re-minted per attempt)
- terminal: PUT returns 403 -> rejects after **one** PUT attempt
- 409 on PUT -> resolves successfully (the wrapper's idempotency rule, reached unchanged through this module)
- ticket POST returns 500 twice then 200 -> resolves, 3 POSTs total
- ticket POST returns 401 -> rejects immediately, **no** PUT attempted
- abort mid-backoff -> rejects `AbortError`, no further fetches
- **retry key identity:** across a transient failure, every PUT used the same URL and key
  </behavior>

  <action>
Create `lib/storage/upload-ticket-types.ts` holding the `UploadTicket` union **only** — pure types, zero runtime code, zero imports. `lib/storage/upload-ticket.ts` re-exports from it and keeps its `import 'server-only'`; `browser-upload.ts` imports from the types file.

Why not `import type` straight from the server module: a type-only import is erased at compile time and would be harmless at runtime, but it still places the server module's specifier in the client module's import list — exactly what Plan 04's static gate scans for. A types-only file makes the client graph provably clean rather than clean-if-you-trust-the-erasure.

Then create `lib/storage/browser-upload.ts`. No `'use client'` directive needed (it is a plain module imported by client components), but it must never import a server module. Header docblock states that constraint and names Plan 04's gate as its enforcement.

**Reuse `uploadWithRetry` verbatim.** Do not fork its backoff, do not reimplement its classification, do not add a parameter to it. Its own test file must stay green *and unmodified* — that green run on an untouched file is the evidence UPLOAD-04 is preserved for the byte move. Your module supplies a `StorageProvider`-shaped object; the wrapper does the rest.

**Why the ticket is minted once, outside the retry loop:** minting per attempt would produce a fresh key per attempt, which (a) breaks the wrapper's 409-means-already-landed rule and (b) strands an orphan object on every transient failure. One ticket, one key, N byte-move attempts. Put that reasoning in a comment above the call, not only here.

`requestUploadTicket`'s own bounded retry is ~20 lines that duplicate the wrapper's *policy* but not its *code* — the wrapper takes a `StorageProvider`, which a JSON POST is not. Keep the two ladders numerically identical and put a comment on each pointing at the other, so a future change to one is visibly a change to only one.

**Do not send credentials to the presigned URL.** No `credentials: 'include'` on the PUT — the default `same-origin` is correct, and sending cookies cross-origin to R2 would both fail CORS and leak a session cookie to a third-party host.
  </action>
