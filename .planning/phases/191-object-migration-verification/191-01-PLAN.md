<objective>
Build the read-and-judge half of the migration command: enumerate what actually
exists in Supabase, learn each object's true byte size and stored content type,
and classify one source object against one destination object into exactly one
status. No writes to R2 happen in this plan — nothing here can move data.

Purpose: MIG-02 is the requirement that makes this phase worth doing. Copying 51
objects is trivial; *proving per object that what landed matches what was there*
is the whole deliverable, and content type is the part that is easy to lose
silently. Production keys such as `platform/1784854705622-kvwo24` have no file
extension, so the stored content-type metadata is the only thing making those
assets render inline instead of downloading as a blob. A copy that drops it
looks successful and breaks the landing page.

Output: `scripts/r2-migrate.ts` with its enumeration + comparison exports, and a
unit test that exercises every status against a fake Supabase client.

Scale is fixed and known: **51 objects, 14.3 MB** (photos 11 MB, platform-brand
2.8 MB, logos 55 kB, audio 55 kB, pdfs 0). Do not build batching, windowing,
concurrency limits, resumability, or a progress bar. Sequential and obvious wins.
</objective>

**THE ONE TRAP THAT MUST NOT BE STEPPED ON.**
The migration run supplies `S3_*` inline. With those vars present,
`serverStorageBackend()` returns `'r2'`, so `getServerStorage()` and
`serverStorage(client)` from `@/lib/storage/server` BOTH return the R2 provider
(see the selection matrix in that file's docblock). If the source side used
either of them, the script would enumerate R2, compare R2 against R2, and report
a perfect migration having moved nothing. **The source side must use
`createStorage(requireServiceClient())` from `@/lib/storage` — the explicit
Supabase factory — for exactly the same reason `lib/storage/asset-source.ts`
does.** Say so in a comment at the call site, not just in the docblock.

**Hard constraints:**
- Do **not** edit `lib/storage/s3-provider.ts`. It is proven against R2 unmodified.
- Do **not** edit `lib/storage/index.ts`, `lib/storage/server.ts`, or
  `lib/storage/supabase-provider.ts` in this plan. The engine reads through the
  existing interface; if something seems missing, get it from the object itself

- Do **not** write any real credential, account id, endpoint, or bucket hostname

    scripted `ListedObject[]` per (bucket, prefix, offset). No network, no
    Supabase client, no credentials.

    - Flat bucket: `list('logos', undefined)` returns two file entries
      (`isFolder: false`) → `walkSupabaseBucket` yields exactly those two keys,
      unprefixed.
    - Nested bucket: root returns one folder placeholder
      (`{ name: '<company-uuid>', isFolder: true }`) plus one file; recursing into
      `<company-uuid>` returns two files → the walk yields
      `['<file-at-root>', '<company-uuid>/a.jpg', '<company-uuid>/b.jpg']`.
      Keys are joined with `/` and the parent prefix is never duplicated.
    - Folder placeholders are never emitted as objects, at any depth.
    - Two-level nesting (`<uuid>/photos/x.jpg`) works — the recursion is not
      hard-coded to one level.
    - Paging: when a prefix returns exactly `limit` entries, the walk requests
      the next page at `offset += limit` and concatenates; when a page returns
      fewer than `limit`, it stops. A fake returning 2 full pages then a short
      page yields all three pages' objects.
    - Paging guard: if the provider keeps returning full pages past a sane
      ceiling (`MAX_PAGES`), the walk THROWS naming the bucket and prefix.
      An infinite listing must crash, not quietly return a prefix of the truth.
    - `list()` rejecting for one bucket propagates — `enumerateSource` does not
      swallow it and does not return a partial-but-successful-looking result.
    - `enumerateSource(storage, MIGRATION_BUCKETS)` returns a flat array of
      `{ bucket, key }` across all five buckets, in bucket order, and a
      per-bucket count map.
    - `.emptyFolderPlaceholder` entries are REAL objects (they have an id, so
      `isFolder` is false) and ARE included — assert this explicitly. They are
      not filtered out: a filter is a place for a bug, and excluding them would
      make source and destination counts disagree by design.

<task type="auto" tdd="true">
  <name>Task 2: Per-object truth — size, content type, and the comparison verdict</name>
  <files>scripts/r2-migrate.ts, tests/unit/storage/r2-migrate.test.ts</files>
  <behavior>
    - `readSourceObject(storage, bucket, key)` calls `storage.download(bucket, key)`
      and returns `{ bucket, key, bytes, size, contentType }` where `size` is the
      blob's byte length and `contentType` is `blob.type`. A fake blob with
      `type: 'image/jpeg'` and 12 bytes → `{ size: 12, contentType: 'image/jpeg' }`.
      The byte size is taken from the downloaded body, NOT from the listing's
      `metadata.size`, so a stale listing cannot certify a wrong size.
    - `normalizeContentType('Image/JPEG')` → `'image/jpeg'`.
    - `normalizeContentType('text/plain;charset=UTF-8')` → `'text/plain'`
      (parameters stripped, so a charset the two backends spell differently is
      not reported as a data-integrity failure).
    - `normalizeContentType(undefined)` and `normalizeContentType('')` → `''`.
    - `compareObject(source, destination)` returns exactly one status:
      | destination | source vs destination | status |
      |---|---|---|
      | `null` | — | `'missing'` |
      | present | size differs | `'size-mismatch'` |
      | present | size equal, normalized content type differs | `'content-type-mismatch'` |
      | present | both equal | `'match'` |
      Size is checked before content type so the more severe finding wins the
      single-status slot; the `detail` string always names both observed values.
    - `'match'` requires BOTH. A destination with the right bytes and
      `application/octet-stream` against a source of `image/jpeg` is
      `'content-type-mismatch'` — assert this explicitly, it is the extensionless
      -key failure mode the whole requirement exists for.
    - Source content type absent: `compareObject` on a source with `contentType: ''`
      yields status `'unknown-source-content-type'` when the destination is
      `application/octet-stream`, and that status renders as `WARN`, is counted
      separately in the summary, and is NOT a failure — but it is also NOT a
      match. If such a source's destination differs from
      `application/octet-stream`, it is still `'content-type-mismatch'`.
    - `formatMigrationReport(rows)`:
      - renders one line per object, prefixed `[MATCH] | [COPIED] | [FAIL] | [WARN] | [EXTRA]`,
        with bucket, key, size, and content type;
      - renders per-bucket count lines `bucket: source=N destination=M`;
      - returns `allPassed: false` when ANY row is `[FAIL]`;
      - returns `allPassed: true` when the only non-`[MATCH]` rows are `[COPIED]`,
        `[WARN]`, or `[EXTRA]`;
      - a `[WARN]` row must render distinctly from `[MATCH]` — assert on the
        rendered text, the same discipline `scripts/r2-verify.ts` applies to
        `SKIP` ("SKIPPED is not a PASS").
    - `[EXTRA]` (a destination object with no source counterpart) is reported,
      counted, and NON-fatal. Assert a report containing only matches plus one
      extra still returns `allPassed: true`, and that the extra appears in the
      text. Rationale to put in a comment: once Phase 188/189 route writes to R2,
      R2-only objects are expected — failing on them would make the command
      permanently red. Their presence is precisely the W1 rollback signal
      documented in `docs/STORAGE-MIGRATION.md`, so they must be visible.
  </behavior>
  <action>
    Extend `scripts/r2-migrate.ts` with the judgement layer. No R2 access yet —
    `compareObject` takes a plain destination descriptor, so it stays a pure
    function and Plan 02 supplies the real `HeadObject` result.

    ```typescript
    export interface SourceObject {
      bucket: string
      key: string
      bytes: Uint8Array
      size: number
      contentType: string      // raw, as stored — preserved verbatim on upload
    }
    export interface DestinationObject { size: number; contentType: string }

    export type ComparisonStatus =
      | 'match'
      | 'missing'
      | 'size-mismatch'
      | 'content-type-mismatch'
      | 'unknown-source-content-type'

    export interface Comparison {
      bucket: string
      key: string
      status: ComparisonStatus
      source: { size: number; contentType: string }
      destination: DestinationObject | null
      detail: string
    }

    export type RowLabel = 'MATCH' | 'COPIED' | 'FAIL' | 'WARN' | 'EXTRA'
    export interface ReportRow { label: RowLabel; bucket: string; key: string; detail: string }

    export async function readSourceObject(storage: StorageProvider, bucket: string, key: string): Promise<SourceObject>
    export function normalizeContentType(raw: string | undefined): string
    export function compareObject(source: SourceObject, destination: DestinationObject | null): Comparison
    export function formatMigrationReport(rows: ReportRow[], countsByBucket: Record<string, { source: number; destination: number }>): { text: string; allPassed: boolean }
    ```

    - `readSourceObject` obtains bytes via `new Uint8Array(await blob.arrayBuffer())`
      and `contentType` via `blob.type`. Comment why the blob is the authority:
      Supabase serves the stored mimetype as the response `Content-Type`, and
      `Blob.type` carries it — which is the only route to that metadata through
      the existing `StorageProvider` interface, since `ListedObject` has no
      content-type field and widening it is out of scope here.
    - Holding 14.3 MB of bodies is fine at this scale, but read and compare ONE
      object at a time and let each `bytes` go out of scope after its row is
      produced — do not accumulate an array of 51 buffers.
    - `normalizeContentType`: `raw?.split(';')[0]?.trim().toLowerCase() ?? ''`.
      Normalization is for COMPARISON ONLY — the value written to R2 is the raw
      `source.contentType`, unmodified. State that in a comment; silently
      re-writing a stored content type during a migration is the class of
      "helpful" change that makes a verification meaningless.
    - `formatMigrationReport` ends with a summary line in the shape
      `objects=51 match=NN copied=NN warn=NN extra=NN FAIL=NN` followed by
      `ALL OBJECTS VERIFIED` or `ONE OR MORE OBJECTS FAILED VERIFICATION`.
      `allPassed` is `rows.every(r => r.label !== 'FAIL')` — computed from the
      rows, never passed in by a caller, so no caller can assert success.
  </action>
