<objective>
Write the runbook MIG-04 asks for, and then actually run the migration.

Purpose: the storage doc currently contains a Hetzner-era procedure that is
wrong in its target, its endpoint shape, its bucket policy, and its rollback —
plus two standing cautions ("do not set `S3_*` in Coolify until Phase 191 has
copied the objects") whose expiry condition is written nowhere. This plan

result of the real run.

strings are asserted by a test, not by good intentions.

automated doc gate, and a recorded live execution.

deliberately lives in the operator's scratchpad, not in `.env.local`, not in
Coolify, and not in this repo. No automation in this codebase can hold it, so
the live run is an operator action by construction, not by preference.

Existing commands the runbook chains:
- `npm run verify:r2` — asserts the five buckets + scope; SKIPPED is not a PASS.
- `npm run migrate:r2` — copy + verify (Plan 02).
- `npm run migrate:r2 -- --verify-only` — verify without writing. The `--` is
  load-bearing.

Provider selection, verbatim from `lib/storage/server.ts`:
`STORAGE_PROVIDER=supabase` is an explicit kill switch that wins even when the
`S3_*` vars are complete. That is the fastest rollback lever and the runbook must
say so.

The asset proxy's Supabase read-through (`lib/storage/asset-source.ts`) means a
partially-copied R2 still serves every asset correctly — so copying can happen in
any order, at any time, with no maintenance window and no write pause. **W1** is
the limit on that: the fallback is one-directional. Once Phase 188/189 route
writes to R2, objects can exist ONLY in R2, and a rollback then requires copying
those back to Supabase. The rollback section must state both halves.
</interfaces>
