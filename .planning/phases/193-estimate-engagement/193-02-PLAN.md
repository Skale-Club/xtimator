# 193-02 — Optional password lock on shared estimates

**Goal:** the owner can set/remove a password on an estimate's share link; visitors must
enter it once per device (24h) before seeing any estimate content on either public route.

## Task 1 — Schema (same migration as 193-01 or a sibling `<ts>_phase193_share_password.sql`)

```sql
ALTER TABLE estimates
  ADD COLUMN share_password_hash text,        -- scrypt: salt$hash, both base64url
  ADD COLUMN share_password_set_at timestamptz;
```

NULL hash = link is open (default, no behavior change for existing estimates).
Apply to prod via Supabase MCP `f2b95485` before code push; regen types.

## Task 2 — Crypto helper `lib/auth/share-password.ts`

No new dependencies — `node:crypto`:

- `hashSharePassword(pw)` → `scrypt(pw, randomSalt16, 64)`, returns `salt$hash` string.
- `verifySharePassword(pw, stored)` → recompute + `timingSafeEqual` with length guard
  (copy the discipline in `lib/oauth/pkce.ts`).
- Cookie session — copy `lib/auth/support-mode.ts` wholesale:
  `encodeUnlockCookie({ t: sha256Hex(share_token), exp })` HMAC-SHA256-signed with
  `APP_ENCRYPTION_KEY`; cookie name `estimate_unlock`, `httpOnly`, `secure`, `sameSite:lax`,
  TTL 24h. `hasValidUnlock(cookieValue, shareToken)` verifies signature + token hash + exp.
- Enforce password rules server-side: 4–72 chars, trimmed non-empty. No complexity rules
  (these are homeowners typing on phones).

## Task 3 — Owner UI: set / remove password

- Server action `setEstimateSharePassword(estimateId, password | null)` in
  `lib/actions/` (auth + owner gate + `assertCompanyWritable`, per existing action
  patterns; auto-discovered by the manifest sweep → add `guarded` entry).
- UI: in `components/workspace/send/send-hub-dialog.tsx` and/or
  `components/workspace/estimate/estimate-tab.tsx` next to the copy-link control:
  a "Protect with password" toggle + password field + "remove" affordance; show a lock
  badge on the link when protected. Follow shadcn/ui patterns already in those files.
- Send flows (email/SMS/WhatsApp bodies) are **not** changed — the password travels out
  of band by the owner's choice; optionally append a "this estimate is password-protected"
  line to the message templates (copy-only change, keep minimal).

## Task 4 — Public gate on both routes

The gate must run **before any estimate content, metadata, or signed photo URL is produced**.

- Extend `lib/queries/share.ts`: `getEstimateByShareToken` /`getEstimateByPublicToken`
  return `{ locked: true, companyBranding }` (name, logo, brand color only — no PII, no
  totals) when `share_password_hash` is set and the request lacks a valid unlock cookie
  (read via `cookies()` in the page and passed down, or checked inside the query helpers).
- `app/estimate/[token]/page.tsx` and `app/estimate/[token]/[estimateSlug]/page.tsx`:
  when locked, render `components/share/estimate-unlock-form.tsx` (client component:
  password input + submit + error state, branded, light theme) instead of `EstimateView`.
  `generateMetadata` for a locked estimate returns a generic title ("Protected estimate")
  — no project name leak.
- Server action `unlockEstimate(token, password)` in `app/estimate/[token]/actions.ts`:
  1. `rateLimit('estimateUnlockPerMinute', `${ip}:${sha256(token).slice(0,16)}`)` —
     new `LimitName`, 5/min (brute-force guard; throttle before any lookup work).
  2. Resolve estimate, `verifySharePassword`.
  3. On success: set the signed `estimate_unlock` cookie, insert `unlock_ok` engagement
     event (service role), return ok → client refreshes via `router.refresh()`.
  4. On failure: insert `unlock_fail` event, return generic error (no oracle on whether
     the token exists).
  - Manifest: extend the existing `app/estimate/[token]/actions.ts` guarded entry
    (line ~612) with the new symbol.
- `logEstimateView` and the 193-01 tracker must **not** record a `view` while locked
  (the unlock form page emits nothing except the server-side `unlock_*` events).
