<objective>
Build the `/invite/accept` route (the link the Phase-136 invite email points at) and wire
the auth flow so an invited person — already a user OR brand new — lands inside the existing
company as a member, never creating their own. The route is the JOIN authority: because it
lives OUTSIDE the (app) group it never triggers the onboarding "create a company" redirect,
and an invited new user reaches accept (JOIN) instead of /onboarding (CREATE). This is the
core "branch" of SEAT-04: the create-company path is skipped for invited signups by ROUTING
them to accept.

Purpose: close SEAT-04 end-to-end — authed join, unauthed signup-then-join, no second company.
Output: app/invite/accept/page.tsx + a `next`-param redirect in lib/actions/auth.ts + a test
proving an invited signup never hits the create-company path.
</objective>

```typescript
export async function acceptInvite(
  token: string

// service-client token authority: validates pending+unexpired+email-match,
```


signUp / signIn today (lib/actions/auth.ts) — they hardcode the post-auth redirect:
```typescript
// signUp: redirect('/onboarding')   ← invited new user must NOT land here
// signIn: redirect(company ? '/dashboard' : '/onboarding')
```
Both read formData. Threading a `next` field (a safe relative path) lets the invite token
survive the auth round-trip. ONLY honor `next` when it starts with '/invite/accept' (prevent
open-redirect — never redirect to an absolute/external URL).

The (app) layout (app/(app)/layout.tsx) redirects to /onboarding when getActiveCompany()
is null. The accept route is OUTSIDE (app), so it renders even before a company exists —
that is exactly why an invited new user can JOIN there instead of being forced into create.

The auth dialog signup is triggered via `/?auth=signup`; login via `/?auth=login`.
A logged-out accept visitor is redirected to `/?auth=signup&next=<encoded accept url>`.
