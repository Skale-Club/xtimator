   `xtimator.com`, not `*.supabase.co`, and a repeated edge request for those

**Edge layer.** `xtimator.com` is proxied through Cloudflare (Free plan, zone
`f4526407a944ec6098b4c1e951c0e8cd`), SSL mode Full (strict), origin Hetzner
`188.245.112.3` behind Coolify/Traefik. **No cache rule exists** — `/_next/static/*`
caches on Cloudflare's default rules alone because those URLs carry real file
extensions. See `docs/CLOUDFLARE-CDN.md`.

**Why HIT is plausible without a new rule.** The proxy serves `platform-brand`
with `public, max-age=31536000, immutable` and sets **no `Vary: Cookie`** on
public buckets (`app/storage/[bucket]/[...key]/route.ts` sets `Vary` only for
private buckets). The landing images are written to keys ending in `.webp`
(`hero-images/{ts}-{name}.webp`, `hero-bg-images/…webp`, `step-images/…webp`,
`feature-images/…webp`, `logo-{ts}.webp`, `favicon-{ts}.{ext}`), which are on
Cloudflare's default cached-extension list.

**Why it might still not.** Cloudflare's default caching keys off the file
extension. Any rewritten key **without** an extension (Phase 187 verified
production holds keys like `platform/1784854705622-kvwo24`) will come back
`cf-cache-status: DYNAMIC` no matter what the origin's `Cache-Control` says. That
is the case that requires a Cache Rule. Measure first; add a rule only on
evidence.

**Landing images are `unoptimized`.** `components/landing/{hero,how-it-works,features}-section.tsx`
all pass `unoptimized` to `next/image` (the self-hosted standalone container has
no `sharp` and the optimizer intermittently failed, making images vanish). So the
browser requests the raw `src` directly — there is no `/_next/image?url=…`
indirection to reason about, and the cache key is the `/storage/...` path itself.

**Query strings are part of Cloudflare's cache key** at the Standard cache level.
That is the cache-bypass mechanism for the fallback proof below: append
`?cb=<random>` to force an origin fetch.

**The fallback's direction limit (W1, `docs/STORAGE-MIGRATION.md`).** The
Supabase read-through covers "object is in Supabase but not yet in R2". Removing
`S3_*` returns every read to Supabase **only while no object exists SOLELY in
R2**. After Phase 188 routed server writes to R2 and Phase 189 sent browser
uploads there, that stops being automatic. The proof below must therefore
establish the precondition, not assume it.

**Observability.** `X-Asset-Source: r2|supabase` is a convenience header and is
**edge-cached along with the body on public buckets**, so a cached value can
outlive the condition it described. The authoritative signal is the server-side
`[asset-proxy] fallback` warn line from `lib/storage/asset-source.ts`.

**Part B — edge cache.** For each distinct landing image path:

```bash
curl -sI "https://xtimator.com$P" | tr -d "\r" | grep -iE "^(cf-cache-status|cache-control|content-type|age):"
```

Request each path **three times in a row** and record the `cf-cache-status`
sequence. Cloudflare will typically report `MISS` (or `EXPIRED`) then `HIT`;
`REVALIDATED` also counts as cached. The pass condition is: **the final request
for each `platform-brand` path reports `HIT`.**

Interpret failures rather than retrying blindly:
- `DYNAMIC` → Cloudflare considers the response uncacheable. Check whether the
  key has a file extension. Extensionless keys are the expected cause.
- `BYPASS` → something is sending a no-cache directive; check the response
  `Cache-Control` actually matches `public, max-age=31536000, immutable`.
- A `Vary: Cookie` on a public-bucket response → a regression in the route; stop
  and fix it, do not paper over it with a cache rule.

Record the full per-path table (path, extension yes/no, cache-control,
cf-cache-status sequence) in the scratchpad; it goes into the summary and into
`docs/CLOUDFLARE-CDN.md`.

**Note on `logos`:** it is served `public, max-age=300, stale-while-revalidate=86400`
deliberately (stable keys + `upsert: true` mean `immutable` would pin a stale
logo in uncacheable browser caches). A `logos` HIT is welcome but a 300-second
TTL is the intended behavior — do not "fix" `logos` to immutable here; that is
tracked as a Phase-190 candidate contingent on versioned keys.
  </action>
