## EXCLUDED — `company_price_book.image_url`

**293 non-null rows, ZERO Supabase URLs.** Every one is an external
`https://images.pexels.com/...` stock photo. This column is NOT a rewrite target.

The requirement text names "price-book image URLs", so this is the trap: a
rewrite that matched on *column name* rather than on the *Supabase storage URL
prefix* would corrupt 293 rows of working data. It is recorded as an explicit
exclusion, with its numbers, so a later reader does not "fix" the omission.

(Its writers do call `getPublicUrl('photos', key)` — and `photos` is
`public = false` in Supabase — so such a value *would* be broken if it existed.
None exists in production today, so there is nothing to verify and no plan step
depends on it.)

## The shape of the work

8 of the 11 occurrences live **inside one JSONB document**. A rewrite that only
handled `text` columns would silently miss 73% of the scope and leave the landing
page — the exact surface PROXY-05 must prove — still pulling from `*.supabase.co`.
The document must be walked, and the rewrite must be **value-level** (each URL
leaf replaced independently); the *audit record* is document-level so restore is
a single exact assignment. Those two are not in conflict — say both.

One of the 8 is a background **video** (`heroBackgroundVideoUrl`, written to
`hero-bg-videos/{ts}-{name}.{mp4|webm}` by `app/admin/landing/actions.ts`), not
an image. Nothing in the rewrite may be image-only.

```typescript
export type ValueKind = 'text' | 'jsonb' | 'user_metadata'
export interface RewriteTarget { id: string; table: string; column: string; pk: string; kind: ValueKind }
export interface ExcludedTarget { id: string; reason: string; measuredRows: number; measuredSupabaseUrls: number }

export const REWRITE_TARGETS: RewriteTarget[]     // the 8 census targets
export const EXCLUDED_TARGETS: ExcludedTarget[]   // company_price_book.image_url, 293 rows, 0 supabase urls

export interface PlannedChange { target: string; rowPk: string; kind: ValueKind; oldValue: unknown; newValue: unknown }
export interface AuditRecord { id: number; target: string; row_pk: string; value_kind: ValueKind; old_value: unknown; new_value: unknown }

export function planTextRewrite(rows: Record<string, unknown>[], target: RewriteTarget): PlannedChange[]
export function planJsonRewrite(rows: Record<string, unknown>[], target: RewriteTarget): PlannedChange[]
export function planUserMetadataRewrite(users: { id: string; user_metadata: Record<string, unknown> | null }[]): PlannedChange[]
export function projectRefFromUrl(url: string | undefined): string | null
export function assertProjectConfirmed(envRef: string | null, flagRef: string | null): { ok: true } | { ok: false; reason: string }
export function planRevert(records: AuditRecord[], current: Map<string, unknown>): { restore: AuditRecord[]; drifted: AuditRecord[] }
```

Rules:

1. **Selection is by URL prefix, never by column name.** Every candidate value
   goes through Plan 01's `rewriteAssetUrl`, which only matches a Supabase public
   storage URL for an allowlisted bucket. This is the single property that keeps
   the 293 external price-book URLs and the 8 OAuth avatars safe. Any DB-side
   `ilike` filter is an optimisation on top of that, never the authority.
2. `EXCLUDED_TARGETS` carries the reason and the measured numbers in code, not
   just in a comment, so `--preflight` can print them and a reader cannot mistake
   the omission for an oversight.
3. The three `plan*` functions take **plain arrays of rows** — no Supabase
   client, no network. That is what makes them testable and the production run
   predictable.
4. For `kind: 'jsonb'` and `kind: 'user_metadata'`, `oldValue`/`newValue` are the
   **whole** document/object — the rewrite is value-level, the record is
   document-level, so restore is one exact assignment and never a merge.
5. `assertProjectConfirmed` is the wrong-database guard: `--apply` and `--revert*`
   require `--confirm-project <ref>` matching the ref derived from
   `NEXT_PUBLIC_SUPABASE_URL`. **This matters concretely: `.env.local` in this
   repo points at the PRODUCTION Supabase project.** Absent or mismatched →
   refuse, exit non-zero, write nothing.
6. `planRevert` compares each audit record's `new_value` against the row's current
   value. Equal → restore. Different → `drifted`, and do NOT restore — a newer
   upload must not be clobbered by a rollback.
7. Nothing in this file may throw on a malformed row; a bad row is skipped and
   counted, never fatal mid-flight.
8. Never print a secret, a service key, or a full env value. The project ref is
   public and fine to print.

Add the I/O shell around Task 1's core. Four modes; **dry-run is the default**.

**`--preflight`** (read-only, always safe)
- Print the resolved project ref from `NEXT_PUBLIC_SUPABASE_URL` (never the key).
- BLOCKER check: `public.storage_url_rewrites` exists (`select id ... limit 1`).
  Missing → print BLOCKER, exit non-zero. Plan 03 relies on this failing loudly
  when the migration has not yet been applied by hand.
- BLOCKER check: Phase 190 shipped — `getPublicUrl` already emits the same-origin
  form. Verify by importing the provider factory and asserting
  `getPublicUrl('logos','x/y.webp')` starts with `/storage/`. Not shipped →
  BLOCKER, exit non-zero. Rationale: rewriting rows while writers still persist
  absolute URLs means the data drifts straight back.
- WARN (not blocker): R2 object presence (Phase 191). The asset proxy's Supabase
  read-through fallback makes the rewrite correct even with an empty R2. State
  that explicitly; do not report it as a pass.
- Print the census per target: occurrences holding an absolute Supabase URL, rows
  already in the new form, rows holding something else. Print the expected
  measured baseline alongside it (**11 total: 1 / 1 / 1 / 8**, four targets at
  zero) so a divergence is visible without arithmetic.
- Print the `EXCLUDED_TARGETS` block read-only: `company_price_book.image_url —
  EXCLUDED — 293 non-null rows, 0 Supabase URLs (external images.pexels.com stock
  photos)`. Re-count the Supabase-URL figure live; if it is not 0, print a
  BLOCKER — something started writing Supabase URLs into that column and the
  exclusion needs re-deciding.
- `--dump <path>`: write the complete pre-state (every target's current value) as
  JSON to `<path>`. The operator points this **outside the repo** (it contains
  tenant rows). At 11 occurrences this is one small artifact, and it is a second,
  independent restore path that exists before the audit table holds a single row.

**default / `--dry-run`** — run the full plan and print every change as
`target | row_pk | old -> new` (truncate each URL at 100 chars) plus totals.
**Writes nothing.** Exit 0.

**`--apply`** — requires `--confirm-project <ref>`. Generate one `batch_id`
(uuid) for the run and print it FIRST, before any write, so it survives a crash
in scrollback. Then per change:
1. `insert` the audit row into `public.storage_url_rewrites` (target, row_pk,
   value_kind, old_value, new_value);
2. only then `update` the target row, or call `auth.admin.updateUserById` for the
   `user_metadata` target.
Insert-before-update means a crash can leave an audit row whose `new_value` was
never written — and `planRevert`'s drift check handles that correctly
(current == old ≠ new → drifted → skipped, which is right: there is nothing to
undo). Print a per-target summary and the batch id again at the end. Any error →
print it and exit non-zero. Never swallow.

**`--revert-latest`** (or `--revert <batch-id>`) — requires `--confirm-project`.
Load every audit row for the batch with `reverted_at is null`, read current
values, run `planRevert`, restore the `restore` set, stamp `reverted_at`, and
print the `drifted` set explicitly. **Exit non-zero if anything drifted**, so a
partial rollback can never be mistaken for a clean one. `--force` also restores
drifted rows and must say so loudly.

**No scale engineering.** The measured scope is 11 occurrences; plain full selects
per target are correct and clearer than a paging loop. Do not add batching,
windowing, chunked updates, resumability or progress bars — they would be
unexercised code on the one script in this repo that touches production business
rows.

Add to `package.json` scripts:
```json
"rewrite:asset-urls": "npx tsx scripts/rewrite-asset-urls.ts"
```
so the rollback is literally one command:
`npm run rewrite:asset-urls -- --revert-latest --confirm-project <ref>`.

The docblock at the top must state, in this order: what the script does; the
measured scope (11 occurrences / 4 columns) and the price-book exclusion; that it
is an OPERATIONAL step run by hand, never by CI or the deploy pipeline; that
dry-run is the default and `--apply` is required to write; that `.env.local` in
this repo points at PRODUCTION; and the one-command rollback.

No route handler is added by this plan, so
`tests/unit/demo/mutation-boundary-sweep.test.ts` needs no manifest edit. If you
find yourself adding one, register it there.
