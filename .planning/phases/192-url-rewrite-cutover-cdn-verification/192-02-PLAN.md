Rules:

1. **Selection is by URL prefix, never by column name.** Every candidate value
   goes through Plan 01's `rewriteAssetUrl`, which only matches a Supabase public
   storage URL for a **persistable, non-exempt** bucket. This single property
   keeps the 293 external price-book URLs, the 8 OAuth avatars and the hero video
   safe. Any DB-side `ilike` filter is an optimisation on top, never the authority.
2. `EXCLUDED_TARGETS` carries the reason and the measured numbers **in code**, not
   just a comment, so preflight can print them and a reader cannot mistake the
   omission for an oversight.
3. `selectApplyBatch` is the crash-recovery primitive (see B5 in Task 2): if an
   unreverted batch already exists, apply **reuses** it instead of minting a
   second. The unique index on `(batch_id, target, row_pk)` makes re-recording
   inside a reused batch a no-op.
4. The `plan*` functions take **plain arrays of rows** — no Supabase client, no
   network. That is what makes them testable and the production run predictable.
5. For `kind: 'jsonb'`/`'user_metadata'`, `oldValue`/`newValue` are the **whole**
   document/object — value-level rewrite, document-level record, so restore is one
   exact assignment and never a merge.
6. `assertProjectConfirmed` is the wrong-database guard: `--apply` and `--revert*`

7. `planRevert` compares each record's `new_value` against the row's current value.

   be clobbered.
8. Nothing here may throw on a malformed row; a bad row is skipped and counted.
9. Never print a secret, a service key, or a full env value. The project ref is
   public and fine to print.

### `--apply` (requires `--confirm-project <ref>`)

**B5 — crash-safe batching.** Query for unreverted batches FIRST and pass them to
`selectApplyBatch`. If one is open, **reuse it**; print `BATCH_REUSED=true`. This
is what makes a crashed apply + re-run a single batch, so `--revert-latest` cannot
restore half of production while reporting success. Print `BATCH_ID` before any
write so it survives a crash in scrollback.

**B6 — compare-and-set, and prove the write happened.** Per change:
1. `insert` the audit row (target, row_pk, value_kind, old_value, new_value);
2. `update` the target row **conditionally on its prior value**, and `.select()`
   the result:
   - `text` targets: `.eq(pk, rowPk).eq(column, oldValue)` — exact-string CAS;
   - `platform_branding.landing_content` (jsonb): read `updated_at` alongside the
     document, then `.eq('id', 1).eq('updated_at', priorUpdatedAt)` — a JSONB
     equality filter is not reliable through PostgREST, the timestamp guard is.
     `platform_branding.updated_at` is `not null default now()` and every admin
     save sets it;
   - `user_metadata`: the Admin API has no CAS. Re-read the user immediately
     before the write and abort if `avatar_url` changed. Document the residual
     race honestly — and note it has zero subjects in production.
3. **Assert exactly 1 row affected.** On 0 rows: DELETE the audit row just
   inserted, print which target/row and why (concurrent write or stale read), and
   **exit non-zero**. Never leave an audit row claiming a change that did not
   happen — that row would later surface as "drifted" and be indistinguishable
   from a legitimate re-upload, which is precisely the ambiguity you do not want
   at 2am.

Print `APPLIED_CHANGES` and `BATCH_ID` again at the end. Any error → print and
exit non-zero. Never swallow.

### `--revert-latest` (requires `--confirm-project`)

**B5 — completeness over convenience.** Count unreverted batches first and print
`UNREVERTED_BATCHES`. Then revert **all** of them, newest-first, in one run —
partial rollback is the failure mode this exists to prevent. For each batch: load
rows with `reverted_at is null`, read current values, run `planRevert`, restore the
`restore` set with the same CAS + 1-row assertion as apply, stamp `reverted_at`,
and print the `drifted` set explicitly.

**Exit non-zero if anything drifted**, so a partial rollback can never read as
clean. `--force` also restores drifted rows and must say so loudly.
`--revert <batch-id>` stays available for surgical single-batch use, and prints
`UNREVERTED_BATCHES` so the operator sees what it is NOT reverting.

### `--restore-from-dump <path>` (requires `--confirm-project`)

The independent second restore path — the one that works when the audit table
itself is the thing that went wrong. Reads the `--dump` JSON, compares against
current values via `planRestoreFromDump`, restores differences with the same CAS +
1-row assertion, and prints what it changed. Without this, `--dump` is a file
nothing consumes and must not be described as a restore path.

### No scale engineering

The measured scope is 11 occurrences. Plain full selects per target are correct and
clearer than a paging loop. No batching, windowing, chunked updates, resumability
or progress bars — unexercised code has no place in the one script that touches
production business rows.
