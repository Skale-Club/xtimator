<task type="auto">
  <name>Task 3: Rollback rehearsal — clean revert AND the interrupted-apply case</name>
  <files>(no repo files — production data)</files>
  <action>
The reversible record is only a claim until it is executed. Prove it twice: once
for the clean case, once for the case that actually bites.

**Part A — clean revert.**
1. ```bash
   npm run rewrite:asset-urls -- --revert-latest --confirm-project prmqgcrnpuvpzruyzvuv
   ```
   Expect `UNREVERTED_BATCHES=1`, `REVERTED=11`, `DRIFTED=0`, exit 0. Any drift
   here means something else is writing these rows concurrently — STOP and
   investigate.
2. **Verify the restore is exact.** Re-read every target value and compare against
   `$T/192-pre-state.json` from Task 1. Use a **deep-equal** comparison, not a
   byte comparison: `jsonb` does not preserve key order, so a byte diff on
   `landing_content` would report a false failure. Write a throwaway comparison
   snippet in the scratchpad; do not add it to the repo.
3. Re-apply:
   ```bash
   npm run rewrite:asset-urls -- --apply --confirm-project prmqgcrnpuvpzruyzvuv
   ```
   A NEW `BATCH_ID` (the prior batch is stamped `reverted_at`). Record it.

**Part B — the interrupted apply.** This is the failure mode a clean rehearsal
never exercises: each run minting a fresh batch means a crash mid-apply leaves
batch A open, the re-run creates batch B, and a naive `--revert-latest` restores
only B while reporting zero drift and exiting clean — half-restored production
that looks like success.
1. Revert the live batch again so production is back at the pre-state.
2. Start an apply and **interrupt it mid-run** (Ctrl-C, or a temporary env/network
   break) after at least one write has landed. Confirm an open batch exists with a
   partial row count.
3. Re-run `--apply --confirm-project <ref>`. It must print `BATCH_REUSED=true` and
   complete the remaining changes **into the same batch** — `UNREVERTED_BATCHES`
   must be 1, never 2.
4. Run `--revert-latest`. It must report `UNREVERTED_BATCHES=1`, restore all 11,
   `DRIFTED=0`, and leave production deep-equal to the pre-state dump. If the
   design had minted two batches, this is where a half-restore would show up.
5. Re-apply one final time. Record the final `BATCH_ID` — this is the live batch
   Plans 04 and 05 verify against, and the one an operator would revert if the
   phase is abandoned.
6. Final dry run: `PLANNED_CHANGES=0`.

Record in the summary: every batch id and its disposition (reverted / live), the
drift counts from both rehearsals (must be 0), the deep-equal comparison result,
and `BATCH_REUSED=true` from Part B step 3 — that token is the evidence that the
crash path was actually exercised rather than reasoned about.
  </action>
  <verify>
