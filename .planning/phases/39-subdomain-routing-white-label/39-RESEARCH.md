## Summary

Phase 39 implements the routing and rendering side of custom domain support. When a request arrives at a company's custom domain (e.g., `estimates.mycompany.com`), the app must (1) detect the non-Xtimator host in the middleware/proxy layer, (2) look up which company owns that domain, (3) serve the correct `/estimate/{token}` page transparently (no redirect), and (4) hide the "Generated by Xtimator" footer.

All the infrastructure is already present. Phase 38 added `custom_domain` to the `companies` table with index and save action. The public estimate route `/estimate/[token]` is already auth-exempt. The `EstimateView` component already renders company branding; only the footer needs a conditional.

The critical architectural decision is **where to do the host lookup**. There are two valid options: (A) detect in `proxy.ts` and rewrite the URL, letting the existing `/estimate/[token]` page handle rendering; or (B) create a new route group for custom-domain requests. Option A is strongly preferred — it reuses all existing route logic and aligns with the existing 404-rewrite pattern already in `proxy.ts`. The `/estimate/[token]/page.tsx` then simply receives a `whiteLabelMode` flag derived from the request host.

**Primary recommendation:** Detect custom host in `proxy.ts`; if the request host matches a `companies.custom_domain`, rewrite to `/estimate/{token}` and set a request header `x-white-label: 1`; read that header in `page.tsx` to pass `whiteLabelMode` to `EstimateView`; render nothing for the footer when `whiteLabelMode` is true.

## How the Existing System Works (Verified from Source)

### proxy.ts — the routing layer

File: `/proxy.ts` (root of repo, NOT `/middleware.ts`).

Next.js (Turbopack) picks up this file as the middleware module even though the export is named `proxy`, not `middleware`. The dev build confirms: `"[project]/proxy.ts [middleware] (ecmascript)"`. The `export const config` matcher applies to all paths except static assets.

**Current flow:**
1. `updateSession(request)` refreshes the Supabase session cookie and returns `{ claims, response }`.
2. Admin gate for `/admin/*` — 404-rewrite if not a platform admin.
3. If `updateSession` returned a redirect (3xx), short-circuit.
4. Otherwise return `response`.

**Custom host detection goes here.** The right insertion point is BEFORE the `updateSession` call (or immediately after, but before any redirect logic), so custom-domain requests are intercepted first.

The pattern to add:
```typescript
const host = request.headers.get('host') ?? ''
const appHost = process.env.NEXT_PUBLIC_APP_HOST ?? 'xtimator.com'
const isCustomHost = host !== appHost && !host.startsWith('localhost') && !host.endsWith('.vercel.app')

if (isCustomHost && pathname.startsWith('/estimate/')) {
  // Pass through — /estimate/* is already public, no auth needed
  // Set a header so page.tsx knows it's white-label mode
  const requestWithHeader = new NextRequest(request, {
    headers: { ...Object.fromEntries(request.headers), 'x-white-label': '1' }
  })
  return NextResponse.next({ request: requestWithHeader })
}
```

Note: Simply passing through is sufficient because `/estimate/[token]` already renders the correct company estimate by token alone. The token is globally unique across all companies — there is no ambiguity about which company's estimate to show.

**The auth redirect trap:** `isPublicRoute('/estimate/abc123')` already returns `true` in `lib/supabase/proxy.ts`, so the `updateSession` redirect guard (`if (!claims && !isPublicRoute(pathname))`) will NOT redirect custom-domain estimate requests to `/login`. No change needed to `isPublicRoute`.

### lib/supabase/proxy.ts — isPublicRoute

```typescript
const isPublicEstimate = pathname.startsWith('/estimate')
```

`/estimate/*` is already public. The custom domain request arrives with `pathname = '/estimate/{token}'` regardless of the host. Auth is not triggered.

### lib/queries/share.ts — getEstimateByShareToken

Fetches estimate by `share_token` (globally unique). Joins company data via `estimate.company_id`. The company select currently fetches:
```
name, owner_name, phone, email, website, address, city, state, zip, logo_url,
brand_primary_color, notify_on_view, notify_on_accept, notify_on_decline
```

**`custom_domain` is NOT fetched** in the current query. For Phase 39, the page does NOT need to re-query `custom_domain` — the white-label mode is determined by the incoming host header, not by a DB lookup at render time. The host header detection in `proxy.ts` is the single source of truth.

However, there is one optional enhancement: the page could verify that `host === estimate.company.custom_domain` to prevent one company's custom domain from serving another company's estimate. In practice, this is mitigated by the fact that (a) tokens are globally unique, and (b) a bad actor would need to know another company's token to misuse this. For v1, host verification at render time is not required — the proxy layer already guarantees the host matches a configured domain.

## Architecture Patterns

### Pattern 1: Host-header detection in proxy.ts

**What:** Read `request.headers.get('host')` in the middleware, compare to the known app hostname, and add a downstream header if it is a custom domain.

**When to use:** Any time middleware-level routing decisions need to be communicated to RSC page components. Headers are the standard channel because they survive the `NextResponse.next()` boundary.

**Example:**
```typescript
// proxy.ts — insert BEFORE updateSession call
const host = request.headers.get('host') ?? ''
const appHost = process.env.NEXT_PUBLIC_APP_HOST ?? 'xtimator.com'

// localhost, *.vercel.app, and the primary app host are NOT custom domains
const isCustomHost =
  !host.includes('localhost') &&
  !host.endsWith('.vercel.app') &&
  host !== appHost

if (isCustomHost && pathname.startsWith('/estimate/')) {
  const res = NextResponse.next()
  res.headers.set('x-white-label', '1')
  return res
}
```

**Important:** Mutating request headers in Next.js middleware requires constructing a new `NextRequest` or using `NextResponse.next({ request: { headers: newHeaders } })`. The `res.headers.set()` approach sets RESPONSE headers (visible to the browser), not request headers forwarded to the page. To pass info to the RSC, use `NextResponse.next({ request: { headers: ... } })`.

Correct pattern:
```typescript
const requestHeaders = new Headers(request.headers)
requestHeaders.set('x-white-label', '1')
return NextResponse.next({
  request: { headers: requestHeaders },
})
```

### Pattern 2: Reading forwarded headers in RSC

```typescript
// app/estimate/[token]/page.tsx
import { headers } from 'next/headers'

export default async function SharePage({ params }: SharePageProps) {
  const { token } = await params

  // ...
  return (
    <EstimateView
      {...props}
      whiteLabelMode={isWhiteLabel}
    />

```

### Anti-Patterns to Avoid

- **Creating a new route for custom domains:** A separate route group (`app/(custom-domain)/...`) would duplicate the estimate rendering logic. Unnecessary — the existing `/estimate/[token]` route works from any host.
- **DB lookup in middleware for host resolution:** Do NOT query Supabase inside `proxy.ts` to find the company matching the host. Middleware runs on every request; a DB round-trip per request would add latency. The host detection pass-through is zero-cost — the DB lookup for the estimate by token is already happening in the page component.
- **Hardcoding `xtimator.com`:** Use `process.env.NEXT_PUBLIC_APP_HOST` with a fallback so the check works in Vercel preview deployments (where the host will be `*.vercel.app`).
- **Setting response headers instead of request headers:** `res.headers.set('x-white-label', '1')` sets a response header (sent to browser), NOT a forwarded request header. The RSC `headers()` API reads request headers. Use `NextResponse.next({ request: { headers: ... } })`.

## Common Pitfalls

### Pitfall 1: Setting response header instead of request header in middleware

**What goes wrong:** Doing `NextResponse.next(); res.headers.set('x-white-label', '1')` sets the header in the outgoing HTTP response to the browser — NOT in the request forwarded to the RSC. The `headers()` call in `page.tsx` reads incoming request headers and won't see a response header.

**Why it happens:** The Next.js `NextResponse` API has both request and response header mutation paths. The subtle distinction is easy to miss.

**How to avoid:** Always use `NextResponse.next({ request: { headers: modifiedHeaders } })` to forward headers to the page.

**Correct pattern:**
```typescript
const requestHeaders = new Headers(request.headers)
requestHeaders.set('x-white-label', '1')
return NextResponse.next({ request: { headers: requestHeaders } })
```

### Pitfall 2: localhost dev testing — custom host detection fails or triggers on localhost

**What goes wrong:** If the custom domain check is too broad (e.g., `host !== 'xtimator.com'`), it will trigger on `localhost:3000` during development, causing all local estimate views to be white-label.

**Why it happens:** `localhost:3000` does not match `xtimator.com`.

**How to avoid:** Explicitly exclude localhost: `!host.includes('localhost') && !host.endsWith('.vercel.app') && host !== appHost`.

**Warning signs:** Footer disappears on all local estimate preview pages.

### Pitfall 3: Vercel preview deployment host triggers false positive

**What goes wrong:** Vercel preview deploys have hosts like `xtimator-abc123.vercel.app`. These are not custom domains but don't match `xtimator.com`.

**Why it happens:** The primary `NEXT_PUBLIC_APP_HOST` check only covers the production domain.

**How to avoid:** Also exclude `.vercel.app` suffixes: `!host.endsWith('.vercel.app')`.

### Pitfall 4: Auth redirect loop for authenticated users visiting a custom domain

**What goes wrong:** If a user is authenticated and visits `estimates.mycompany.com/estimate/abc123`, `updateSession` runs and may attempt to refresh their Supabase session. The session cookie is set for `xtimator.com` (different domain), so the cookie isn't present. This is fine — `isPublicRoute('/estimate/abc123')` returns `true`, so no redirect occurs.

**Why it happens:** Theoretically, cookie mismatch could cause `getClaims()` to return null and trigger a redirect. But `isPublicRoute` already guards this.

**How to avoid:** No action needed. The existing `isPublicRoute` guard prevents any auth redirect on `/estimate/*` paths regardless of host.

### Pitfall 5: Vercel project needs the custom domain registered

**What goes wrong:** Even with correct DNS (CNAME to `cname.vercel-dns-0.com`), requests to `estimates.mycompany.com` will return an error if the domain is not added to the Vercel project dashboard. Vercel won't route the domain to the app until it is explicitly added in the project settings.

**Why it happens:** Vercel requires explicit domain registration to issue TLS certs and route traffic.

**How to avoid:** Document for users that after configuring DNS, they must also add the domain in the Vercel dashboard (or this step needs to be automated via the Vercel API — out of scope for v1). Phase 38 already shows DNS instructions; Phase 39 could add a note about Vercel-side registration.

**Note for v1:** The instructions card in Phase 38 already says to point DNS to Vercel. Adding a note that the domain must also be registered in Vercel project settings is sufficient for v1.

```typescript
import { type NextRequest, NextResponse } from 'next/server'
import { updateSession } from '@/lib/supabase/proxy'
import { checkPlatformAdmin } from '@/lib/supabase/admin-gate'

export async function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  // === NEW: Custom domain white-label pass-through ===
  const host = request.headers.get('host') ?? ''
  const appHost = process.env.NEXT_PUBLIC_APP_HOST ?? 'xtimator.com'
  const isCustomHost =
    !host.includes('localhost') &&
    !host.endsWith('.vercel.app') &&
    host !== appHost

  if (isCustomHost && pathname.startsWith('/estimate/')) {
    const requestHeaders = new Headers(request.headers)
    requestHeaders.set('x-white-label', '1')
    return NextResponse.next({ request: { headers: requestHeaders } })
  }
  // === END NEW ===

  // Always refresh session first (existing behavior — preserved).
  const { claims, response } = await updateSession(request)

  // ... (rest unchanged)
}
```
