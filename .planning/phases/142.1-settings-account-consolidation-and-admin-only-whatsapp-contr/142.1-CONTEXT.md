# Phase 142.1: Settings Account Consolidation and Admin-Only WhatsApp Control - Context

**Gathered:** 2026-06-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Consolidate the tenant's personal profile and security controls into a single Account settings page, restore WhatsApp as a platform-managed capability, remove tenant access to WhatsApp provisioning and conversation visibility, and give the super-admin an account-filtered operational surface. Preserve tenant outbound estimate sending as an opaque provisioned action. This phase corrects an authority/privacy regression; it does not redesign the WhatsApp AI engine or Meta platform credentials.

</domain>

<decisions>
## Implementation Decisions

### Settings information architecture
- **D-01:** General and Account must not remain separate. Account is the canonical tenant route for profile photo, account name, personal phone, email, and password.
- **D-02:** Remove General from the settings navigation and keep `/settings/general` only as a compatibility redirect to `/settings/account`.
- **D-03:** Keep `/settings` redirecting to Company; this phase does not change the default settings landing page.

### WhatsApp ownership and visibility
- **D-04:** WhatsApp provisioning is controlled exclusively by the super-admin. A tenant cannot view or edit linked numbers, routing status, delivery format, WABA/platform configuration, or provisioning state.
- **D-05:** A tenant cannot view an inbox, conversation thread, message history, unread count, or message preview through `/whatsapp`, project Client surfaces, or any direct legacy URL.
- **D-06:** Tenant outbound estimate sending via WhatsApp remains available as an opaque action when the account is active and admin-provisioned. The action must not reveal configuration or conversation history.
- **D-07:** Remove the tenant-facing WhatsApp card from Settings → Integrations rather than retaining a read-only “platform managed” card.

### Administration
- **D-08:** `/admin/whatsapp` is the canonical operational surface and must filter server-side by tenant company/account, authorized sender/member, phone/contact search, status, unread state, and date range, with pagination.
- **D-09:** Super-admins can provision, activate, suspend, and remove authorized WhatsApp routing numbers. Every mutation requires `requireAdmin()`, E.164 validation, active-number uniqueness, and an `admin_audit_log` entry.
- **D-10:** Conversation inspection remains read-only in this phase. Admin reply/send controls are out of scope.

### Data and routing authority
- **D-11:** Separate company-level WhatsApp configuration from authorized sender identities rather than continuing to overload `company_whatsapp` with both concerns. The planner may choose final table names, but the authority boundary and cardinality split are locked.
- **D-12:** Use an expand–migrate–contract rollout. Preserve existing rows first, migrate deterministically, report companies with conflicting active numbers for manual admin review, and contract deprecated columns/indexes only after compatible application reads are deployed.
- **D-13:** Inbound owner commands resolve only through active admin-provisioned senders. Remove onboarding/profile writes and the `companies.phone` owner-routing fallback.
- **D-14:** Existing conversation fallback may remain only for already-associated external contacts and must fail closed on ambiguity; `clients.phone` must not silently select one tenant when a phone exists in multiple companies.

### Notifications and consent
- **D-15:** Remove WhatsApp controls from tenant notification settings and disable proactive WhatsApp notification dispatch during this transition.
- **D-16:** Preserve historical WhatsApp opt-in timestamps/data. A super-admin cannot grant consent on behalf of a tenant. A future compliant consent mechanism is outside this phase.
- **D-17:** SMS remains independent and is not removed by this phase.

### Verification and rollout
- **D-18:** Add structural tenant-surface guards, admin authorization tests, account redirect/profile tests, migration contract tests, webhook routing tests, and cross-tenant isolation coverage before deleting legacy paths.
- **D-19:** Migrations are authored only and deployed through CI → GHCR → Coolify; no remote/manual migration is part of execution.

### the agent's Discretion
- Exact admin component composition, filter control layout, cursor versus offset pagination, final normalized table names, and internal compatibility helper names.
- Whether the Account page uses one card or separate Profile and Security cards, provided the page remains mobile-safe and visually consistent with current settings patterns.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `AccountSection` and `ProfileSection`: existing credential and profile forms to compose under Account.
- `requireAdmin`, `requireServiceClient`, and `logAdminAction`: established admin authorization, privileged DB access, and audit patterns.
- Admin Companies pages: existing company selection/detail patterns that can feed account filters and provisioning links.
- `AdminWhatsAppClient` and `MessageBubble`: existing read-only conversation table and thread rendering.
- `PhoneInput` and existing E.164 normalization helpers: reusable phone entry/validation primitives.

### Established Patterns
- Tenant-sensitive service-role operations require an explicit app-layer authority gate because WhatsApp tables use deny-all RLS.
- Super-admin cross-tenant reads use `requireAdmin()` plus the service client.
- Settings uses route-per-section navigation and redirects for canonical routes.
- Authored migrations are deployed through CI/GHCR/Coolify and must be idempotent.

### Integration Points
- Account consolidation touches settings navigation, account/general pages, loading skeletons, and `updateProfile` revalidation.
- Tenant WhatsApp removal touches Settings, the direct `/whatsapp` route, project conversation cards/queries, notification preferences, and tenant inbox actions.
- Admin filtering/provisioning touches `/admin/whatsapp`, Companies/member identity lookup, server actions, and admin audit log.
- Routing hardening touches onboarding company creation, `syncOwnerPhone`, the webhook resolver, conversation identity, outbound send gating, and notification dispatch.

</code_context>

<specifics>
## Specific Ideas

- “General” and “Account” are redundant; Account is the clearer single label.
- WhatsApp must not be available for tenant visualization and must be visible operationally only to super-admins with filters by account.
- The fix must address the underlying writer/routing model, not merely hide UI elements.

</specifics>

<deferred>
## Deferred Ideas

- Admin-authored replies or outbound conversation management from the admin inbox.
- A new tenant-controlled WhatsApp notification consent mechanism.
- Redesign of the WhatsApp AI agent, prompt, Meta credentials, or template registry.

</deferred>
