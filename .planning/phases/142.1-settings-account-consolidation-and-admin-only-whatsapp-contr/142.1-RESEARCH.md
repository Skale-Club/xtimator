<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions
- Account replaces the separate General page and contains profile plus credential controls.
- Tenants cannot view or configure WhatsApp provisioning, inboxes, conversations, numbers, status, delivery format, unread counts, or previews.
- Super-admin owns provisioning and gets server-side account/sender/status/unread/date/search filters with pagination.
- Tenant outbound estimate sending remains as an opaque action for active provisioned accounts.
- Company configuration and authorized sender identity become separate concepts.
- Owner routing trusts active admin-provisioned senders only; onboarding/profile/company phone cannot change routing.
- Proactive tenant WhatsApp notifications are disabled while historical consent is preserved.
- Use authored, idempotent expand–migrate–contract migrations deployed through CI/GHCR/Coolify.

- Account card composition.
- Final normalized table/helper names.

### Deferred Ideas (OUT OF SCOPE)

- A replacement WhatsApp notification consent flow.

<research_summary>
## Summary

The repository already contains both sides of the product decision. Quick task `260602-jns` deliberately moved WhatsApp to a platform-managed model; `260620-m6p` later introduced per-user `owner_phone`, tenant profile writes, tenant-scoped conversation history, and webhook owner routing. The current state therefore is not a missing UI polish pass: it is an authority-model regression across schema, server actions, settings, webhook routing, notification preferences, and project surfaces.

The safest repair is an expand–migrate–contract sequence. Introduce a company configuration table/row and an authorized-sender registry while old reads still work, migrate current rows deterministically, expose conflicts to admins, move all reads/writes to a single server-only repository, then remove tenant writers and legacy routing fallbacks. The admin dashboard must query filters at the database boundary rather than loading a global 500-row slice and filtering in the browser.

**Primary recommendation:** Build one server-only WhatsApp account repository over normalized configuration/sender tables, migrate all admin, webhook, notification, and send gates to it, then delete tenant visibility and legacy writers behind structural tests.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### Target data flow

```text
Admin provisioning request
  → requireAdmin
  → validate company/member/E.164/status transition
  → WhatsApp account repository
  → company config + authorized sender registry
  → admin audit log

Inbound Meta webhook
  → HMAC verification
  → normalized sender phone
  → active authorized sender lookup
  → exactly one company or fail closed
  → existing WhatsApp processing graph

Tenant outbound estimate action
  → authenticated active company
  → opaque account-active predicate
  → existing send-estimate path
  → no config/history returned to browser
```

### Pattern 1: Expand–migrate–contract
Add new structures and compatibility reads first; migrate and validate; switch writers/readers; remove legacy columns/indexes only after no application path uses them. This prevents deployment skew when migrations and the new image do not become active at exactly the same instant.

### Pattern 2: One server-only repository
All provisioning status, authorized-sender lookup, and account-active checks should flow through one `server-only` module. Direct `.from('company_whatsapp')` reads scattered across pages/actions created the current semantic drift.

### Pattern 3: URL-backed admin filters
Parse `searchParams` with Zod, build the Supabase query before `.range()`, preserve filters in pagination links, and return only the selected page. Company/member display data should be fetched only for result IDs or selected filter context.

### Anti-Patterns to Avoid
- Hiding the tenant nav while leaving `/whatsapp` and service-role actions callable.
- Allowing profile/company phone to double as routing authority.
- Using `.maybeSingle()` where duplicate/ambiguous records are possible.
- Filtering after `.limit(500)` in the client.
- Letting admin activation imply user notification consent.
- Dropping old schema in the same step that first introduces new reads.
</architecture_patterns>

<dont_hand_roll>
## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| E.164 parsing/formatting | Ad hoc regex variants in each action | Existing phone normalization helper plus one Zod refinement | Prevents mismatched uniqueness/routing formats |
| Admin authorization | Client role flags or duplicated membership checks | `requireAdmin()` | Existing platform authority boundary |
| Audit records | Console logs | `logAdminAction()` | Durable actor/target/action metadata |
| Filter state | Local-only table state | URL `searchParams` | Shareable, refresh-safe, server-queryable |
| Migration selection | “First member wins” | Owner-role preference plus explicit conflict report | Silent assignment is the original migration hazard |
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: UI-only removal
**What goes wrong:** Direct tenant URLs/actions still expose service-role data.
**How to avoid:** Delete or hard-deny route/action boundaries and add static route/import guards.

### Pitfall 2: Ambiguous phone ownership
**What goes wrong:** `.maybeSingle()` errors or the wrong tenant receives an inbound command.
**How to avoid:** Globally unique active sender index, deterministic migration, explicit conflict state, exact-one resolver.

### Pitfall 3: Breaking outbound send
**What goes wrong:** Removing the tenant inbox accidentally removes shared send primitives or account-active gating.
**How to avoid:** Separate conversation UI/actions from `send-whatsapp` delivery and retain a narrow boolean entitlement/provisioning predicate.

### Pitfall 4: Consent becomes impossible to revoke
**What goes wrong:** Hiding tenant toggles while continuing proactive sends leaves no user control.
**How to avoid:** Force WhatsApp notification resolution off during the transition while retaining historical consent data.

### Pitfall 5: Deployment skew
**What goes wrong:** New code expects tables/columns not yet available, or old code writes columns already removed.
**How to avoid:** Two authored migrations and compatibility reads/writes; contract only after all callers move.
</common_pitfalls>
