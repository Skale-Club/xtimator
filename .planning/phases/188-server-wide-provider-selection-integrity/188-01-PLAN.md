<objective>
Create the one place that decides which storage backend the server uses, and move `getServerStorage()` out of the browser-reachable `lib/storage/index.ts` into it.

Purpose: today `STORAGE_PROVIDER` is read inside `lib/storage/index.ts` — a module six `'use client'` components import. That is both the half-apply bug (only 4 call sites honor it) and a bundling hazard (the AWS SDK + service-role client sit in the client module graph). This plan builds the correct seam. Plans 02 and 03 move the remaining ~19 server call sites onto it.

Output: `lib/storage/server.ts` (new), a stripped `lib/storage/index.ts`, 4 repointed call sites, 1 repointed script, 4 repointed test mocks.

**This plan does NOT activate R2.** No credential goes into `.env.local` or Coolify (Phase 191/192 owns that). The seam is built and proven; it stays dormant because `S3_*` is absent everywhere.
</objective>

Selection matrix for `serverStorageBackend()`. Only the exact strings `'s3'` and `'supabase'` are recognized values of `STORAGE_PROVIDER`; anything else (including empty string and typos) is treated as unset.

| STORAGE_PROVIDER | S3_* complete? | Result |
|---|---|---|
| unset / unrecognized | yes | `'r2'` |
| unset / unrecognized | no  | `'supabase'` |
| `'supabase'`         | yes | `'supabase'` (explicit kill switch wins) |
| `'supabase'`         | no  | `'supabase'` |
| `'s3'`               | yes | `'r2'` |
| `'s3'`               | no  | **throws** — message names the missing var(s) and never silently degrades |

Additional behaviors to test:
- Called with `globalThis.window` defined → throws (`serverStorageBackend`, `getServerStorage`, `serverStorage` all guard).
- `serverStorage(client)` in `'supabase'` mode returns a provider that delegates to **the passed client**, not the service-role client (this is what preserves today's `storage.objects` RLS scoping at user-scoped call sites).
- `getServerStorage()` in `'supabase'` mode uses `requireServiceClient()`.
- Both functions in `'r2'` mode return a provider built from `s3ConfigFromEnv()`, and `serverStorage(client)` ignores the client entirely.
- Partial config (e.g. `S3_ENDPOINT` set, `S3_SECRET_ACCESS_KEY` empty) with `STORAGE_PROVIDER` unset → `'supabase'`, no throw.
- `lib/storage/index.ts` source contains no occurrence of `s3-provider`, `@/lib/supabase/service`, `process.env`, or `STORAGE_PROVIDER` (read the file with `readFileSync` and assert — this is a suite assertion, not a shell grep, so it cannot short-circuit).

Create `lib/storage/server.ts`.

**Hard constraints, in priority order:**

1. **NO `import 'server-only'`.** `scripts/storage-smoke.ts` imports this module and runs under plain `tsx`, where `server-only` throws at import time (same reason `lib/storage/s3-config.ts` omits it — see its docblock). Enforce server-ness at runtime instead: a module-private `assertServer()` that throws when `typeof window !== 'undefined'`, called at the top of every exported function. Plan 04 adds the static import-graph gate that proves no client module reaches this file.

2. **DO NOT modify `lib/storage/s3-provider.ts`.** It is verified working against R2 unmodified. `git diff --stat lib/storage/s3-provider.ts` must be empty at the end of this task.

3. **Every exported function is synchronous.** All ~19 downstream call sites do `const storage = createStorage(supabase)` synchronously; an async seam would force an `await` cascade through server actions, Inngest jobs, and the PDF renderer. Load `./s3-provider` and `@/lib/supabase/service` with lazy `require()` (with the same `// eslint-disable-next-line @typescript-eslint/no-require-imports` the current `getServerStorage()` uses), so the AWS SDK stays off the cold path when Supabase is selected.

4. **Read `S3_*` only through `s3ConfigFromEnv()` from `./s3-config`.** Do not re-inline the env mapping. This closes the duplication that `s3-config.ts`'s docblock item (c) scheduled for this phase — delete the inline copy rather than leaving two.

5. **No caching / no module-level singleton.** Construct the provider per call, exactly as `getServerStorage()` does today. A cached S3 client would survive env changes between tests and would make the reversibility property (constraint 3: pull the env vars, get Supabase) untrue until process restart. If you feel tempted to memoize, don't — the call sites already hoist the factory call out of loops.

Exports:

```typescript
export type StorageBackend = 'r2' | 'supabase'

/** The ONE provider decision for the whole server process. */
export function serverStorageBackend(): StorageBackend

/**
 * Server default provider. Supabase mode uses the service-role client.
 * Replaces the getServerStorage() that used to live in ./index.ts.
 */
export function getServerStorage(): StorageProvider

/**
 * Drop-in replacement for createStorage(client) at SERVER call sites.
 * Supabase mode: byte-identical to createStorage(client) — same client, same
 * RLS scoping. R2 mode: the client argument is ignored.
 */
export function serverStorage(client: SupabaseClient): StorageProvider
```

Write a file header docblock that states, explicitly:

- That `serverStorage(client)` **drops Supabase `storage.objects` RLS in R2 mode**, because an S3 backend has no per-user policy layer. In Supabase mode the passed client's RLS still applies.
