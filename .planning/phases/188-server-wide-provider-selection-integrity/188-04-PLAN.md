<objective>
Build the automated check that fails the build when a server-side module reintroduces a Supabase-only storage path, then prove it can actually fail.

Purpose: PROV-02. Phase 66 shipped a shell `grep` gate that proved there were no raw `supabase.storage.from(...)` calls — and that gate was *green the entire time* the provider seam was rotting, because it asked the wrong question. It never proved the provider was swappable. A census with exact-manifest equality asks the right question: it enumerates every storage call site mechanically and refuses to pass unless each one is explicitly classified.

Output: `tests/unit/storage/storage-seam-census.test.ts` + a corrected `docs/STORAGE-MIGRATION.md`.

Model: `tests/unit/demo/mutation-boundary-sweep.test.ts` (Phase 180). Same shape — mechanical AST discovery, an explicit literal manifest, exact set equality, and a synthetic-rejection test. Read it before you start; reuse its `walk` / `parseModule` / `manifestDiff` / `repoPath` helpers rather than reinventing them.

  <behavior>
Discovery (mechanical — no hand-maintained file list): walk `app/`, `lib/`, `components/`, `hooks/` for `.ts`/`.tsx`, parse each with `ts.createSourceFile`, and for every file record:
- whether its first statement is a `'use client'` directive prologue;
- every call expression named `createStorage`, `serverStorage`, or `getServerStorage`;
- every property-access call matching `.storage.from(...)` (the raw-Supabase escape hatch);
- the module specifiers it imports from (`@/lib/storage`, `@/lib/storage/server`, and relative equivalents).

Emit one census id per (file, symbol) pair, e.g. `components/workspace/photos/photo-card.tsx#createStorage`.

Assertions:

1. **Exact set equality** between discovered ids and `STORAGE_SEAM_MANIFEST` — `{ duplicateManifestIds: [], missing: [], stale: [] }`. This is the load-bearing gate: a new call site anywhere is `missing`, a deleted one is `stale`.

2. Every `server-provider` row's file: calls `serverStorage` or `getServerStorage`, imports from `@/lib/storage/server`, and does **not** call `createStorage`.

3. Every `browser-supabase` row's file: has a `'use client'` directive.

4. **No `'use client'` file imports `@/lib/storage/server`** (direct import specifier check across all discovered files). This is the credential-safety property: the server seam is the only module that touches `S3_*`, and it must never appear in a client module graph.

5. `lib/storage/index.ts` source contains no occurrence of `s3-provider`, `@/lib/supabase/service`, `process.env`, or `STORAGE_PROVIDER` (keeps Plan 01's strip from silently reverting).

6. Zero `.storage.from(` calls in any discovered file except the explicitly exempted ones (`lib/storage/supabase-provider.ts` is the adapter and is the only legitimate holder). This is the Phase-66 STORAGE-03 grep gate, re-expressed as a suite assertion so it cannot short-circuit the way `! grep ...` does under `set -e`.

7. Every `deliberate-supabase` and `browser-supabase` row carries an `authority` string > 12 chars and a `reason` string > 24 chars — copy the discipline from `mutation-boundary-sweep.test.ts`'s exception rows so an exemption cannot be added without writing down why.

8. **Synthetic rejection** (mirrors the sweep's `rejects a synthetic unclassified boundary`): feed `manifestDiff([...discovered, { id: 'lib/actions/synthetic.ts#createStorage', ... }], STORAGE_SEAM_MANIFEST)` and assert the synthetic id appears in `missing`. This proves in-suite that the diff detects an unlisted site.
