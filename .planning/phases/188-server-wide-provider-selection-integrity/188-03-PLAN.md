<objective>
Move the 6 remaining `createStorage(client)` call sites — the read/delivery/cleanup half of the server — onto `serverStorage(client)`.

Purpose: PROV-01, and specifically the readers in the split-brain failure. `lib/estimate/adapters/whatsapp.ts` already honors the flag (it uses `getServerStorage()`), so inbound WhatsApp media would write to R2 today; `lib/pdf/render-estimate-pdf.ts` and `lib/queries/share.ts` are exactly the readers that would then hand out Supabase signed URLs for objects that live in R2 — the silent 404s the field assessment predicted. This plan makes the readers follow the writer.

The two Inngest cleanup jobs matter for a subtler reason: `storage-orphan-cleanup.ts` **lists a bucket and deletes what it finds unreferenced**. Left on Supabase while writes go to R2, it sees an empty-ish Supabase bucket and the real R2 objects go unswept forever; worse, in the reverse direction it could delete live objects. It must resolve the same backend as everything else.

Output: 5 source files converted, up to 2 test files repointed. This plan is **file-disjoint from Plan 02** and runs in parallel with it.

**No R2 activation.** No credential enters `.env.local` or Coolify in this plan.
</objective>

**`lib/inngest/functions/storage-orphan-cleanup.ts` needs one extra beat — read the code before editing.** It walks a bucket via `list()` and deletes unreferenced objects. Two provider differences bite in R2 mode:
1. `isFolder` — the Supabase provider marks folder placeholders; the S3 provider never emits them (S3 has no folder entries). Code that *skips* `isFolder` entries stays correct under S3. Code that *depends on* placeholders existing does not. Verify which it is.
2. `createdAt` — the S3 provider populates only `name`, `size`, `updatedAt`. If the age/orphan heuristic reads `createdAt`, under S3 it will be `undefined` for every object.

Do **not** modify `lib/storage/s3-provider.ts` to fix this (hard constraint — it is verified working against R2 unmodified and this phase does not touch it). Instead:
- If the existing code already falls back from `createdAt` to `updatedAt` (the `ListedObject` docblock says callers "should prefer `updatedAt` and fall back to this field"), it is already S3-safe — state that in the SUMMARY and move on.
- If it is not S3-safe, add the minimal defensive handling **at the call site in this file** (prefer `updatedAt`, treat a missing timestamp as "not old enough to delete" — fail closed, never delete on missing metadata) and cover it with a test case.

A cleanup job that deletes on missing metadata is the worst possible failure mode here; fail-closed is non-negotiable.

Change nothing else — no signature changes, no error-handling rewrites, no unrelated cleanups.
