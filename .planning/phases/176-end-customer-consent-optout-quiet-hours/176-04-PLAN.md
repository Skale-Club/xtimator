Phase 177's `sendSms()`/`sendEmail()` wrapper and Phase 178's agentic `sendCustomerMessage()` will BOTH call this single function before dispatch — this plan's job is to make bypassing it a COMPILE ERROR, not just a code-review convention, and to make its behavior exhaustively correct under TDD, since a bug here is a live legal-compliance bug, not just a UX bug.

Purpose: Twilio's own Advanced Opt-Out is NOT queryable before a send (confirmed HIGH confidence in research) — the suppression check MUST live in Xtimator's own database, checked synchronously, before every attempt. This plan is that check, composed with consent and quiet-hours, gated behind an opaque `SendPermit` so the type system enforces the call order.

```ts
// lib/notifications/customer-send-gate.ts

// Branded/opaque — cannot be constructed outside this module (no exported
// constructor other than assertSendAllowed itself). Phase 177's sendCustomerMessage()
// and Phase 178's agentic send path will type their recipient parameter as
// SendPermit, not a bare clientId — calling the send primitive without first
// calling assertSendAllowed() becomes a TypeScript compile error.
export type SendPermit = {
  readonly __brand: 'SendPermit'
  clientId: string
  channel: 'sms' | 'email'
  grantedAt: string
}

export interface SendGateResult {
  allowed: boolean
  reason?: 'suppressed' | 'no_consent' | 'quiet_hours' | 'unresolvable_timezone' | 'client_not_found'
  permit?: SendPermit // present if and only if allowed === true
}
// 'client_not_found' is an addition beyond research's literal 4-value reason type — a
// defensive fail-closed case for a clientId/companyId pair that doesn't resolve
// to a real row (should not happen in normal call flow, but never silently allow).

export async function assertSendAllowed(
  companyId: string,
  clientId: string,
  channel: 'sms', // widen to 'email' later if email ever needs quiet-hours/consent gating — not this phase
): Promise<SendGateResult>

// Pure, independently-testable — the ONE place Operational Decision #2 (whether
// consent-status 'unknown' defaults to sendable) can be flipped after legal
// sign-off, without touching assertSendAllowed's control flow.
export const UNKNOWN_CONSENT_IS_SENDABLE = false

export function isConsentSendable(
  status: string,
  unknownIsSendable: boolean = UNKNOWN_CONSENT_IS_SENDABLE,
): boolean
// 'granted' -> true always. 'revoked' -> false ALWAYS, regardless of the flag
// (revocation is never silently overridden). 'unknown' -> returns the flag's
// value (false by default = blocked; true = sendable). Any other/unexpected
// status string -> false (fail closed).
```

Composition order (LOAD-BEARING — matches research exactly, do not reorder):
1. Fetch the `clients` row scoped by BOTH `id = clientId` AND `company_id = companyId` (never trust a bare `clientId` without the tenant-scope check — this is the same defense-in-depth the rest of the codebase applies via RLS, except this gate runs via service role so the `company_id` filter must be explicit in the query, not implicit via RLS). Row not found -> `{ allowed: false, reason: 'client_not_found' }`.
2. **Suppression** (cheapest, most legally decisive, single column read): `sms_opted_out_at IS NOT NULL` -> `{ allowed: false, reason: 'suppressed' }`. Checked FIRST, unconditionally — a suppressed client is blocked no matter what consent/quiet-hours would otherwise say.
3. **Consent**: call `isConsentSendable(client.sms_consent_status)`. `false` -> `{ allowed: false, reason: 'no_consent' }`. This is the WIRED version of Operational Decision #2 — `isConsentSendable` is a real branch in the control flow, not a constant sitting unused next to a hardcoded `!== 'granted'` check.
4. **Quiet hours** (time-dependent, so ordered LAST — a retry a few hours later could pass, no point paying the timezone-derivation cost for a client already blocked by #2/#3): call `resolveRecipientZones({ clientState: client.state, clientPhone: client.phone, companyState: company.state })`. `null` -> `{ allowed: false, reason: 'unresolvable_timezone' }`. Otherwise call `isWithinQuietHours(resolution.zones)` -> if `false`, `{ allowed: false, reason: 'quiet_hours' }`.
5. All checks pass -> `{ allowed: true, permit: { __brand: 'SendPermit', clientId, channel, grantedAt: new Date().toISOString() } }`.

The `companies.state` fetch can be a second query (join not required — `clients` doesn't denormalize company state) or a single query with an explicit join via Supabase's `companies(state)` embed syntax, executor's choice; either way, fetch BOTH `clients` and `companies` rows before running the quiet-hours check.

`channel` param on `assertSendAllowed` is accepted but not yet branched on (only `'sms'` is valid this phase) — typed as a literal so a future email-gating decision is a type change, not a silent behavior change. `SendPermit.channel` is typed `'sms' | 'email'` (wider than the gate's current input type) so the permit shape doesn't need to change again the day email gating ships — only `assertSendAllowed`'s parameter type does.
