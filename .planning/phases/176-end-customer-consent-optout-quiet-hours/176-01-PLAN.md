**Part 1 — `clients` new columns** (exact names/types/constraints, per 176-RESEARCH.md's Schema Recommendation):
```sql
ALTER TABLE public.clients
  ADD COLUMN IF NOT EXISTS sms_consent_status TEXT NOT NULL DEFAULT 'unknown'
    CHECK (sms_consent_status IN ('granted', 'revoked', 'unknown')),
  ADD COLUMN IF NOT EXISTS sms_consent_method TEXT,
  ADD COLUMN IF NOT EXISTS sms_consent_text TEXT,
  ADD COLUMN IF NOT EXISTS sms_consent_recorded_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS sms_consent_recorded_by UUID REFERENCES auth.users(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS sms_opted_out_at TIMESTAMPTZ;
```
Add a COMMENT ON COLUMN for `sms_consent_status` and `sms_opted_out_at` explaining: (a) `'unknown'` is NOT the same as `'granted'` — the 176-04 gate treats it as non-sendable by default (fail-closed; Operational Decision #2 from research is deliberately NOT resolved here — flag as deferred, config-driven), (b) `sms_opted_out_at` is the fast/authoritative suppression check, deliberately redundant with `sms_consent_status='revoked'`.

Indexes (both needed — different query patterns):
```sql
-- 176-05's inbound-webhook reverse lookup (From phone -> matching client rows, across companies)
CREATE INDEX IF NOT EXISTS idx_clients_phone ON public.clients(phone) WHERE phone IS NOT NULL;
-- 176-04's pre-send gate hot-path suppression check (partial index — cheap, only suppressed rows)
CREATE INDEX IF NOT EXISTS idx_clients_sms_opted_out ON public.clients(id) WHERE sms_opted_out_at IS NOT NULL;
```

**Part 2 — `client_message_events`** (append-only audit; NEVER updated/deleted, only inserted):
```sql
CREATE TABLE IF NOT EXISTS public.client_message_events (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id          UUID REFERENCES public.companies(id) ON DELETE CASCADE,
  client_id           UUID REFERENCES public.clients(id) ON DELETE SET NULL,
  from_phone          TEXT NOT NULL,
  keyword_type        TEXT NOT NULL CHECK (keyword_type IN ('stop', 'start', 'help', 'other')),
  raw_body            TEXT,
  twilio_message_sid  TEXT NOT NULL,
  received_at         TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
IMPORTANT deliberate deviation from the research doc's literal column table: `company_id` is NULLABLE here (research listed it `uuid` non-null "Tenant scope (RLS)" but also required `client_id nullable ... never drop an inbound event ... log it unresolved rather than discard` — those two requirements conflict when a STOP arrives from a phone number matching NO client anywhere: there is no tenant to attach it to). Resolve the conflict by making `company_id` nullable: a fully-unresolved event gets `company_id = NULL, client_id = NULL`, is still inserted (never dropped), and simply won't be visible to any tenant via RLS (NULL never matches `IN (...)`) — it stays queryable by service-role/support for manual review. When a phone number matches clients in MULTIPLE companies (same end-customer texted more than one of your tenants — plausible, not fabricated), insert ONE row per matched company (fan-out), each with that company's `client_id` — this is correct because CUST-03's dedicated Messaging Service is SHARED platform-wide, so a STOP to that one number is sender-agnostic and must suppress every tenant relationship at that phone number, not just one.

Indexes:
```sql
CREATE INDEX IF NOT EXISTS idx_client_message_events_company_id ON public.client_message_events(company_id);
CREATE INDEX IF NOT EXISTS idx_client_message_events_from_phone ON public.client_message_events(from_phone);
CREATE INDEX IF NOT EXISTS idx_client_message_events_sid ON public.client_message_events(twilio_message_sid);
```
No unique constraint on `twilio_message_sid` (Postgres treats NULLs as distinct so a company_id-inclusive unique index wouldn't dedupe unresolved rows anyway) — 176-05 handles inbound-webhook idempotency at the APPLICATION level (check-then-insert against `idx_client_message_events_sid` before processing), matching the existing WhatsApp webhook's dedup-by-insert precedent in spirit, adapted for the fan-out case.

RLS:
```sql
ALTER TABLE public.client_message_events ENABLE ROW LEVEL SECURITY;

CREATE POLICY "client_message_events_select" ON public.client_message_events FOR SELECT TO authenticated
  USING (company_id IN (SELECT company_members.company_id FROM company_members WHERE company_members.user_id = (SELECT auth.uid())));
```
No INSERT/UPDATE/DELETE policy for `authenticated` — only the service-role webhook writes here (mirrors `estimate_deliveries`'s "status updates are server-side only" precedent).
