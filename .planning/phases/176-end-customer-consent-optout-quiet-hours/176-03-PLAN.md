<objective>
Build CUST-04's platform-wide quiet-hours guard as two composable pure functions: recipient-timezone derivation (state -> area-code -> company-state -> fail-closed) and the 8am-8pm window check itself. Both are pure (no DB access — callers pass in already-fetched strings), independent of 176-01's schema migration, so this plan is Wave 1 (parallel with 176-01/176-02).

CUST-04's "platform-wide guard" wording is satisfied most defensibly by adopting that stricter window everywhere (Operational Decision #3, recommended and adopted here as the shipped default — expressed as named constants, not inline magic numbers, so a future owner/legal decision to change the window doesn't require touching the derivation or comparison logic).
Output: `resolveRecipientZones()` + `isWithinQuietHours()`, fully unit-tested including DST transitions and split-timezone states.

**Design simplification vs. the research doc's literal wording (documented, not silent):** research describes computing the 8am boundary against "whichever zone has the latest clock" and the 8pm boundary against "whichever has the earliest clock" for split-timezone states. This plan achieves the IDENTICAL safety guarantee (never sends outside 8am-8pm in ANY zone the state could be in) with a simpler, more obviously-correct construction: `resolveRecipientZones()` returns an ARRAY of 1+ IANA zone candidates (multiple only for genuinely split states), and `isWithinQuietHours(zones)` returns `true` only if the current instant is independently within [8, 20) local hour in EVERY zone in the array (intersection). A single-zone array behaves exactly like a normal single-timezone check.

```ts
// lib/notifications/timezone-derive.ts
export type ZoneSource = 'client_state' | 'area_code' | 'company_state'
export interface ZoneResolution { zones: string[]; source: ZoneSource }

export function resolveRecipientZones(input: {
  clientState?: string | null
  clientPhone?: string | null
  companyState?: string | null
}): ZoneResolution | null   // null = FAIL CLOSED, no signal resolved
```

Returns a 1-element `zones` array when the NPA is found; unmapped NPA -> tier 3.

Tier 3 — `companyState`: same `STATE_TIMEZONES` lookup as tier 1, applied to the tenant's own `companies.state`.

If none of the three tiers resolve -> return `null` (fail closed — the caller, 176-04's gate, MUST treat `null` as "block the send", never default to ET/UTC/any guess, per research's explicit "guessing wrong is materially worse than a delayed send").

```ts
// lib/notifications/quiet-hours.ts
export const QUIET_HOURS_START_HOUR = 8   // 8:00am local, inclusive
export const QUIET_HOURS_END_HOUR = 20    // 8:00pm local, EXCLUSIVE (research: 8am-8pm)

export function isWithinQuietHours(zones: string[], at: Date = new Date()): boolean
```
Implementation: for each zone in `zones`, compute local hour via `new Intl.DateTimeFormat('en-US', { timeZone: zone, hour: 'numeric', hour12: false }).format(at)` (zero new dependency, matches `lib/utils/format-date.ts`'s existing `Intl.DateTimeFormat` convention — handle the `'24'` midnight edge case Node's `Intl` sometimes returns instead of `'0'`, normalize via `Number(hourStr) % 24`), then check `hour >= QUIET_HOURS_START_HOUR && hour < QUIET_HOURS_END_HOUR`. Return `true` only if ALL zones pass (empty `zones` array -> return `false`, treat as unresolved/fail-closed, defensive even though `resolveRecipientZones` should never produce an empty array).
