**CRITICAL — the Coolify reverse-proxy URL pitfall (`lib/utils/site-url.ts`'s own documented incident):** `new URL(request.url).origin` resolves to the INTERNAL bind address (`https://0.0.0.0:3000`) behind Coolify, not the public domain Twilio actually POSTed to and signed against. Signature verification MUST use the same URL reconstruction the rest of the codebase already uses for exactly this reason:
```ts
import { resolveBaseUrl } from '@/lib/utils/site-url'
const url = `${resolveBaseUrl(request)}/api/webhooks/twilio`
```
Getting this wrong doesn't fail loud — it fails as "every single Twilio webhook rejected in production, silently, forever" (the signature will never match because the URL half of the signing string is wrong). Do not use `request.url` or `request.nextUrl` directly for the signing URL.

No GET handler is needed (unlike the WhatsApp webhook's `hub.challenge` dance) — Twilio has no equivalent verification handshake for a plain "A Message Comes In" webhook.

Request body: Twilio POSTs `application/x-www-form-urlencoded`, NOT JSON (different from the WhatsApp webhook). Read raw text FIRST (`await request.text()`, mirrors WA-01's "raw body before parsing" discipline, though here it's for building the exact param set to sign, not a raw-body hash), then `new URLSearchParams(rawBody)` to get decoded key/value pairs — build a plain `Record<string,string>` from it (via `Object.fromEntries`) for `verifyTwilioSignature`.

Relevant Twilio form fields: `Body` (message text), `From` (E.164 sender), `MessageSid` (dedupe key), `To` (ignore — not needed this phase). `OptOutType` MAY be present (Advanced Opt-Out on a Messaging Service, not yet provisioned — Phase 177) but is NOT required; the keyword classifier (`classifyInboundKeyword(Body)`) is the sole authority this phase, do not branch on `OptOutType`'s presence/absence.

Phone matching (`From` -> `clients.phone`, imperfect by design — `clients.phone` is free text with no enforced format, see 176-01's interfaces note): normalize `From` to digits only, take the last 10, build 3 candidate strings, and match `clients.phone` exactly against any of them:
```ts
const digits = from.replace(/\D/g, '')
const last10 = digits.slice(-10)
const candidates = [`+1${last10}`, `1${last10}`, last10]
const { data: matches } = await svc.from('clients').select('id, company_id').in('phone', candidates)
```
This is a documented, deliberate limitation (misses differently-formatted stored numbers like `"(555) 123-4567"`) — acceptable for v1 per research's explicit tolerance for phone-matching imprecision; the raw event is NEVER dropped regardless (see below), so an unmatched STOP still leaves a full audit trail for manual reconciliation even when the app-level suppression doesn't fire on a specific `clients` row.

Implement the POST handler exactly per the flow above:
1. `await request.text()` -> raw body.
2. `x-twilio-signature` header.
3. `resolveBaseUrl(request) + '/api/webhooks/twilio'` -> the signing URL (see the CRITICAL note in interfaces — do not use `request.url`).
4. `getTwilioConfig()`; if `null` -> 401.
5. Parse raw body via `new URLSearchParams(rawBody)` -> plain params object.
6. `verifyTwilioSignature(url, params, signature, twilio.authToken)`; if `false` -> 401.
7. Extract `Body`, `From`, `MessageSid` from params.
8. Idempotency check against `client_message_events.twilio_message_sid` (service client select, `.limit(1)`); if found -> 200 immediately.
9. `classifyInboundKeyword(Body ?? '')`.
10. Build phone candidates from `From`, query matching `clients` rows (`id, company_id`).
11. If `keyword === 'stop'`: update every matched client's row (`sms_opted_out_at = now, sms_consent_status = 'revoked'`).
    If `keyword === 'start'`: update every matched client's row (`sms_opted_out_at = null, sms_consent_status = 'granted', sms_consent_method = 'explicit_opt_in', sms_consent_recorded_at = now`).
    If `'help'`/`'other'`: no mutation.
12. Insert `client_message_events` — fan-out one row per matched client (or one unresolved row with `client_id`/`company_id` null if zero matches), regardless of keyword type (EVERY inbound event is logged, not just stop/start).
13. Wrap steps 7-12 in try/catch; on error, `console.error` and still return 200 (steps 1-6, the security boundary, are NOT inside this catch — a signature failure must always be a hard 401, never silently swallowed into a 200).
