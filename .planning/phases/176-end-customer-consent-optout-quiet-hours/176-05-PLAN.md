<objective>
Build the inbound Twilio webhook route CUST-03 requires — there is no inbound SMS webhook anywhere in this codebase today (the only Twilio integration is the outbound `sendSms()` primitive). This is the ONE mechanism by which a real STOP/START/HELP reply from an end customer ever reaches Xtimator's own suppression state — Twilio's own carrier-level Advanced Opt-Out block is real but NOT queryable (confirmed HIGH confidence in research), so without this route, `assertSendAllowed()` (176-04) would have no data to ever return `suppressed: true`.

Purpose: close Pitfall 10 (HIGH/legal) — "no end-customer consent/opt-out infra exists today; carrier filtering alone does not discharge the sender's own TCPA obligation."
Output: `POST /api/webhooks/twilio`, fully route-tested against mocked Twilio payloads (no live Twilio number exists yet — Phase 177 provisions it; this route ships fully unit-tested against mocked/forged payloads per research's explicit scope).

**Revision note (plan-checker pass):** Three behavioral fixes: (1) phone matching now uses 176-01's `phone_normalized` generated column (single indexed equality on last-10-digits) instead of a fragile 3-candidate exact-string `.in()` match. (2) START no longer unconditionally sets `sms_consent_status = 'granted'` on every matched row — that would manufacture consent for a client whose status was `'unknown'` (never explicitly granted OR revoked) from a bare carrier-level opt-in keyword, which is not itself an affirmative consent event for a relationship that never had consent recorded. START now only RESTORES `'granted'` where the prior status was `'revoked'` (a true re-opt-in); an `'unknown'` row has its suppression cleared but stays `'unknown'`. (3) Signature/config rejections are now logged (`console.warn`, mirroring the WhatsApp webhook's pattern) instead of silent 401s.
</objective>

Signature verification MUST use the same URL reconstruction the rest of the codebase already uses for exactly this reason:
```ts

const url = `${resolveBaseUrl(request)}/api/webhooks/twilio`
```
Getting this wrong doesn't fail loud — it fails as "every single Twilio webhook rejected in production, silently, forever" (the signature will never match because the URL half of the signing string is wrong). Do not use `request.url` or `request.nextUrl` directly for the signing URL. **Record in the SUMMARY as an operational runbook note:** whatever URL is configured in the Twilio Console as the number's/Messaging Service's "A Message Comes In" webhook MUST byte-match `resolveBaseUrl(request) + '/api/webhooks/twilio'` in production — if `APP_ORIGIN`/`NEXT_PUBLIC_SITE_URL` ever changes, the Twilio Console webhook URL must be updated to match or signature verification silently fails 100% of the time from that point on.

No GET handler is needed (unlike the WhatsApp webhook's `hub.challenge` dance) — Twilio has no equivalent verification handshake for a plain "A Message Comes In" webhook.

Request body: Twilio POSTs `application/x-www-form-urlencoded`, NOT JSON (different from the WhatsApp webhook). Read raw text FIRST (`await request.text()`, mirrors WA-01's "raw body before parsing" discipline, though here it's for building the exact param set to sign, not a raw-body hash), then `new URLSearchParams(rawBody)` to get decoded key/value pairs — build a plain `Record<string,string>` from it (via `Object.fromEntries`) for `verifyTwilioSignature`.

Relevant Twilio form fields: `Body` (message text), `From` (E.164 sender), `MessageSid` (dedupe key), `To` (ignore — not needed this phase). `OptOutType` MAY be present (Advanced Opt-Out on a Messaging Service, not yet provisioned — Phase 177) but is NOT required; the keyword classifier (`classifyInboundKeyword(Body)`) is the sole authority this phase, do not branch on `OptOutType`'s presence/absence.

**Phone matching (`From` -> `clients.phone_normalized`) — REVISED per checker feedback, use the generated column, not exact-string candidates:**
```ts
const digits = from.replace(/\D/g, '')
const last10 = digits.slice(-10)
const { data: matches } = await svc
  .from('clients')
  .select('id, company_id, sms_consent_status')
  .eq('phone_normalized', last10)
```
Note `sms_consent_status` is now selected too — 176-05's START handling (see below) needs each matched row's PRIOR consent status to decide whether to restore `'granted'` or leave `'unknown'` alone. Residual limitation (documented, accepted): international/VOIP numbers with fewer than 10 digits, or two different real customers who happen to share the same last-10-digit sequence across different country codes, won't match correctly — Twilio's own carrier-level Advanced Opt-Out block (once Phase 177 provisions the Messaging Service) remains a backstop even when this app-level match misses, and the raw event is NEVER dropped regardless (an unmatched STOP still gets a full `client_message_events` audit row for manual reconciliation).

**STOP/START mutation semantics — REVISED per checker feedback (START must not manufacture consent):**
- `keyword === 'stop'`: for EVERY matched row, unconditionally `UPDATE clients SET sms_opted_out_at = now(), sms_consent_status = 'revoked' WHERE id = match.id`.
- `keyword === 'start'`: for EVERY matched row, ALWAYS clear suppression (`sms_opted_out_at = null`). Additionally restore consent to `'granted'` (with `sms_consent_method = 'explicit_opt_in'`, `sms_consent_recorded_at = now()`) **ONLY IF** `match.sms_consent_status === 'revoked'` at read time — this is a genuine re-opt-in after a prior explicit opt-out. If `match.sms_consent_status === 'unknown'`, do NOT touch `sms_consent_status`/`sms_consent_method`/`sms_consent_recorded_at` at all — a bare carrier-level "START" keyword is not itself an affirmative consent event for a relationship that never had consent recorded (Operational Decision #2's territory; do not silently resolve it via START). If already `'granted'` (defensive — shouldn't normally co-occur with `sms_opted_out_at` set, but not impossible), leave `sms_consent_status` untouched, only clear suppression.
- `keyword === 'help' | 'other'`: no `clients` mutation at all (Operational Decision #4).

This means STOP and START are both per-row updates (not a single batched `.in('id', ids)` update), since START's payload depends on each row's prior `sms_consent_status`.
