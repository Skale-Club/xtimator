# Phase 151 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Per 151-CONTEXT.md, this phase is almost entirely plumbing/security. There are exactly **two** UI surfaces in scope:
1. `SupportModeBanner` — a new fixed banner rendered in `app/(app)/layout.tsx` while a Support Mode session is active.
2. A "Support Mode →" row action on the Companies admin list (Phase 150's table), next to the existing "Configure →" link.

No new design language is introduced. Every token, color, and copy pattern below is copied verbatim from existing code (`components/demo/demo-banner.tsx`, `app/admin/layout.tsx`'s inline banner, `app/admin/companies/page.tsx`'s row actions, `app/admin/companies/handoff-button.tsx`). Where 151-CONTEXT.md left something to "Claude's discretion," this document makes the final call and locks it — no open visual questions remain for planning or execution.

## Typography

This phase's own typography budget covers **one new component only — `SupportModeBanner`** — and stays within **2 weights**, reused from the existing global type scale (`app/globals.css`); no new sizes or weights are introduced:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Banner body text | 14px (`text-sm`) | 400 (normal) | 20px (`--line-height-sm`, 1.43) |
| Banner exit CTA | 14px (`text-sm`) | 600 (semibold) + underline | 20px |

**Weights in active use for this phase's design contract: 2 — 400 (body) and 600 (exit CTA).**

Rationale: `DemoBanner` uses `text-sm` (14px/400) for body copy and `font-semibold underline` for its inline CTA. `SupportModeBanner` mirrors this exactly — the exit CTA's `font-semibold` (600) is a hard-locked requirement from 151-CONTEXT.md (it must match `DemoBanner`'s `exitDemoToSignup` button verbatim), so it is not weakened to a lighter weight for the sake of a lower weight count. The admin-side "Super Admin Mode" banner in `app/admin/layout.tsx` instead uses `text-xs font-medium` — that pattern is NOT copied for the tenant-side banner (151-CONTEXT.md specifies mirroring `DemoBanner`'s shape, not the admin banner's type scale; the admin banner's icon/color-family is what carries over, not its smaller type size).

**Footnote — Companies-list row action label (not part of this phase's typography budget):** The row action reuses `text-xs font-medium` (500), the pre-existing convention already shipped by Phase 150 for the "Configure →" and "Hand off" row links on the same table. This is an *inherited* sibling pattern this phase's row action sits next to and matches for consistency — it is not a new typographic choice introduced by Phase 151, and Phase 150 already owns that convention. Because it is inherited rather than authored here, it is excluded from this phase's declared weight count; the two weights this phase actually introduces/locks are 400 and 600, both scoped to `SupportModeBanner`.

## Color

Reused entirely from existing semantic tokens (`--primary`, `--muted-foreground`) — no new colors introduced. This phase does not touch the 60/30/10 page-level color split (it adds a banner strip and a text-link row action, not a new page), so this section documents role usage rather than a fresh dominant/secondary/accent split:

| Role | Value | Usage |
|------|-------|-------|
| Banner surface | `bg-primary/10` (i.e., `hsl(var(--primary) / 0.1)`) | `SupportModeBanner` background — copied verbatim from `DemoBanner`'s `bg-primary/10` |
| Banner border | `border-primary/20` | `SupportModeBanner` bottom border — copied verbatim from `DemoBanner` |
| Banner icon + CTA | `text-primary` (icon), inherited `text-foreground` (body text), `font-semibold underline` (CTA button, no separate color — matches `DemoBanner`'s CTA which relies on underline + weight, not a distinct color) | `ShieldCheck` icon tint; exit CTA emphasis |
| Row action (Support Mode entry) | `text-primary` (via `text-[hsl(var(--primary))]`, matching "Configure →"'s existing class) | The new "Support Mode →" link text/icon on the Companies list |
| Accent (10%) | `--primary` | Reserved for: the `ShieldCheck` icon in the banner, the exit-CTA underline emphasis, and the "Support Mode →" row-action link text/icon. Not used anywhere else in this phase's surfaces. |
| Destructive | `--destructive` | Not used — entering/exiting Support Mode is not a destructive action (see Copywriting Contract below) |

Accent reserved for: `ShieldCheck` icon in `SupportModeBanner`, the banner's "Exit Support Mode" CTA text emphasis, and the "Support Mode →" row-action icon/link on the Companies list. No other element in this phase's two surfaces uses the accent color.

**Icon choice (locked, resolving 151-CONTEXT.md's "Claude's discretion"):** `ShieldCheck` — for visual continuity with the existing `/admin` "Super Admin Mode" banner (`app/admin/layout.tsx` line 5/51), which already uses `ShieldCheck` for the exact same "elevated/audited access" semantic. Using the same icon on both the admin-side and tenant-side banners lets a screenshot or support ticket immediately read as "this is the admin-support-mode icon" regardless of which side of the app it appears on. `Eye` (used by `DemoBanner`) is reserved for the read-only-demo semantic and must not be reused here — the two concepts (public demo vs. audited admin impersonation) must stay visually distinguishable even though they share the same banner shape.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Banner copy (locked, resolving 151-CONTEXT.md's "something like" placeholder) | `Support Mode — viewing {companyName} as {adminEmail}.` followed by inline button `Exit Support Mode` |
| Row action label (Companies list) | `Support Mode →` (mirrors the existing `Configure →` arrow-suffix convention on the same row) |
| Row action icon | `Eye` — chosen specifically to be visually distinct from `HandoffButton`'s `Send` icon and `Configure →`'s plain text link (no icon), so an admin scanning the row cannot mistake "view as tenant" for "invite this prospect" (Send) or "edit AI override" (bare text). Note: `Eye` here labels the *entry-point link on the admin list*, not the banner — the banner itself uses `ShieldCheck` per the icon-continuity rule above. There is no collision risk since these two icons never render in the same view. |
| Primary CTA (banner exit) | `Exit Support Mode` — inline `<button>` inside a `<form action={endSupportSession}>`, styled `font-semibold underline underline-offset-2 hover:no-underline` (verbatim from `DemoBanner`'s CTA button classes) |
| Empty state | Not applicable — this phase has no list/empty-data surface. The Companies list's empty state ("No companies found.") is Phase 150's existing contract and is unchanged by this phase. |
| Error state (start fails — e.g., company not found, admin re-verification fails) | Toast: `Couldn't start Support Mode. {reason if safe to show, else "Please try again."}` — mirrors the existing toast pattern in `HandoffButton` (`toast.error(result.error)`). Use `sonner`'s `toast.error()`, consistent with the codebase's existing error-toast convention. |
| Error state (session expires mid-view) | No blocking error — per 151-CONTEXT.md, `getSupportModeSession()` returning `null` simply falls through to normal (non-impersonated) resolution. If that leaves the admin with no real company membership, the existing `app/(app)/layout.tsx` `redirect('/onboarding')` fallback applies unchanged — no new error copy needed. |
| Destructive actions | **None in this phase.** Entering or exiting Support Mode is reversible, read-only, and fully audit-logged — it is not classified as destructive and requires no confirmation dialog. This matches 151-CONTEXT.md's framing of Support Mode as a "view-only capability," not a data-mutating or identity-altering action. |

## Component Inventory (executor reference)

**`SupportModeBanner` (new component, `components/admin/support-mode-banner.tsx` suggested path):**
- Shape: single fixed bar, full-width, centered content — copy `components/demo/demo-banner.tsx` verbatim structurally.
- Classes: `flex items-center justify-center gap-2 border-b border-primary/20 bg-primary/10 px-4 py-2 text-sm text-foreground`
- Icon: `<ShieldCheck className="h-4 w-4 shrink-0 text-primary" />`
- Body: `<span className="text-center">Support Mode — viewing <strong>{companyName}</strong> as {adminEmail}. </span>`
- Exit CTA: `<form action={endSupportSession} className="inline"><button type="submit" className="font-semibold underline underline-offset-2 hover:no-underline">Exit Support Mode</button></form>`
- Placement in `app/(app)/layout.tsx`: render in the same position as `{isDemo && <DemoBanner />}` — i.e., directly below `MobileHeader`, above `<main>`. If both a Support Mode session AND a demo/trial banner condition could theoretically overlap, Support Mode takes precedence (a super admin is never viewing their own demo/trial state while impersonating) — render only `SupportModeBanner` when a valid support session exists, skip `DemoBanner`/`TrialBanner` checks entirely in that branch.
- Company switcher suppression: pass no `memberships` (or an explicit empty array) to `Sidebar` while in Support Mode, per 151-CONTEXT.md decision #3 — this is a plumbing change, not a new visual state; `Sidebar`'s existing "no switcher" rendering path (when memberships is empty) is reused as-is.

**Companies-list row action (extends Phase 150's table, `app/admin/companies/page.tsx` today):**
- Sits in the same right-aligned actions cell as `HandoffButton` and "Configure →", in this left-to-right order: `HandoffButton` (demo rows only) → **Support Mode →** (new) → `Configure →`.
- Markup pattern (mirrors "Configure →"'s existing `<Link>` styling, adapted to a form-submit action since starting Support Mode is a server action, not a navigation):
  `<form action={startSupportSessionAction}><input type="hidden" name="companyId" value={c.id} /><button type="submit" className="inline-flex items-center gap-1 text-xs text-[hsl(var(--primary))] hover:underline font-medium"><Eye className="h-3 w-3" />Support Mode →</button></form>`
  Note on `font-medium`: this class is carried over verbatim from Phase 150's existing "Configure →" row action for visual consistency within the same table row — see the Typography footnote above.
- On success, the server action redirects to `/dashboard` (per 151-CONTEXT.md) — no client-side toast needed on the happy path since the redirect itself (into the tenant view with the banner visible) is the confirmation.
- On failure, catch and surface via `toast.error(...)` exactly as `HandoffButton` does — this requires the row action to be a small client component wrapper (`'use client'`) if `useTransition`/toast feedback is desired, mirroring `HandoffButton`'s structure; otherwise a plain server-action form with `redirect()`-or-throw is acceptable given the low complexity. Executor's discretion on client-vs-server-component split, but the visual result (icon + "Support Mode →" text, `text-xs font-medium`, primary color) is locked.
