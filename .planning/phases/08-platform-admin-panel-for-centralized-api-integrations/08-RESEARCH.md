## Summary

Phase 8 moves the platform from env-var-coupled secrets and hardcoded identity strings to a DB-backed, admin-editable configuration layer. The technical surface area is narrow but security-sensitive: **(a)** correct AES-256-GCM encryption/decryption, **(b)** a tamper-proof super-admin gate that fails closed with 404, and **(c)** a loader with a hot path that is called on every server action / API route.

Three forces drive the design decisions:

1. **Vercel's serverless model** — warm invocations share an in-memory cache; cold starts repopulate from DB. A 60s TTL is the right default and will produce at most 1 DB round-trip per 60s per warm instance per key.
2. **Next.js 16's rename** — `middleware.ts` → `proxy.ts` (already in place in this repo). The proxy runs on the **Node.js runtime by default in Next 16** — this is what unlocks the super-admin DB lookup in `proxy.ts` without calling out to a Route Handler. This is a critical enabler for D-07.
3. **Supabase's custom access token hook** is the fastest membership-check mechanism, but it requires the hook SQL function to be live before the first admin logs in. Simpler path: plain service-role DB lookup in proxy, cached per-request. JWT-claim optimisation is an optional Phase 8.1 enhancement, not required for v1.

**Primary recommendation:** Build the simplest correct path first: DB lookup in proxy with per-request memoisation (no JWT-claim hook), AES-256-GCM with `crypto` stdlib and explicit 12-byte IV per row, and a module-level cache object keyed by `updated_at`. Defer the JWT-claim optimisation.

## Key Patterns

### 1. Node AES-256-GCM (crypto stdlib) — reference implementation

**Key facts (verified against Node.js v25 docs, NIST SP 800-38D):**
- Use a **12-byte (96-bit) random IV per encryption** — NIST recommends 96 bits for GCM, and Node's `createCipheriv` enforces valid length.
- **Never reuse an (IV, key) pair.** Reuse compromises confidentiality and authenticity immediately.
- Use `crypto.randomBytes(12)` for IV; `crypto.randomBytes` is CSPRNG.
- Authentication tag is 16 bytes (default). Retrieve via `cipher.getAuthTag()` and store alongside ciphertext.
- On decrypt, `decipher.setAuthTag(tag)` MUST be called before `decipher.final()`; if the tag mismatches, `final()` throws — this is the integrity check.
- Key must be **32 bytes (256 bits)** raw. Decode `APP_ENCRYPTION_KEY` with `Buffer.from(process.env.APP_ENCRYPTION_KEY, 'base64')` and assert `buffer.length === 32` at module load.

**Reference `lib/crypto/aes.ts` (HIGH confidence):**

```ts
// Source: Node.js crypto stdlib docs (https://nodejs.org/api/crypto.html),
// rjz/AndiDittrich canonical examples, verified 2026-04.
import { randomBytes, createCipheriv, createDecipheriv } from 'node:crypto'

const ALGO = 'aes-256-gcm' as const
const IV_LEN = 12   // 96 bits — NIST recommendation for GCM
const TAG_LEN = 16  // 128 bits

function loadKey(): Buffer {
  const raw = process.env.APP_ENCRYPTION_KEY
  if (!raw) throw new Error('APP_ENCRYPTION_KEY is not set')
  const key = Buffer.from(raw, 'base64')
  if (key.length !== 32) {
    throw new Error(
      `APP_ENCRYPTION_KEY must decode to 32 bytes (256 bits); got ${key.length}. Generate with: openssl rand -base64 32`
    )
  }
  return key
}

export type EncryptedBlob = {
  ciphertext: Buffer
  iv: Buffer         // 12 bytes
  authTag: Buffer    // 16 bytes
}

export function encrypt(plaintext: string): EncryptedBlob {
  const key = loadKey()
  const iv = randomBytes(IV_LEN)
  const cipher = createCipheriv(ALGO, key, iv, { authTagLength: TAG_LEN })
  const ciphertext = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()])
  const authTag = cipher.getAuthTag()
  return { ciphertext, iv, authTag }
}

export function decrypt(blob: EncryptedBlob): string {
  const key = loadKey()
  if (blob.iv.length !== IV_LEN) throw new Error('invalid iv length')
  if (blob.authTag.length !== TAG_LEN) throw new Error('invalid auth tag length')
  const decipher = createDecipheriv(ALGO, key, blob.iv, { authTagLength: TAG_LEN })
  decipher.setAuthTag(blob.authTag)
  const plaintext = Buffer.concat([decipher.update(blob.ciphertext), decipher.final()])
  return plaintext.toString('utf8')
}
```

**Key loading:** `loadKey()` runs per-call. Node caches the buffer via module closure if desired, but per-call is fine (Buffer.from on a 44-char base64 string is nanoseconds).

**Rotation procedure (document in README + `supabase/ADMIN-BOOTSTRAP.md`):**
1. Generate new key: `openssl rand -base64 32`.
2. Temporarily dual-read: loader tries new key first, falls back to old key on GCM auth-tag failure.
3. Admin hits a `/admin/rotate-keys` server action that decrypts every row with old key and re-encrypts with new key.
4. Verify all rows decrypt with new key; remove old key from env.

Plan can defer rotation UI to a later phase; v1 documents the manual SQL path.

### 2. Super-admin gate in `proxy.ts` (Next.js 16)

**Key facts (verified against Next.js 16.2 proxy docs):**
- Next.js 16 renamed `middleware.ts` → `proxy.ts`. This repo is already on the new convention (`proxy.ts` at root, `lib/supabase/proxy.ts` as helper). Confirmed via `next@16.2.3` in package.json.
- **Proxy defaults to Node.js runtime in Next 16** (stable in 15.5). The `runtime` config option is forbidden in proxy and throws. This is the key enabler — service-role Supabase queries work out of the box.
- Proxy runs **before** filesystem routes. An admin-path match + negative membership → rewrite to a not-found page (produces a 404 without revealing the admin surface — satisfies D-07).
- **Critical gotcha from the docs:** "Server Functions are not separate routes... A matcher change or a refactor that moves a Server Function to a different route can silently remove Proxy coverage. Always verify authentication and authorization inside each Server Function rather than relying on Proxy alone."

**Reference pattern (recommended in this repo):**

```ts
// proxy.ts — composed from existing auth gate + new admin gate
import { type NextRequest, NextResponse } from 'next/server'
import { updateSession } from '@/lib/supabase/proxy'
import { checkPlatformAdmin } from '@/lib/supabase/admin-gate'

export async function proxy(request: NextRequest) {
  const response = await updateSession(request)  // existing auth
  if (response.status >= 300 && response.status < 400) return response

  const { pathname } = request.nextUrl
  if (pathname.startsWith('/admin')) {
    const isAdmin = await checkPlatformAdmin(request)
    if (!isAdmin) {
      // 404, NOT 403 (D-07): don't reveal /admin exists
      return NextResponse.rewrite(new URL('/404', request.url))
    }
  }
  return response
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)'],
}
```

```ts
// lib/supabase/admin-gate.ts — new helper
import { createServerClient } from '@supabase/ssr'
import { createServiceClient } from '@/lib/supabase/service'
import type { NextRequest } from 'next/server'

export async function checkPlatformAdmin(request: NextRequest): Promise<boolean> {
  // 1. Get user id from the SSR cookie session
  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    { cookies: { getAll: () => request.cookies.getAll(), setAll: () => {} } }
  )
  const { data } = await supabase.auth.getClaims()
  const userId = data?.claims?.sub
  if (!userId) return false

  // 2. Look up platform_admins membership using service role (bypass RLS)
  const svc = createServiceClient()
  const { data: row } = await svc
    .from('platform_admins')
    .select('user_id')
    .eq('user_id', userId)
    .maybeSingle()
  return !!row
}
```

**Belt-and-braces layout gate** (per P-01, D-07, and Next docs warning):

```ts
// app/(admin)/layout.tsx
import { notFound } from 'next/navigation'
import { cache } from 'react'
import { createClient } from '@/lib/supabase/server'
import { createServiceClient } from '@/lib/supabase/service'

const getAdminContext = cache(async () => {
  const supabase = await createClient()
  const { data } = await supabase.auth.getClaims()
  const userId = data?.claims?.sub
  if (!userId) return null
  const svc = createServiceClient()
  const { data: row } = await svc.from('platform_admins').select('user_id').eq('user_id', userId).maybeSingle()
  return row ? { userId } : null
})

export default async function AdminLayout({ children }: { children: React.ReactNode }) {
  const ctx = await getAdminContext()
  if (!ctx) notFound()
  return <div data-theme="admin-dark">{children}</div>
}
```

`cache()` is React's per-request memoisation; it deduplicates the DB lookup when layout + nested server components + server actions all call `getAdminContext()` in one render.

### 3. Supabase custom access token hook (optional optimisation — NOT required for v1)

Documented for completeness; **planner should NOT include this in the phase 8 plan** (complexity >> benefit for a single-user platform admin).

```sql
create or replace function public.custom_access_token_hook(event jsonb)
returns jsonb language plpgsql as $$
declare
  claims jsonb;
  is_admin boolean;
begin
  select exists(select 1 from public.platform_admins where user_id = (event->>'user_id')::uuid)
    into is_admin;
  if is_admin then
    claims := event->'claims';
    if jsonb_typeof(claims->'app_metadata') is null then
      claims := jsonb_set(claims, '{app_metadata}', '{}');
    end if;
    claims := jsonb_set(claims, '{app_metadata, is_platform_admin}', 'true');
    event := jsonb_set(event, '{claims}', claims);
  end if;
  return event;
end;
$$;

grant all on table public.platform_admins to supabase_auth_admin;
revoke all on table public.platform_admins from authenticated, anon, public;
```

Then enable in Dashboard → Authentication → Hooks → Custom Access Token → select this function.

**Tradeoff:** Saves one DB round-trip per admin request, but requires user re-login on add/remove (JWT is signed at login, not on claim change), and introduces a second source of truth. For ≤5 admins on a single-tenant admin panel, the extra 2ms per request is irrelevant. Defer.

### 4. Next.js 16 route groups — `(admin)` alongside `(app)`, `(auth)`

**Key facts (verified against Next.js 16.2 docs):**
- Route groups are parentheses-wrapped directories that **do not appear in the URL**. `app/(admin)/integrations/page.tsx` → `/admin/integrations`. Wait — route groups DO NOT add a URL segment. To get `/admin/*` you need `app/admin/` (no parens) OR `app/(admin)/admin/...`.
- Convention in this repo: `app/(app)/dashboard/...` → `/dashboard` (no `(app)` prefix). That means for `/admin/*` we need **`app/admin/` as a real folder** with its own `layout.tsx` acting as the admin shell. We can wrap it in a route group `app/(admin)/admin/` if we want a separate root layout without touching `app/layout.tsx`, but for this phase a plain `app/admin/layout.tsx` is sufficient.
- Each route group can have its own `layout.tsx`. No metadata inheritance gotchas — metadata composes normally.
- Proxy matcher is a regex over URL paths; it does not know about route groups. Use `pathname.startsWith('/admin')` as the trigger.

**Recommended structure:**
```
app/
  (admin)/                       ← route group (optional — lets us skip root layout)
    admin/
      layout.tsx                 ← admin-only shell + gate re-check
      integrations/page.tsx      → /admin/integrations
      branding/page.tsx          → /admin/branding
      admins/page.tsx            → /admin/admins
      not-found.tsx              ← optional custom 404 (but plain Next 404 is fine)
```

Or simpler (skip route group):
```
app/
  admin/
    layout.tsx
    integrations/page.tsx
    branding/page.tsx
    admins/page.tsx
```

Both work. The simpler version is fine; the route group adds value only if we want a separate root layout (e.g., no `ThemeProvider`). Planner's call — recommend the simpler form.

### 5. In-memory cache on Vercel serverless

**Key facts (verified against Vercel docs):**
- A warm Vercel Function **preserves memory across invocations** on the same instance. Module-scoped variables persist; cold starts reinitialise them.
- Cold-start frequency depends on traffic. For admin config loaded on every tenant request, a warm instance dominates — expect <1% cold starts on paid plans.
- Fluid compute (Vercel's 2025 default) allows **in-function concurrency**, meaning the same instance handles multiple overlapping invocations — the cache is **shared across concurrent requests**. This means the cache must be concurrency-safe. A plain object is safe if writes are atomic (assignment is atomic in JS); the simplest idiom works.
- DB round-trip on cold start (1 per 60s worst case) is **cheap**: Supabase RPC + single-row SELECT is <20ms.

**Reference `lib/platform-config.ts`:**

```ts
import 'server-only'  // harden: prevents accidental client import
import { createServiceClient } from '@/lib/supabase/service'
import { decrypt } from '@/lib/crypto/aes'

type Branding = {
  appName: string
  logoUrl: string | null
  primaryColor: string | null
  emailFromName: string | null
}

let brandingCache: { value: Branding; fetchedAt: number } | null = null
const integrationCache = new Map<string, { value: string; fetchedAt: number }>()
const TTL_MS = 60_000

export async function getBranding(): Promise<Branding> {
  const now = Date.now()
  if (brandingCache && now - brandingCache.fetchedAt < TTL_MS) return brandingCache.value
  const svc = createServiceClient()
  const { data, error } = await svc.from('platform_branding').select('*').eq('id', 1).single()
  if (error || !data) {
    // Null-safe fallback so pages don't crash during first deploy before seed runs.
    const fallback: Branding = { appName: 'Xtimator', logoUrl: null, primaryColor: null, emailFromName: null }
    brandingCache = { value: fallback, fetchedAt: now }
    return fallback
  }
  const branding: Branding = {
    appName: data.app_name,
    logoUrl: data.logo_url,
    primaryColor: data.primary_color,
    emailFromName: data.email_from_name,
  }
  brandingCache = { value: branding, fetchedAt: now }
  return branding
}

export async function getIntegrationKey(provider: 'resend' | 'anthropic' | 'openai'): Promise<string | null> {
  const now = Date.now()
  const cached = integrationCache.get(provider)
  if (cached && now - cached.fetchedAt < TTL_MS) return cached.value

  const svc = createServiceClient()
  const { data } = await svc
    .from('platform_integrations')
    .select('ciphertext, iv, auth_tag')
    .eq('provider', provider)
    .maybeSingle()

  if (!data) {
    // Fallback: env var (D-16). Warn once per process.
    const envKey = process.env[`${provider.toUpperCase()}_API_KEY`]
    if (envKey) {
      console.warn(`[platform-config] Falling back to env var ${provider.toUpperCase()}_API_KEY for provider ${provider}`)
      integrationCache.set(provider, { value: envKey, fetchedAt: now })
      return envKey
    }
    return null
  }

  try {
    const plaintext = decrypt({
      ciphertext: Buffer.from(data.ciphertext),
      iv: Buffer.from(data.iv),
      authTag: Buffer.from(data.auth_tag),
    })
    integrationCache.set(provider, { value: plaintext, fetchedAt: now })
    return plaintext
  } catch (e) {
    console.error(`[platform-config] Failed to decrypt ${provider} key; check APP_ENCRYPTION_KEY`, e)
    return null
  }
}

export function invalidatePlatformConfig() {
  brandingCache = null
  integrationCache.clear()
}
```

The `'server-only'` import at the top is a cheap safety net: if a client component ever imports this module, the build fails — preventing key leak via client bundle.

### 8. Migration strategy for removing env vars

**Rollout order (lowest-risk):**

1. **Wave 1 (schema + loader):** Deploy migration + `lib/platform-config.ts` + `lib/crypto/aes.ts` + admin gate. Loader reads from DB first; falls back to `process.env.*_API_KEY` if DB row is null. `APP_ENCRYPTION_KEY` set in Vercel prod. Existing env-var-coupled code paths unchanged.
2. **Wave 2 (admin UI):** Build `/admin/{integrations,branding,admins}`. Admin logs in, configures each key (Resend, Anthropic, OpenAI) via UI — loader reads from DB from that moment forward.
3. **Wave 3 (usage migration):** Swap the 5 `process.env.*_API_KEY` call sites to `await getIntegrationKey(...)` + the 7 `"Xtimator"` hardcode sites to `await getBranding()`. Verify app still works end-to-end.
4. **Wave 4 (env var deprecation):** Keep env vars in Vercel/`.env.example` marked as "optional dev fallback". Do NOT remove them — they're the escape hatch for local dev where the admin UI isn't populated. Log a warning when the fallback fires.

Phases 1–3 can live in one plan; Phase 4 is documentation.

**Turbopack env-var caching (R-01 below):** `process.env.*` is replaced at build time by Turbopack for client components. Our code only reads these env vars **server-side**, so the build-time replacement is not a concern here — but assert this in a test to prevent future drift.

### 9. Test strategies for encrypted-at-rest secrets

**Unit tests (no DB):**
- `tests/unit/crypto.aes.test.ts`: roundtrip `encrypt(plaintext)` → `decrypt(blob)` equals `plaintext`. Use a fixed 32-byte test key injected via `process.env.APP_ENCRYPTION_KEY`.
- Tamper tests: flip a byte in ciphertext → `decrypt` throws. Flip a byte in authTag → throws. Wrong IV length → throws.
- Key-length tests: 16-byte key → `loadKey()` throws with actionable error message.

**Integration tests (seeded DB):**
- Provide a test-only `APP_ENCRYPTION_KEY` in CI env (different from prod).
- Insert a `platform_integrations` row with known ciphertext produced by the test key.
- Call `getIntegrationKey('resend')` → asserts exact plaintext.
- Assert loader cache hit: two calls → one DB round-trip (mock Supabase client to count calls).

**Snapshot tests (optional):** one-row golden file with ciphertext/iv/authTag. Only useful if you want to catch accidental encryption-scheme drift; skip for v1.

**Running E2E Playwright against admin pages:**
- Seed test DB with `platform_admins(user_id = <test-user-uuid>)` in `tests/setup/seed-admin.ts`.
- Log in as test user, navigate to `/admin/integrations`, fill form, assert persistence.
- **Do NOT use production Resend/Anthropic/OpenAI keys in Test-button tests.** Stub the fetch in e2e, or mark it `skip` in CI.

### 10. Identify pitfalls specific to this scope

See §Risks & Pitfalls below — 10 concrete risks enumerated.

## Risks & Pitfalls

### R-01: Turbopack / Next build-time env replacement
**What:** Next.js inlines `process.env.*` into client bundles at build time. If the loader is accidentally imported into a client component, the compiled output contains `process.env.APP_ENCRYPTION_KEY` literally — but more importantly, the build may fail or the env var may be `undefined` at runtime.
**Prevention:** Add `import 'server-only'` at the top of `lib/platform-config.ts` AND `lib/crypto/aes.ts`. The Next.js build fails fast if a client component imports either.
**Detection:** Unit test asserts `server-only` import exists. Grep test asserts no `'use client'` file imports the loader.

### R-02: IV reuse (catastrophic for AES-GCM)
**What:** Using the same (IV, key) pair twice breaks GCM's authenticity and confidentiality. Developer mistakes: hardcoding an IV constant; caching and reusing an IV across saves; deriving IV from a counter that resets.
**Prevention:** `crypto.randomBytes(12)` on every `encrypt()` call, freshly per row. Never store a "default IV" or "IV template."
**Detection:** Unit test: encrypt the same plaintext twice → the two IVs are different; the two ciphertexts are different.

### R-03: Service role leak via RSC serialisation
**What:** A Server Component calls `getIntegrationKey('resend')` → the decrypted string becomes part of the React Server Component payload and is shipped to the browser. Or a Server Action returns the key accidentally.
**Prevention:** The loader's return value MUST only be passed to SDK constructors server-side, never to a client component prop, never returned from a server action, never placed in `Response.json(...)`. Code review checklist + a grep test that the loader is only imported from `app/api/**`, `lib/actions/**`, and `lib/**` server modules.
**Detection:** Add a lint rule or a unit test: for each call site of `getIntegrationKey`, the enclosing function must be marked `'use server'` or live under `app/api/`. Simpler heuristic: no React component file (`.tsx`) may assign the return value to a JSX prop.

### R-04: Null-branding crash
**What:** `getBranding()` returns a row where `app_name` is null or undefined on first boot (before seed runs, or after a bad migration). Every page that renders `<title>{branding.appName}</title>` crashes server-side with a confusing error.
**Prevention:** Loader returns a **non-null fallback** (see §Key Pattern 5). Seed migration creates the singleton row (P-10).
**Detection:** Unit test for loader returns fallback when Supabase query errors. Integration test: delete the row, call `getBranding()`, get fallback.

### R-05: Admin gate bypass via Server Function matcher drift
**What:** Proxy matcher excludes `/api/*`. A future developer adds an admin-only API route under `/api/admin/...` — the proxy doesn't run, so there's no admin check. The Next.js 16 docs flag this as a common issue.
**Prevention:** Every `/api/admin/*` route handler must start with `await requireAdmin()` from `lib/auth/admin-gate.ts`. Layout gate (P-01c) catches page routes but not API routes.
**Detection:** Unit test: grep all files under `app/api/admin/` for a `requireAdmin()` call in the first 10 lines.

### R-06: Middleware/proxy loop on 404 rewrite
**What:** `NextResponse.rewrite(new URL('/404', ...))` can trigger another proxy invocation on `/404`, which might re-check admin membership and rewrite again. Infinite loop.
**Prevention:** Matcher excludes `/404` explicitly, OR the admin check returns `NextResponse.next()` (not rewrite) when pathname === `/404`.
**Detection:** Smoke test: hit `/admin/integrations` unauthenticated → single redirect, no hang.

### R-07: Loader cache stale after admin edit
**What:** Admin changes the Resend key via UI. The running serverless instance still has the old key in its 60s cache. Next email send uses the old key and fails.
**Prevention:** Admin server actions call `invalidatePlatformConfig()` after upsert (P-05). This clears the in-process cache — but ONLY on the instance that ran the server action. Other warm instances still have stale data for up to 60s.
**Detection:** Acceptable for a low-volume platform admin (changes happen rarely; 60s is the documented TTL). Document the constraint. Rotation protocol accounts for it.
**Alternative:** Drop cache TTL to 5s for keys; keep 60s for branding. Branding changes even rarer.

### R-08: Bootstrap chicken-and-egg
**What:** `/admin/admins` requires platform admin to access; there's no way to create the first admin from the UI.
**Prevention (already decided, D-06):** One-time SQL in Supabase SQL editor: `INSERT INTO platform_admins (user_id) VALUES ('<your-auth-uid>')`. Document in `supabase/ADMIN-BOOTSTRAP.md` with step-by-step (how to find your auth uid in the Supabase dashboard).
**Detection:** Boot script or README assertion.

### R-09: Cascading logo-URL nullability glitch
**What:** `logo_url` is nullable. Components that do `<Image src={branding.logoUrl} />` crash when null (empty-string src throws a Next Image warning; null throws a TS error at runtime with strict mode).
**Prevention:** Always branch: `{branding.logoUrl ? <Image src={branding.logoUrl} ... /> : <LogoSvgFallback />}`. Use the existing placeholder SVG in `components/auth/auth-card.tsx:13-24` as the fallback component.
**Detection:** Unit test each branded component with `logoUrl: null`.

### R-10: Google OAuth redirect vs dark auth layout
**What:** After Google OAuth, user lands on `/auth/callback`, which currently has no custom layout. If callback flashes a light-mode page before the redirect to dashboard/admin, UX is jarring.
**Prevention:** `/(auth)/callback/page.tsx` inherits the dark `(auth)/layout.tsx`. Callback page typically renders nothing or a brief "Signing you in…" — render with the dark theme for consistency.
**Detection:** Manual QA in Playwright smoke test.
