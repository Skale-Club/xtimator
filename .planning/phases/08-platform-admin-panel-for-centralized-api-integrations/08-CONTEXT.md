# Phase 8: Platform admin — integrations & branding — Context

**Gathered:** 2026-04-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Introduce a super-admin-only platform panel that centralizes two classes of configuration currently scattered across `process.env` and hardcoded literals:

1. **Shared API integrations** (Resend, Anthropic, OpenAI) — credentials stored once in the DB (encrypted), consumed by all tenants via a single server-side loader with short in-memory cache. Eliminates dependency on Vercel env vars for provider keys and enables rotation without a redeploy.

2. **Global platform branding** — app name, logo, visual identity fetched from DB at runtime so the platform owner (you) can rebrand the chrome (currently "EstimateBuilder Pro" → "Xtimator") without touching code. No platform-brand string may remain hardcoded after this phase.

Also folded: a dark-themed visual pass on `/(auth)/*` routes, isolated from the main app (global dark mode remains V2-06, deferred).

Out of scope:
- Per-tenant API keys (tenants always consume platform-shared credentials)
- Global theme switcher / dark-mode toggle for the main app (V2-06)
- Admin console beyond integrations + branding (metrics, user list, feature flags belong in a later phase)
- Public marketing site

</domain>

<decisions>
## Implementation Decisions

### Secret Storage
- **D-01:** API keys stored in `platform_integrations` table with **app-layer AES-256-GCM encryption** keyed by a new `APP_ENCRYPTION_KEY` env var (stored in Vercel prod + `.env.local` for dev). Supabase Vault (pgsodium) evaluated and rejected as overkill for 3 low-rotation keys. Combined with RLS super-admin-only and Supabase's native at-rest encryption, this gives defense-in-depth without pgsodium operational overhead.
- **D-02:** `APP_ENCRYPTION_KEY` generated with `openssl rand -base64 32` (256-bit). Rotation procedure: set new env, re-encrypt all rows via one-shot admin action, flip env. Document in README.
- **D-03:** DB row shape: `(provider TEXT PK, ciphertext BYTEA, iv BYTEA, auth_tag BYTEA, updated_at TIMESTAMPTZ, updated_by UUID, metadata JSONB)`. Ciphertext never returned to client — only the server-side loader decrypts.
- **D-04:** Providers initially supported: `resend`, `anthropic`, `openai`. Schema allows more without migration (provider is a free text PK, validated in app code).

### Super-Admin Identity & Bootstrap
- **D-05:** New table `platform_admins (user_id UUID PRIMARY KEY REFERENCES auth.users(id), created_at TIMESTAMPTZ DEFAULT now(), notes TEXT)`. Membership = super-admin. Keeps role orthogonal to tenant/company roles and avoids touching `auth.users.raw_app_meta_data`.
- **D-06:** Bootstrap: first admin seeded via one-time SQL in Supabase SQL editor, documented in `supabase/ADMIN-BOOTSTRAP.md`. No env-var allowlist (too easy to misconfigure); no UI self-promotion (forge-proof by requiring DB access).
- **D-07:** `/admin/*` routes protected by middleware that (a) requires authenticated session and (b) checks membership via service-role query to `platform_admins`. Unauthorized → 404 (not 403 — don't reveal the admin surface exists). Performance: membership cached per-request in a request-scoped store (no N+1 across middleware + page + server actions).
- **D-08:** Admin adds/removes other admins from `/admin/admins` (in-scope). First admin cannot self-remove if they're the only one (DB check trigger).

### Global Branding
- **D-09:** New table `platform_branding (id INT PRIMARY KEY DEFAULT 1 CHECK (id = 1), app_name TEXT NOT NULL, logo_url TEXT, primary_color TEXT, email_from_name TEXT, updated_at TIMESTAMPTZ, updated_by UUID)`. Single-row singleton via PK check constraint. Seeded with `app_name='Xtimator'` in the initial migration so the rebrand lands on deploy.
- **D-10:** Boundary between platform brand and company brand is strict:
  - **Platform brand** applies to: auth pages (login/signup/reset wordmark + logo), main app layout (sidebar/topbar wordmark), platform-originated emails (welcome, password reset — `from` name + header), PDF footer "Generated by" line.
  - **Company brand** (already in `companies.logo_url` + `brand_primary_color`) applies to: estimate PDF body (header, accent colors), public share page (`/estimate/[token]` chrome), client-facing email "from" name (company name, not platform).
  - When a feature is ambiguous, default to **whose eyes see it**: tenant-facing = platform; client-facing = company.
- **D-11:** Logo upload reuses the existing `logo-uploader` pattern (`components/onboarding/logo-uploader.tsx`, also used for clients). Stored in new Storage bucket `platform-brand/` with super-admin-only RLS.
- **D-12:** `primary_color` on platform_branding drives auth card accent + nav highlight only. It does NOT override the per-company `brand_primary_color` on tenant-facing artifacts.

### Loader & Consumption
- **D-13:** Single server-side loader module `lib/platform-config.ts` exposes `getIntegrationKey(provider)`, `getBranding()`. Uses in-memory cache keyed on DB `updated_at`; TTL 60s. Loader runs only on server (imports `lib/supabase/service`).
- **D-14:** All existing usages migrated:
  - `process.env.RESEND_API_KEY` → `await getIntegrationKey('resend')` (2 files: `app/api/estimates/[id]/send/route.ts`, `app/estimate/[token]/actions.ts`)
  - `process.env.ANTHROPIC_API_KEY` → `await getIntegrationKey('anthropic')` (2 files: `app/api/generate-estimate/route.ts`, `app/api/analyze-photos/route.ts`)
  - `process.env.OPENAI_API_KEY` → `await getIntegrationKey('openai')` (1 file: audio transcription server action)
  - Hardcoded `"EstimateBuilder Pro"` → `(await getBranding()).app_name` (7 code files: `app/layout.tsx`, `components/auth/auth-card.tsx`, `components/onboarding/onboarding-card.tsx`, `components/share/estimate-view.tsx`, `app/estimate/[token]/actions.ts`, `app/api/estimates/[id]/send/route.ts`, `tests/e2e/auth.spec.ts`)
- **D-15:** Key-missing UX: when a feature's provider key isn't configured, the server route returns HTTP 503 with a friendly message ("Feature not configured — contact platform admin"). Frontend surfaces this as a disabled button with tooltip, NOT a hidden feature. Consistent with the pattern just shipped for Resend in commit `3492264`.
- **D-16:** Environment variables `RESEND_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` deprecated. Loader reads DB first; falls back to env var only if DB row is null (smoothes local dev where admin UI isn't used). Log a warning on fallback.

### Admin UI
- **D-17:** Three admin pages under `app/admin/`:
  - `/admin/integrations` — one card per provider (Resend, Anthropic, OpenAI). Password-masked input, "Test" button that makes a real validation call (Resend: send to admin's own email; Anthropic: 1-token completion; OpenAI: `/models` list). Save encrypts and upserts. "Last updated" timestamp + "who" badge.
  - `/admin/branding` — app name (text), logo upload (reuses `logo-uploader`), primary color (color picker + hex). Live preview card showing the auth wordmark + nav chrome with changes applied.
  - `/admin/admins` — list current super-admins with add/remove. Cannot remove self if last admin.
- **D-18:** Admin UI layout is a minimal shell: left nav with 3 links, page-level h1, shadcn Card forms. No attempt at matching the tenant-app shell. Dark theme by default (distinguishes from tenant surface visually).

### Auth Visual Pass
- **D-19:** `/(auth)/*` route group gets a dedicated `layout.tsx` with dark background (`bg-zinc-950`) and accent from platform `primary_color`. Auth card stays `bg-zinc-900` with subtle border. Wordmark + logo pulled from `getBranding()`.
- **D-20:** Dark styling is scoped via CSS vars on the auth layout wrapper — no `darkMode` strategy in `tailwind.config.ts` change, no `ThemeProvider`. Keeps global dark-mode toggle (V2-06) truly deferred.
- **D-21:** Google OAuth button restyled for dark background (outline variant with light text). Form inputs use shadcn dark variants already present.

### Claude's Discretion
- Exact shadcn dark palette tokens (zinc vs slate vs neutral) — pick what reads best with the platform `primary_color`.
- Whether the `/admin/integrations` "Test" button returns inline status or toast — either is fine.
- How to render the branding live preview — iframe or styled div, planner's call.
- Migration file naming scheme (follow existing `YYYYMMDDHHMMSS_description.sql` pattern).
- Whether to precompute `decrypted_secrets` view in DB vs decrypt in Node — default to decrypt in Node (keeps key material out of postgres logs).

</decisions>

## Existing Code Insights

### Reusable Assets
- **`components/onboarding/logo-uploader.tsx`** — avatar-circle upload already does 2MB limit, PNG/JPG validation, Supabase Storage upload. Plan to reuse for `/admin/branding` logo.
- **`lib/supabase/service.ts`** — service-role client helper; reused for super-admin queries bypassing RLS in middleware.
- **`components/settings/*`** — form patterns (zod + react-hook-form + toast) established for company settings. Admin forms follow the same shape.
- **`components/auth/auth-card.tsx`** — centered-card layout already handles logo + wordmark above card; just needs to consume loader instead of hardcoded strings, plus dark styling.
- **Lazy-SDK pattern** — `app/estimate/[token]/actions.ts` already uses `if (process.env.RESEND_API_KEY) { const resend = new Resend(...) }`. Apply same shape replacing env access with loader call.

### Established Patterns
- **Server actions for privileged ops** (Phase 7 D-21) — admin mutations follow this pattern, not API routes.
- **Route groups for layout scope** (`(app)`, `(auth)`) — `(admin)` group will do the same, with a dedicated layout.
- **RLS-first data access** — `platform_integrations` and `platform_admins` both need super-admin RLS; loader uses service role explicitly to bypass.
- **JWT claims via `getClaims()`** (Phase 1 AUTH-04) — middleware already validates sessions this way; super-admin check layered on top.

### Integration Points
- `middleware.ts` — add `/admin/*` matcher + super-admin check (highest-impact single file).
- `app/layout.tsx` — root layout consumes `getBranding()` for `<title>` metadata.
- Next.js route group `app/(admin)/` — new tree; parallel to `(app)` and `(auth)`.
- `.env.example` — document new `APP_ENCRYPTION_KEY`; mark old provider keys as "optional fallback for local dev".

</code_context>

<specifics>
## Specific Ideas

- App name rebrand target is **"Xtimator"** (platform owner's direction) — seed in initial migration.
- Auth dark mode is a **visual refresh**, not a toggle. Tenant app stays light.
- User explicitly wants **"zero hardcoded"** branding after this phase. Acceptance criterion in verification: grep for `"EstimateBuilder Pro"` in `app/`, `components/`, `lib/` returns zero matches.
- User wants **one shared set** of API keys for all tenants (classic shared-SaaS-platform billing model). No per-tenant BYO-key in v1.

</specifics>

## Deferred Ideas

- **Per-tenant BYO API keys** — may be a v2 upsell for enterprise tenants. Noted as potential V2 requirement.
