# Stack Research

**Domain:** Cross-renderer document pagination (web paginated editor mirrors `@react-pdf/renderer` v4 PDF output)
**Researched:** 2026-07-27
**Confidence:** MEDIUM-HIGH (react-pdf API surface verified against official docs + npm registry ground truth; cross-renderer text-measurement determinism claims are engineering inference and flagged LOW — recommend an early spike, see Version Compatibility)

**Scope note:** This is a *subsequent-milestone, additive* stack file. It does not re-litigate the existing stack (Next.js 16.2.6 App Router, React 19.2.4, TypeScript strict, Tailwind 4, shadcn/ui, `@react-pdf/renderer@4.4.0` already installed, Docker `node:24-alpine`, no puppeteer). It covers only what's needed to make the new in-browser paginated editor deterministically mirror `@react-pdf/renderer`'s page breaks, per the v4.23 Unified Estimate Document Engine milestone.

## Recommended Stack

### Core Technologies

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| `@react-pdf/renderer` | `^4.5.1` (bump from installed `4.4.0`) | Existing PDF renderer, unchanged role | Already the project's only PDF stack (Alpine container rules out puppeteer/chromium). `4.5.1` is the current latest 4.x (verified via `npm view @react-pdf/renderer versions`) — already inside the project's existing `^4.4.0` semver range, so this is a routine lockfile refresh, not a decision. No breaking pagination-API changes found between 4.4.0 and 4.5.1 in release notes (patch-level fixes only, e.g. border rendering). |
| `fontkit` | `^2.0.4` | Node-side font parsing for **deterministic glyph advance-width measurement** — the core primitive a homegrown pagination engine needs to predict wrapped-line heights before `@react-pdf/renderer` renders | `fontkit` is **already a transitive dependency** of the installed stack — both `@react-pdf/font@4.0.8` (react-pdf's own font loader) and `@react-pdf/pdfkit@5.1.1` depend on `fontkit@^2.0.2` (confirmed via `npm view` against the installed tree). Promoting it to a direct dependency means the pagination engine measures text with **the exact same parsing/metrics code react-pdf itself uses internally** — not a second implementation that could drift from react-pdf's actual output. This is the single highest-leverage choice for the milestone's "deterministic mirroring" requirement. |
| `linebreak` | `^1.1.0` | Unicode UAX#14 line-break **opportunity** algorithm (where a line is *allowed* to break — spaces, hyphens, etc.), independent of font metrics | Also already transitive (a dependency of `@react-pdf/pdfkit@5.1.1`). Pairing `linebreak` (break points) + `fontkit` (glyph widths) is a minimal, stable, publicly-documented reimplementation of what react-pdf's own internal `@react-pdf/textkit` does — see "What NOT to Use" for why textkit itself should not be depended on directly. |
| Self-hosted **Inter** TTF files (Regular + Bold, + Italic if the classic template uses it) | N/A (static asset, not an npm package) | Shared, measurement-critical font for the **classic** template — same typeface across `Font.register` (PDF) and the web paginated editor | The app already ships Inter via `next/font/google` in `app/layout.tsx` (`variable: "--font-inter"`) for the whole UI. Reusing it for the PDF closes the metrics gap described in "Alternatives Considered" below, at zero brand-identity cost (it's already the product's font). Needs the **TTF variant** specifically (see WOFF2 caveat below) — obtainable from Google Fonts' TTF export or Inter's own GitHub releases (OFL licensed, no cost). |
| A second self-hosted **serif** TTF (e.g. Source Serif 4 or Lora, OFL-licensed) | N/A (static asset) | Shared, measurement-critical font for the **modern** template, replacing `Times-Roman` (PDF) / Tailwind `font-serif` (web) | The modern webview (`estimate-document-modern.tsx`) already opts into `font-serif` (a generic system-serif stack: Georgia/Cambria/Times New Roman depending on OS) while the modern PDF uses the built-in `Times-Roman` AFM font. Neither is the *same* rendered typeface, so their metrics already diverge today — this milestone's parity goal requires picking one real serif TTF and registering/loading it in both places, the same way as Inter for classic. |

### Supporting Libraries — none new for the pagination algorithm itself

No third-party pagination/layout library is recommended. The pagination *decision logic* (never split a line item; section header keeps with first row; subtotal keeps with last row; totals/photos blocks stay together) is domain-specific business logic, not a generic layout problem — it should be a small, homegrown, pure-TypeScript module (e.g. `lib/estimate/pagination/`) built on the two primitives above (`fontkit` + `linebreak`), not an external pagination framework. See "What NOT to Use" for libraries considered and rejected.

### Development Tools

| Tool | Purpose | Notes |
|------|---------|-------|
| `Font.register` (from `@react-pdf/renderer`, already installed) | Registers the shared TTF fonts server-side for PDF rendering | Call **once at module load** (module-level, not per-request/per-render) and guard against re-registration — react-pdf has no built-in idempotency check, and re-parsing the same font file on every PDF generation is wasted CPU. `src` should be an **absolute filesystem path** into the Docker image (e.g. `path.join(process.cwd(), 'assets/fonts/Inter-Regular.ttf')`), not a remote URL — see "What NOT to Use." |
| `debug={true}` prop (any react-pdf primitive) | Visualizes content/padding/margin boxes during development | Official react-pdf debugging aid (react-pdf.org/advanced) — useful when validating that the precomputed page chunks actually fit the rendered page without relying on react-pdf's own auto-wrap to "save" an underestimate. |

## Installation

```bash
# Core PDF stack — patch bump only, already within the existing semver range
npm install @react-pdf/renderer@^4.5.1

# Node-side deterministic text measurement (promote existing transitive deps to direct)
npm install fontkit@^2.0.4 linebreak@^1.1.0

# Dev dependency for fontkit types (fontkit ships its own .d.ts; verify after install)
npm install -D @types/fontkit
```

Font assets (Inter TTF, chosen serif TTF) are **not npm packages** — download the OFL-licensed TTF files once and commit them under a repo path already covered by the Docker build context (e.g. `assets/fonts/`), so they ship inside the `node:24-alpine` image the same way any other static asset does.

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|-------------------------|
| `fontkit` for Node-side glyph metrics | `opentype.js` | If `fontkit`'s Node-oriented API (uses `fs`, not built for bundling into a browser chunk) proves inconvenient, or if the same parsing code is later needed isomorphically in the browser too. `opentype.js` is a fine, independently-maintained TTF/OTF parser — but it is a **separate implementation** from what react-pdf uses internally, so it carries a (small but real) risk of diverging on hinting/kerning edge cases from what `@react-pdf/renderer` actually renders. `fontkit` wins by being the literal library react-pdf already trusts. |
| Explicit page composition (pure-TS engine precomputes chunks → N `<Page>` elements, both renderers just paint the decision) | React-pdf's automatic `wrap` + `minPresenceAhead` engine as the primary decision-maker | Only if the milestone did *not* need the web preview to mirror the PDF ahead of render time. Automatic wrap is an opaque black box: it decides breaks *during* react-pdf's own render pass, with no way to query "where will page 2 start" before that render happens — which is structurally incompatible with also needing to drive a *separate* React DOM renderer for the web paginated editor. `minPresenceAhead` additionally has multiple long-standing, unresolved upstream GitHub issues where it silently does not hold ([#2658](https://github.com/diegomura/react-pdf/issues/2658), [#2659](https://github.com/diegomura/react-pdf/issues/2659), [#2238](https://github.com/diegomura/react-pdf/issues/2238)) — do not build the parity guarantee on top of it. Confirmed viable/recommended pattern: precompute chunks in the shared module, drive N explicit `<Page>` elements from the array, and keep react-pdf's own `wrap`/`fixed`/`wrap={false}` only as redundant per-block safety nets (mirroring how the codebase already uses `wrap={false}` today, e.g. the photos block in `estimate-pdf.tsx`). |
| DOM `ResizeObserver`-driven live re-pagination as a **secondary, self-correcting** layer only | `ResizeObserver`/mirror-element autosizing as the **primary** pagination mechanism | Live DOM measurement (the classic "autosize textarea" pattern used by many rich-text editors) is accurate for a single browser render, but it has no Node/PDF equivalent — it cannot be the shared source of truth the milestone requires. Use it only as a debounced watchdog that re-invokes the same pure-TS pagination function when live-typed content diverges from the precomputed estimate — never as a competing measurement method. |
| One shared TTF font family per template (Inter for classic, one serif for modern), registered in both renderers | Keep built-in Helvetica/Times-Roman AFM fonts, try to match them with a browser font stack | The 14 standard PDF fonts (Helvetica, Times-Roman, etc.) have their own fixed Adobe AFM metrics tables baked into `pdfkit`. No browser renders literal PostScript Helvetica/Times — `font-serif`/system-sans stacks resolve to Arial/Helvetica Neue/Times New Roman/Georgia depending on OS, none of which share the AFM tables' exact advance widths. Because the parity requirement is specifically about *wrapped* text (item descriptions — the thing that actually determines row height and page breaks), this mismatch is not cosmetic; it silently produces different line-wrap points in the two renderers. This is the actual mechanism CLAUDE.md's "no `Font.register` anywhere" constraint needs to be lifted for. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Puppeteer / Playwright / headless Chromium for PDF or measurement | Explicit project constraint — Docker `node:24-alpine` cannot host a Chromium binary; this was already ruled out for the existing PDF stack and remains ruled out for any new measurement approach | `@react-pdf/renderer` (rendering) + `fontkit`/`linebreak` (measurement), both pure-JS/WASM-free Node libraries with no browser binary dependency |
| `paged.js` / PagedJS (CSS Paged Media polyfill) | Built for **static** print-style pagination of already-rendered DOM via `@page` CSS rules — it mutates/fragments the DOM after layout, synchronously, which fights directly against the milestone's requirement that the paginated editor stay **fully inline-editable** (re-running a DOM-fragmentation pass on every keystroke is expensive and awkward to reconcile with React state). It also shares **no measurement model whatsoever** with `@react-pdf/renderer` — using it would not move the project any closer to "one deterministic page-break rule shared by both renderers," it would just add a *third*, unrelated pagination algorithm to reconcile. ~200KB+ dependency for a problem this milestone should solve with a shared TS module instead. | The homegrown `fontkit` + `linebreak` pagination module (see Core Technologies), driving plain CSS fixed-height page-box `<div>`s |
| `@react-pdf/textkit` as a direct dependency | It is react-pdf's **internal**, undocumented layout-engine package (exports things like `layoutEngine`, `bidi`, `scriptItemizer` with no stable public API contract), versioned in lockstep with the rest of the react-pdf monorepo. Depending on it directly is fragile — a routine react-pdf upgrade could silently change or remove its internals with no deprecation notice, since it's not meant for external consumption. | `fontkit` + `linebreak` directly — the same lower-level, independently-versioned, publicly-documented primitives textkit itself is built on |
| WOFF2 font files passed to `Font.register` | `@react-pdf/font`'s metadata lists woff2 as accepted, but the official react-pdf.org fonts doc states only TTF/WOFF are reliably supported, and community reports (e.g. [react-pdf discussion #2073](https://github.com/diegomura/react-pdf/discussions/2073)) describe rendering problems specifically with WOFF2 files (the format Google Fonts serves by default) | Plain TTF files (or OTF) — download the TTF variant explicitly rather than reusing whatever `next/font/google` optimized for the browser bundle (which is WOFF2) |
| Fetching custom fonts from a remote URL (Google Fonts CSS endpoint, a CDN) inside `Font.register` at render/request time | Adds a network round-trip, latency, and an external failure mode to *every* PDF generation request — a transient DNS/CDN hiccup would break estimate PDFs in production. Also non-deterministic: a remote font could change without a deploy. | Bundle the TTF file locally in the repo, ship it inside the Docker image, and register via an absolute filesystem path resolved from `process.cwd()` |
| A rich-text/canvas editor framework (TipTap, Slate, Lexical, ProseMirror) for the paginated editor mode | The milestone only needs the **existing** inline field-editing (`components/workspace/estimate/estimate-document.tsx`'s current inputs/handlers) to keep working *inside* fixed-height CSS page boxes — it is a layout/pagination problem, not a rich-text-authoring problem. Introducing a full editor framework would mean re-implementing every existing edit interaction (line items, Bill To, notes) on a new content model for no requirement this milestone actually has. | Keep the current React state/inline-input editing model; wrap it in page-box containers driven by the precomputed pagination array |
| Reaching into `yoga-layout` or `@react-pdf/layout` internals to replicate react-pdf's exact flexbox layout algorithm | Over-engineering for this document's actual shape: a top-to-bottom stack of fixed-width-column rows (line items, sections, totals), not arbitrary nested flexbox. Yoga is a general flex-layout engine (also used by React Native) — reimplementing/hooking it is a much larger surface than the pagination problem here requires. | The homegrown TS pagination module needs only: per-row height (a function of wrapped-line count via `fontkit`+`linebreak`, times line-height, plus fixed row padding) and simple vertical accumulation against a known page content height — no general flexbox solver needed |
| A new global state library (Zustand/Jotai) purely for this milestone | Not currently in the dependency tree (verified: absent from `package.json`). The paginated editor is additive UI state (page index, computed chunks) layered on the *existing* estimate-editor state model in `estimate-document.tsx` — introducing a new state paradigm is an architecture decision outside this milestone's stack scope, not a requirement of pagination itself. | Existing React state/context patterns already used by the estimate editor; revisit only if phase execution proves the existing model insufficient |

## Stack Patterns by Variant

**If the classic template's wrapped text must match pixel-for-pixel between web and PDF:**
- Register Inter TTF (Regular + Bold minimum) via `Font.register`, and ensure the web paginated editor's page boxes render actual DOM text in the same Inter font (already true globally via `next/font/google` — just make sure the paginated-mode CSS doesn't override it)
- Because both renderers now measure the same physical font file's glyph outlines, the residual gap becomes rendering-engine-level (subpixel hinting/kerning differences between a browser's text-shaping engine and `fontkit`'s advance-width math) rather than font-identity-level — budget a small safety margin (see Version Compatibility) rather than promising byte-perfect breaks.

**If the modern template's serif identity must be preserved (not swapped to Inter):**
- Pick one open-license serif TTF (e.g. Source Serif 4), register it for the modern PDF template, and load it via `next/font/local` (or a `@font-face` rule) for the modern webview/paginated editor, replacing the generic Tailwind `font-serif` stack for measurement-critical text specifically.

**If a full spike proves the two renderers cannot be made deterministic enough (see the LOW-confidence flag below):**
- Fall back to a generous safety margin on computed page-break heights (e.g. reserve an extra ~2-4% of page content height, or an extra text line's worth of space) so react-pdf's own automatic `wrap` (left enabled as a fallback, not primary) can silently absorb small overestimates by continuing an atomic block onto a following page, rather than clipping content. This degrades gracefully instead of requiring perfect pixel parity.

## Version Compatibility

| Package A | Compatible With | Notes |
|-----------|------------------|-------|
| `@react-pdf/renderer@^4.5.1` | `fontkit@^2.0.4`, `linebreak@^1.1.0` | Both already satisfy react-pdf's own transitive requirements (`@react-pdf/font@4.0.8` → `fontkit@^2.0.2`; `@react-pdf/pdfkit@5.1.1` → `fontkit@^2.0.2` + `linebreak@^1.1.0`) — promoting them to direct dependencies at these versions will dedupe against the same installed copies, not introduce a second parallel version. |
| `Font.register` (react-pdf) | Next.js 16.2.6 App Router server code (Route Handlers / Server Actions) | Must run server-side only (already true for all current PDF generation) — `Font.register` has no client/edge-runtime relevance and should not be imported into any client component. |
| Inter TTF (bundled asset) | `next/font/google` Inter already in `app/layout.tsx` | Same typeface family, different distribution channel (`next/font` optimizes WOFF2 for the browser bundle at build time; the PDF path needs its own separately-sourced TTF file) — they render the same glyph outlines, so widths match even though the file formats differ. |
| **Cross-renderer text-measurement determinism (browser `canvas`/DOM text layout vs Node `fontkit` advance widths for the same TTF)** | — | **LOW confidence / unverified.** No source found that directly benchmarks "browser-rendered wrapped-line count vs `fontkit`-computed wrapped-line count for identical text, font, and width." Both ultimately derive from the font's own `hmtx`/kerning tables, so they *should* agree closely, but browser text-shaping engines (grapheme clustering, ligatures, subpixel rounding) are a different code path from `fontkit`'s JS-level advance-width math. **Recommend an early, cheap spike** (render a page of representative estimate text in both the web page box and a react-pdf PDF, compare actual line breaks) before committing the pagination engine's exact height-estimation formula — this is the single biggest technical-risk unknown for the milestone and should be resourced as its own early phase/spike, not assumed to "just work." |
